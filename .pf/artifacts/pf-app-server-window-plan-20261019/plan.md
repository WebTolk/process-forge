# План: Textual-панель и запуск App Server без пустого окна

Status: ready_for_review
Date: 2026-10-19
Execution mode: planning_only
Implementation: not_started

## Принятое направление

Пользователь выбрал **Textual**. Планируем отдельную терминальную панель,
которая подключается к App Server и сохраняет ему самостоятельный жизненный
цикл. Закрытие панели завершает только панель. Существующий `pf monitor`
остаётся доступен для отдельного запуска и сохраняет прежний read-only
контракт. Автоматический запуск monitor или новой панели не поручен.

Никакой продуктовый код, dependency pin, установленный сервер и автозапуск
в этой Work не меняются. Результат — план для отдельной реализации.

## Основания и границы доказательств

[Исследование](research.md) описывает актуальные символы и наблюдение на
устройстве. Пустое окно появляется при входе в Windows, по словам пользователя.
Найденная scheduled task запускает `pythonw.exe`, а наблюдавшийся сервер
PID 6052 — `python.exe` из иной, пока не восстановленной цепочки. Их время
старта различается. Принадлежность конкретного видимого окна не подтверждена.

В source и установленной копии уже есть `--console`, но scheduled action
его не добавляет. Ни эта особенность, ни `Hidden: false` не доказаны причиной
именно пользовательского окна. Перезапуски ради воспроизведения здесь
не выполнялись. Версия 1.2.0 в двух копиях не доказывает равенства сборок.

## Режим серверного окна

Последнее требование пользователя: на устройстве с GUI серверное окно
не должно открываться обычным пустым окном; предложен свёрнутый запуск.
Затем пользователь предложил проверить, достаточно ли настройки установки.

Проверка установленного `runtime autostart install --help` и исходников
подтвердила существующий `--python`, но не обнаружила флага минимизации.

| Вариант | Что уже имеется | Что потребуется |
| --- | --- | --- |
| Фоновый сервер без консольного окна на Windows | `--python <pythonw.exe>` в существующей установке autostart | Уточнение инструкции агента и проверка фактического установленного action; доработка сервера не нужна, если запуск исправен |
| Сервер с окном, сразу свёрнутым на панели задач | Специального параметра в PF нет | Отдельная доработка presentation/start adapter; одной инструкции про существующий флаг недостаточно |

Основной план сохраняет явное требование пользователя: **свёрнутое окно
при GUI-запуске**. Режим без окна через pythonw — проверенная существующая
альтернатива, которую можно выбрать отдельным уточнением. Его нельзя считать
минимизацией или подменять им текущее требование. Ответ на дополнительный
вопрос о предпочтении пока не получен; отсутствие ответа не меняет поручение.
Textual и будущий список проектов от этого выбора не зависят.

Если выбран режим без окна, в будущую инструкцию установки включить явный
путь к `pythonw.exe` **из того же проверенного окружения PF**, где доступны
его зависимости. Не подставлять произвольный Python и не выбирать pythonw
для MCP: stdio-процесс MCP принадлежит хосту. Установку/замену существующей
scheduled task выполнять только в отдельной порученной операторской операции.
Текущая задача на устройстве уже содержит pythonw; повторная установка
не является доказанным исправлением неизвестного окна.

Если выбран именно свёрнутый запуск, сворачивать только собственное новое
серверное окно в GUI-сессии, сохраняя прямой foreground process под владением
Task Scheduler. Не использовать `cmd start /min` с немедленным выходом,
detached `runtime start`, скрытие scheduled task или сворачивание чужого
терминала с другими вкладками. Для Windows проверить нативное состояние
окна/STARTUPINFO; [ShowWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindow)
различает минимизацию и скрытие. Конкретный механизм потребует отдельной
проверки на classic console и Windows Terminal до приёмки.

Правило GUI определяется возможностью текущей сессии, а не наличием TTY
или одним названием ОС. В headless/SSH/automation окружении не создавать
окна, не загружать GUI-библиотеки и не менять вывод CLI. Windows — исходный
наблюдавшийся сценарий; поддержку минимизации на иных GUI-платформах нельзя
объявлять доказанной Windows-проверкой. Наличие GUI само по себе не служит
сигналом автоматически открыть Textual.

## Первая версия панели

Экран: логотип PF, название рабочего места, PID и версия серверного
экземпляра, отдельно версия клиента при различии, lifecycle/health,
uptime и возраст наблюдения. Состояния starting/ready/degraded/offline/unknown
отображаются явно. Обновление использует существующий ограниченный read path,
без новых обходов проектов, копии metrics collector или scheduler.

Предлагаемые элементы управления:

| Действие | Поведение |
| --- | --- |
| Обновить | Получить новое ограниченное наблюдение; не запускать сервис |
| Открыть монитор | По явному нажатию отдельно открыть существующий `pf monitor` |
| Остановить сервер | Подтверждение с workplace и identity; прежний guarded shutdown; busy/unknown оставляют сервер работающим |
| Закрыть панель | Закрыть только Textual-клиент |

Макет назначения элементов, не исполняемый прототип:

```text
PF  ProcessForge — App Server
Рабочее место: …     Сервер: …     PID: …
Состояние: …         Работает: …   Сведения обновлены: …

[ Обновить ]  [ Открыть монитор ]  [ Остановить сервер ]
                                             [ Закрыть панель ]
```

Кнопки доступны с клавиатуры; мышь — дополнительный способ управления.
Текст, расположение и точный набор полей проверяются на малом терминале.
Список проектов и подробности по проектам **в первую версию не входят**:
это сохранённая [будущая идея](future-ideas.md).

## Архитектура

```text
launcher / Task Scheduler -> один App Server -> существующие Core services
                                     ^
                                     |
                       отдельный Textual-клиент
                                     |
                         пользователь открывает monitor
```

Textual импортируется только адаптером панели и не становится обязательным
импортом Core, Runtime, argparse или MCP. Новый сервер, GUI framework, системный
трей, DI-контейнер, web frontend и миграция CLI на Click/Typer не требуются.
Политики из [domain.md](domain.md) остаются обязательными.

Точки повторного использования: `monitor.collect_snapshot` и его ограничения,
текущие configuration/interval rules, `service` lifecycle/identity и guarded
shutdown. Текущий monitor snapshot не содержит всех желаемых полей: например,
`instance_version` берётся из `runtime_version`, а не из версии Core. Нельзя
переименовать его в версию PF и нельзя менять wire shape старого monitor JSON
ради новой панели. Для недостающих полей нужен узкий проверяемый read contract
панели с прежними источниками и отдельным отображением неизвестного значения.

При остановке подтверждение связано с показанным instance_id. Смена владельца
между показом/подтверждением/вызовом не должна останавливать новый экземпляр
без повторного осознанного действия. Использовать существующие auth,
`require_idle` и `expected_instance_id`; не заменять их проверкой только PID,
legacy unguarded `runtime stop` или force. UI не владеет этими правилами.

Разделение shared reads/operator operations и presentation оформляется
узкими владельцами и явной композицией в будущем scoped изменении. План
не требует рефакторинга всего `service.py` или текущей OOP-программы.

## Этапы будущей реализации

1. **Установить источник окна.** При следующем естественном logon связать
   заголовок/окно с PID, исполняемым файлом, аргументами, родителем и конкретной
   startup registration. Сопоставить с lock/state identity. Не менять task
   и не завершать процессы на основании одного названия Python.
2. **Закрепить режим установки.** Для выбранного пользователем режима проверить
   существующие возможности. Предпочесть документацию и проверку action, если
   их достаточно. Если нужна реальная минимизация — отдельно проектировать
   ровно этот механизм и его переносимость; не смешивать его с Textual loop.
3. **Оформить интерфейс и зависимости.** Утвердить узкий экран/действия,
   отдельный явный способ запуска панели и read/stop contract; закрепить
   версии Textual и поставляемых dependencies, уведомления и способ установки.
   Новое имя команды будет предложением API, а не уже существующей командой.
4. **Реализовать клиент.** Один writer создаёт presentation module и минимальные
   shared adapters; блокирующие observations/stop не замораживают UI. Ошибки
   клиента не меняют состояние сервера. Не добавлять автозапуск панели/монитора.
5. **Проверить целевые сценарии.** Использовать существующие monitor/operator
   checks и добавить только проверки новых рисков UI/lifetime/packaging.
   Отдельно провести Windows logon acceptance, не выдавая terminal fixture
   за доказательство фактического автозапуска на устройстве.
6. **Поставить отдельно.** Source, archive, installation и реальное наблюдение
   GUI/logon квалифицируются по своим слоям. Применение к устройству,
   перезапуск и внешняя публикация не следуют из утверждения этого плана.

## Границы файлов следующей Work

Панель: новый изолированный presentation module, точное имя определить при
admission; существующие `tools/pf_runtime/monitor.py`, `service.py` — лишь
нужные точки интеграции; CLI parser — только явный вход панели, без миграции
старых команд. Автозапуск: `tools/pf_runtime/windows_autostart.py` только
если существующего install option недостаточно. Инструкция установки:
`docs/getting-started/runtime-autostart.md` и русская версия.

Packaging/лицензии: до будущего start включить в read scope `LICENSE`, `NOTICE`,
`bin/**` и фактические dependency/build manifests; здесь они не изменяются.
Required sources следующей Work: этот план, его license note и domain;
базовые framework ADR/domain/direction; текущие исходники/документация,
нужные конкретному результату. Продуктовое write scope назначается отдельно;
нынешняя капсула разрешает только артефакты. UI — новая функциональность,
которую нельзя включить неявно в текущий чистый OOP-рефакторинг.

## Приёмка

| Проверка | Ожидаемый результат |
| --- | --- |
| Причина пустого окна | Есть подтверждённая связь с конкретным стартовым маршрутом |
| Выбранный GUI startup mode | Фактически подтверждён режим без окна или свёрнутое окно; режимы не подменяют друг друга |
| Headless/redirected CLI/MCP | Нет нового окна, заставки в JSON/stdio, UI-импорта или нового обязательного prompt |
| Панель без работающего сервера | Offline/unknown; ничего не запускается автоматически |
| PID/версии/свежесть | Значения относятся к проверенному серверу; неизвестное не заменено версией/PID клиента |
| Закрытие/ошибка панели | Сервер и текущая Work продолжают работу |
| Stop при busy/unknown/смене владельца | Сохраняется прежний отказ; нет автоматического force |
| Monitor | Отдельный запуск по действию пользователя; прежние Q/Esc/Ctrl+C и read-only/JSON контракты |
| Повторный запуск | Второй сервер не создаётся; Task Scheduler сохраняет владение/политику экземпляров |
| Терминалы | Windows classic/Terminal, клавиатура, малый экран; дополнительные платформы проверяются отдельно |
| Установка/доставка Textual | Зафиксированные dependencies и лицензии присутствуют в готовой поставке; старый CLI работает без импорта UI |
| Объём первой версии | Нет списка проектов, web frontend, tray или побочных OOP-переносов |

Откат: отдельный revert собственного будущего source commit и восстановление
точного прежнего scheduled action, если он менялся, только при операторском
поручении. Не сбрасывать checkout и не переписывать PF capsules/history.

## Решения и отложенное

Textual выбран пользователем; отдельный клиент сохраняет независимость
сервера. MIT совместима с заявленной Apache-2.0 PF при соблюдении условий
уведомлений; детали в [license-note.md](license-note.md). Системный трей
не выбран. Список проектов/подробностей отложен. Точный набор dependency
версий, новое имя команды и привязка наблюдаемого окна к процессу остаются
задачами следующего admission/реализации, а не уже полученным результатом.
