Execution mode: planning_only
Implementation: not_started

## Согласованный результат

Уточнения пользователя после первой ревизии имеют приоритет:

1. **Серверное окно при GUI-запуске сворачивается.** При разворачивании или
   ином появлении консоли видны как минимум логотип PF и версия сервера.
   Скрытие окна через pythonw не подменяет минимизацию.
2. **Монитор — отдельный процесс и отдельная будущая фича на Textual.**
   Он открывается автоматически по явной настройке либо вручную, в том числе
   пользовательским ярлыком. Закрытие монитора не останавливает сервер.
3. **Логика одинакова для Windows и Linux.** Общий контракт запуска не зависит
   от названия ОС. Различаются только механизмы взаимодействия с рабочим столом
   и системной регистрацией запуска.
4. **`PFConfig.autostart_pf_app_server_monitor`** — выбранное направление
   настройки будущего автозапуска монитора; предлагаемое default — `false`.
   Сейчас такой ключ не добавлен и не объявляется существующим.
5. Список проектов и просмотр подробностей остаются [будущей идеей](future-ideas.md).

Эта ревизия заменяет рекомендации `plan.md` в части самостоятельной управляющей
панели, её stop-кнопки и нерешённого режима окна. Предыдущая ревизия сохранена
как уже зарегистрированное PF evidence; её байты не переписаны. [Research](research.md)
и [domain](domain.md) фиксируют знания до последних уточнений; изменения
доменных правил описаны ниже. Все изменения здесь — только планирование.

## Что установлено сейчас

Пользователь наблюдает окно при входе в Windows. Точная принадлежность
пустого окна процессу пока не доказана. Зарегистрированная задача использует
pythonw, а текущий server PID 6052 запущен под python по иной цепочке.
Наблюдения сохранены в `device-observation.json`; ничего не перезапускалось.

`runtime serve` / `server run` уже имеют `--console`: он показывает существующий
брендинг только на TTY, но не версию/PID. `runtime start` уже запускает отдельный
долгоживущий процесс с перенаправлением журналов. Windows autostart прямо
выполняет foreground serve под Task Scheduler. Источники/границы версий
перечислены в `research.md` и `source-evidence.json`.

В установленном `runtime autostart install --help` есть `--python`, но нет
флага «запустить свёрнутым». Выбор pythonw означает отсутствие консоли;
Task Scheduler `Hidden` означает скрытие самой задачи в его интерфейсе.
Поэтому нельзя сейчас обещать решение минимизации единственной инструкцией
про уже существующий PF-флаг. Сначала проверяется профиль запуска и
возможности выбранного терминала/рабочего стола; достаточная настройка
предпочтительнее изменения продукта, если она действительно даёт нужный режим.

Документация текущего autostart описывает Windows Task Scheduler; вне Windows
сам CLI сообщает unsupported. Общий будущий контракт не означает, что PF
уже умеет устанавливать Linux units или desktop entries. В этой задаче не
появляется неявное поручение реализовать установщик всех сервисных менеджеров.

## Единый контракт запуска

```text
Общая политика запуска PF
  -> App Server: один экземпляр; GUI-окно свёрнуто; logo + версия в консоли
  -> Monitor: отдельный Textual-процесс только по настройке или запросу
       -> закрытие monitor завершает только monitor
```

Общая политика задаётся до обращения к системному адаптеру. Не писать
«Windows запускает monitor, Linux — нет». При `autostart_pf_app_server_monitor:
false` monitor не открывается ни на одной ОС. При `true` запрашивается один
monitor после подтверждённой готовности сервера в доступной интерактивной
сессии. Его отказ не останавливает сервер и не запускает повторяющийся цикл
новых окон. Без доступного терминала попытка явно пропускается с диагностикой;
сервер остаётся работоспособным.

Headless/SSH/service окружение не требует создания GUI-окна и не импортирует
desktop библиотеки ради определения режима. Наличие GUI и наличие терминала
различаются: Textual можно вручную открыть в поддерживаемом терминале без GUI.
Пользовательский ярлык — альтернативный ручной вход, не обязательная установка
ярлыков на каждом устройстве.

Минимизация касается только принадлежащего PF серверного окна. Не сворачивать
терминал пользователя со сторонними вкладками. В Windows сохранить владение
foreground server процессом Task Scheduler; не заменять его detached launcher,
который сразу выходит. Для Linux определить поддерживаемые terminal/desktop
backends и проверить X11/Wayland: нельзя объявить один системный вызов общим
универсальным флагом. Источники для проверки механизмов:
[Microsoft ShowWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindow),
[Freedesktop EWMH](https://specifications.freedesktop.org/wm/latest-single/).
Общей остаётся политика; фактическая минимизация принимается по наблюдению.

Если рабочий стол не поддерживает запрошенный режим, он не считается
успешно выполненным: фиксируется ограничение backend, а видимая консоль
всё равно содержит информативный header. Не менять режим на pythonw молча.

## Серверная консоль: ближайшая задача

Показать существующий логотип PF и **версию запущенного серверного Core**,
а также PID и короткое пояснение назначения окна. Не путать версию Core
с `runtime_version`, Python version или версией отдельно запущенного клиента.
`starting`/готовность обозначать по фактической инициализации, а не по
появлению заставки. Для неинтерактивного вывода сохранить прежние JSON,
MCP stdio, ошибки и журналы, без декоративного текста/ANSI.

Существующий `--console` и брендинг повторно использовать там, где подходит
контракт. Если потребуется автоматический header видимого foreground serve,
это явное изменение только человеческого вывода этой команды в новой Work,
а не случайное изменение всех CLI-команд или чистого OOP-рефакторинга.
Textual и новые dependency installs для такого header не нужны.

Закрытие самой серверной консоли может завершить сервер; сворачивание его
не останавливает. Это сообщается в header. Штатная остановка остаётся
прежним отдельным операторским действием с identity/auth/busy guards.

## Textual-монитор: отдельная следующая фича

Первая версия — read-only TUI существующего `pf monitor`: логотип,
workplace, версия/PID сервера, lifecycle/health, uptime и свежесть наблюдения;
переключение подробностей, обновление и выход с клавиатуры, мышь дополнительно.
Существующие plain/`--once`/`--json`, exit codes и самостоятельный запуск
сохраняются. Управление сервером/stop-кнопки сюда не добавляются автоматически.

```text
PF  ProcessForge Monitor
Сервер: …   PID: …   Состояние: …   Сведения обновлены: …

[ Обновить ]  [ Подробности ]  [ Закрыть монитор ]
```

Повторно использовать `monitor.collect_snapshot`, существующие bounded reads,
freshness/configuration intervals и представления metrics. Не обходить проекты
ради заполнения экрана, не добавлять второй scheduler/collector. В текущем
monitor JSON `instance_version` берётся из runtime version, а не Core version;
для новых полей нужен корректный узкий read contract, без переименования старых
wire-полей. Неизвестный PID/версия остаются неизвестными.

Textual импортируется только TUI-адаптером. Core, App Server, MCP и обычный
CLI не требуют установленного Textual для своей работы. Нужен отдельный
согласованный dependency/build профиль UI; при отсутствии библиотеки ручной
запуск TUI даёт понятный отказ, а сервер продолжает работу.

Поле `PFConfig.autostart_pf_app_server_monitor` проектируется в этой же
отдельной фиче: boolean, default false, прежняя проверка конфигурации,
одна точка принятия решения при startup, защита от дублирования окон на
одном workplace/user session. Не запускать monitor при каждом чтении PFConfig
или каждом такте metrics. Вопрос о reload не превращать в автоперезапуск UI.

## Последовательность будущих Work

1. **Окно сервера.** Подтвердить источник окна; описать общий launch contract;
   проверить, достаточно ли профиля установки/ярлыка/terminal; реализовать
   только недостающую минимизацию и header с версией. Обновить инструкции
   агента по установке, различая минимизацию и pythonw. Это ближайший результат.
2. **Textual-монитор.** Отдельно согласовать UI/read contract и dependency pins,
   реализовать renderer и PFConfig-флаг ручного/автоматического запуска,
   сохранить read-only и независимость сервера. Не переносить в эту Work
   список проектов или управление сервером.
3. **Список проектов.** Пока только сохранённая будущая идея, без admission,
   реализации, расписания или обещания срока.

Перед реализацией создать новый явный продуктовый scope с одним writer.
Обязательные входы: эта ревизия, domain/research/license note, актуальные
framework ADR/domain/direction и нужные текущие исходники. Дополнительно
разрешить чтение `bin/**`, LICENSE/NOTICE и реальных dependency/build manifests.
Нынешнюю капсулу не расширять и не возобновлять после завершения.

Предполагаемые точки изменения: `tools/pf_runtime/service.py` и входные
launcher/adapters для первой задачи; `windows_autostart.py` только при
необходимости; обе языковые инструкции runtime-autostart. В мониторной
фиче — изолированный Textual renderer, конфигурационная модель/хранилище,
точки запуска и UI packaging. Точные новые имена файлов/CLI определяются
admission соответствующей Work. Переписывание монолита, DI, общего logging,
новый HTTP API, Qt/tray или новые системные установщики в эти границы не входят.

## Приёмка и откат

| Проверка | Ожидается |
| --- | --- |
| GUI startup Windows/Linux | Одинаковая политика, серверное окно свёрнуто; backend и фактический результат зафиксированы |
| Развёрнутая/видимая консоль сервера | Логотип PF, версия серверного Core, PID и назначение; окно не пустое |
| Headless / redirected CLI / MCP | Нет побочного GUI/TUI, декоративного вывода в JSON/stdio и обязательной UI-зависимости |
| Singleton / service manager | Один сервер; прежний владелец процесса и guards сохранены |
| Monitor flag false | Автозапуска monitor нет на всех поддержанных ОС |
| Monitor flag true | Одна отдельная TUI после готовности; при невозможности открыть терминал явная диагностика, сервер работает |
| Ручной monitor / ярлык | Работает независимо от autostart-флага |
| Выход/сбой monitor | Сервер и текущие работы продолжаются |
| CLI/данные monitor | Прежние JSON/plain/exit/read-only, freshness/unknown и bounded budgets |
| Platform matrix | Windows classic/Terminal; Linux выбранные X11/Wayland desktop/terminal backends; отдельно headless/SSH |
| Delivery/license | Проверены конкретные зависимости, уведомления в архиве и отсутствие Textual import в обязательном серверном пути |

Это проверки будущей реализации. Сейчас проверены документы, ссылки,
селекторы и сохранность исходников; продуктовые smokes, архив, установка и
GUI/logon acceptance не запускались. Результат source не подменяет результаты
archive/installed/connected/device слоёв.

Откат будущей реализации: revert только собственного source commit и
восстановление точного прежнего startup action, если он менялся, в отдельно
порученной операторской операции. Не сбрасывать checkout, пользовательскую
конфигурацию и PF history. План не разрешает установку или перезапуск устройства.
