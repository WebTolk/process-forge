# Доменные правила окна и панели App Server

Status: ready_for_review
Date: 2026-10-19
Основание: [research.md](research.md), текущие контракты Runtime и monitor.

## Модель

App Server — необязательный долгоживущий процесс рабочего места, владеющий
singleton, HTTP endpoint, scheduler и своим состоянием. CLI-команда запуска
или Task Scheduler создают процесс; способ отображения не создаёт второй
сервер и не меняет полномочия Work.

Консоль foreground-сервера — представление внутри серверного процесса.
Отдельная TUI/GUI-панель — клиент работающего сервера. Существующий
`pf monitor` — самостоятельный клиент только для чтения. MCP — иной
stdio-процесс, которым владеет приложение-хост.

```text
Task Scheduler / явный запуск -> один App Server -> существующий Core
                                      ^
                                      |
                    отдельные monitor / TUI / GUI клиенты
```

Схема показывает рекомендуемую границу процессов для клиентского UI;
новая TUI/GUI пока не существует. Фоновый сервер не зависит от наличия окна.

## Правила

1. Версия и PID в интерфейсе относятся к серверному экземпляру; версия клиента
   показывается отдельно, если отличается. Источник — уже проверяемый state
   и существующее чтение identity, а не PID самой панели.
2. `starting`, `ready`, `degraded`, `stopping`, `stopped`, `unknown` различаются.
   Вывод логотипа не означает готовность. `ready` допустим после успешного
   bind/инициализации; устаревшее наблюдение не становится здоровьем.
3. Во foreground-консоли закрытие окна/сигнал может завершить сервер.
   Сворачивание не является остановкой. Интерфейс сообщает это прямо.
4. У отдельного клиента закрытие/выход завершают только клиента. Остановка
   сервера — отдельное действие с точным workplace/instance_id и существующими
   проверками занятости. При отказе busy/unknown сервер продолжает работать;
   нет автоматического перехода к force.
5. Действия с сервером не вызываются из события закрытия окна клиента.
   Не скрывать завершение серверного процесса под названием «выход из панели».
6. `pf monitor` сохраняет read-only контракт, клавиши выхода и прежние JSON/exit
   коды. Управляющая TUI/GUI требует отдельного согласованного интерфейса.
7. Кнопка «Монитор» лишь по действию пользователя запускает существующий monitor
   отдельно. Старт сервера/панели не открывает monitor автоматически.
8. UI не повторяет scheduler, сканирование проектов или сбор metrics. Получает
   ограниченные текущие данные прежними read paths; при отсутствии сервера
   показывает offline/unknown без побочного запуска или ремонта.
9. Human output не попадает в MCP stdout, CLI JSON и перенаправленные потоки.
   Для `pythonw` стандартные потоки могут отсутствовать; их наличие нельзя
   предполагать. ASCII/plain fallback и отсутствие terminal effects в automation
   сохраняются. Источник: [Python sys](https://docs.python.org/3.14/library/sys.html#sys.__stdout__).
10. Scheduled action сохраняет foreground-процесс под владением Task Scheduler,
    principal, logon trigger, single-instance и restart policy. Заменять его на
    detached `runtime start` без отдельной архитектуры нельзя.
11. Ошибка UI не должна прекращать сервер или объявлять Work завершённой.
    Выбор Textual/Qt не переносит правила stop/auth/identity в виджеты.
12. Приватные token/полные state/journals не выводятся в представление.
    Snapshot и capsule permissions не меняются из UI.

## Закрытие консоли Windows

Windows отправляет событие закрытия процессам присоединённой консоли и даёт
ограниченное время очистки. Обработчик не превращает нажатие X в надёжное
«свернуть в трей». Поэтому для обещания «закрытие панели не останавливает
сервер» нужна отдельная клиентская граница.
Основание: [Microsoft HandlerRoutine](https://learn.microsoft.com/en-us/windows/console/handlerroutine).

Для tray-варианта до реализации согласуются иконка, tooltip, меню,
восстановление представления и поведение при logoff/Explorer restart.
Трей не является свойством Textual; это GUI-вариант.

## Соответствие архитектуре PF

ADR D01–D03: UI — тонкий отдельный адаптер общих прикладных операций.
D05: владелец клиента закрывает свои ресурсы, не чужой сервер.
D06/D07 и R04/R07/R12: прежние grants, identity, отказы, journals и private
boundaries сохраняются. D09: обычная явная Python-композиция без нового
универсального контейнера. D11/R03/R10: реализация требует новой scoped Work,
точных required_sources и одного writer; этот план не расширяет капсулу.
