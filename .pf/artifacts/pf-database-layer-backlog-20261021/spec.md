# Общий слой доступа к БД для PF и процессов; единое хранилище журналов

Task: `pf-database-layer-and-journals-20261021`.
Run: `pf-database-layer-backlog-20261021`.

Статус: будущая задача, зарегистрированная по поручению пользователя.
Текущий этап — сохранение требований и исследований. Библиотека и окончательная
схема не выбраны; реализация, установка зависимостей и перенос данных не начаты.
Для выполнения потребуется отдельный актуальный Work с соответствующим scope.

## Основание и проблема

При подготовке обновления устройства защита остановки Runtime стала обходить
файлы статусов исполнителей в `.pf/runtime/agent-runs/`, включая завершённые
запуски. Проверка с исходным бюджетом прервалась на 513-м элементе каталогов
при лимите 512, после 44 чтений файлов за 0,0631 секунды. Результат partial/budget
превратился в `409 runtime_busy_or_activity_unknown`. Отдельное полное
наблюдение двух зарегистрированных проектов показало running=0.

Это проверяемый дефект масштабирования. История работы предназначена для аудита
и не должна препятствовать текущей работе. Увеличение лимита обхода не решает
задачу роста от сотен до 400 000 и более запусков. Историю Вахтёра (Agent Ledger)
и состояние конкретных worker-процессов следует различать.

## Требования пользователя

1. Перенести историю запусков из набора JSON-файлов в SQLite. Сохранить историю
   и устойчивые идентификаторы; её объём не определяет текущую занятость.
2. Рассмотреть все журналы рабочего места как общее хранилище с отдельными
   таблицами, моделями и разграничением проектов/сессий/исполнений.
3. Общий API доступа к БД должен использоваться как внутри Core PF, так и
   процессами для прикладной работы с другими базами. Журналы PF — один
   потребитель этого API, а не его единственное назначение.
4. Поддержать расширяемые драйверы/адаптеры: SQLite, MySQL/MariaDB, PostgreSQL,
   ClickHouse и последующие реализации в пределах проверенных возможностей.
5. Предусмотреть локальные и удалённые подключения через PFConfig:
   именованные профили, driver, database/schema, path либо host/port,
   ссылки на секреты, TLS, таймауты, соединения/pool и driver options.
6. Нужны конструирование запросов, SQL-типы и привязка параметров. Полный ORM
   и отдельный MVC-каркас не являются обязательными требованиями.

## Сохранённые выводы исследования

SQLAlchemy — внешняя зависимость. SQLAlchemy Core можно использовать без ORM,
но зависимость на пакет остаётся. Core предоставляет SQL-выражения, типы,
диалекты, соединения, выполнение и транзакции и близок по уровню к
Joomla Framework Database.

PyDAL — второй прямой кандидат: самостоятельный Database Abstraction Layer,
выделенный из web2py. Фреймворк для его использования не требуется; он предлагает
таблицы/поля, запросы и адаптеры. Миграции при доступе к существующей БД должны
быть явно отделены от обычной работы. Peewee также рассмотрен как внешняя ORM.
PyPika покрывает преимущественно построение SQL, поэтому весь слой выполнения
и управления подключениями им не заменяется.

Фреймворки/библиотеки могут реализовывать общие backend-адаптеры, используя готовые
клиенты СУБД. CMS и магазины часто переиспользуют этот слой: Wagtail, django CMS,
Oscar и Saleor используют Django ORM; Flask/FastAPI позволяют выбрать библиотеку.
Plone использует ZODB с заменяемым storage. Неверно, что каждый крупный продукт
пишет собственные низкоуровневые клиенты БД.

Повторное использование общего API в Core и процессах не обязывает PF создавать
свой SQL-конструктор, универсальную ORM и систему SQL-типов. Нужно оценить
готовый DAL/SQL toolkit с тонкой интеграцией PF. SQL-типы и преобразования
значений необходимо отличать от статической типизации Python, проверки входа
и типизированных результатов прикладных операций.

## Архитектурные границы для проработки

- Общая инфраструктура БД и её драйверы, прикладные модели/репозитории журналов
  и потребители в Core/процессах имеют отдельные обязанности.
- PFConfig/ConfigService уже отделены от адаптера хранения конфигурации.
  Настройка подключения не должна требовать подключения к настраиваемой БД.
- История завершённых запусков и оперативный учёт текущих/незавершённых
  исполнений разделяются. Проверка остановки получает актуальные исполнения,
  проверяет процессы/heartbeat и текущие запросы/scheduler, не восстанавливая
  состояние полным обходом истории.
- Неполнота необязательной истории не превращается в busy guard. Реальная
  неопределённость текущего исполнения не подменяется нулём.
- В существующих SQLite-журналах PF есть также обязательные ID приёма,
  незавершённая обработка, идемпотентность и факты проверок. Их гарантии
  сохраняются отдельно от необязательного аудита.
- Единая физическая БД не устраняет конкуренцию писателей и длительные
  блокировки. Архивная нагрузка должна быть ограничена и при необходимости
  изолируема от оперативного учёта через общий контракт.
- Матрица возможностей драйверов проверяется по ролям. Официальный
  ClickHouse Connect SQLAlchemy HTTP-диалект не предоставляет обычные
  серверные commit/rollback и unique/FK constraints; наличие подключения
  через общий SQL API не доказывает пригодность для оперативных транзакций.
- Доступ к общему хранилищу не расширяет доступ процесса/агента к другим
  проектам. Секреты не включаются в публичные описания процессов и отчёты.

## Миграция и совместимость

Сначала инвентаризировать владельцев журналов, читателей и операции текущего
состояния. Сохранить действующие CLI/MCP-контракты и файловые сценарии PF.
Предусмотреть совместимость старых конфигураций и локальный режим без внешнего
сервера БД. Смена профиля/драйвера с другими данными требует управляемого переноса.

Миграция: штатный backup работающей БД, проверка целостности, сохранение исходных
байтов и порядка в пределах контрактов, повтор без дублирования, сохранение
повреждённых/конфликтующих записей, явное переключение владельца записи и
восстановление при незавершённой операции. Перенос проекта должен позволять
экспортировать его журналы из общего workplace-хранилища.

## Критерии будущей приёмки

1. Пустая история, около 510 и не менее 400 000 завершённых запусков при нуле,
   одном и нескольких текущих исполнениях. Обычная работа и штатная остановка
   не зависят от полного чтения накопленной истории и не требуют force из-за
   числа завершённых записей.
2. Проверки планов запросов, индексов, числа прочитанных записей и памяти;
   постраничное чтение истории с курсорами. Сопоставимые измерения задержек
   до и после роста данных и под архивной нагрузкой, с описанной средой.
3. Конкурентные CLI/MCP/Runtime/процессы, гонка старта с остановкой, перезапуск,
   stale heartbeat, повторное использование PID, незавершённый старт/выход,
   повторы событий и неизвестное текущее состояние.
4. Локальные/удалённые подключения, сетевые таймауты и восстановление,
   redaction секретов, разграничение проектов, backup/restore, повтор
   миграции, quarantine и старые конфигурации.
5. Общие contract tests и реальные интеграционные проверки каждого заявленного
   драйвера. Возможности, проверенные только на одном backend, не объявляются
   универсальными.
6. В конце каждой реализованной задачи — применимые полные PF-тесты и Python
   QA инструментами PF с использованием локальных знаний Python; затем коммит
   и push в оба remote, GitVerse через токен, с точным readback SHA.
