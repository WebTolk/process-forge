# Доступ к данным в Python-фреймворках, CMS и магазинах

Исследование по запросу пользователя от 2026-10-21. Изучены локальные знания
Python PF, действующие проектные документы и официальная документация проектов.
Это сравнение архитектур: установка библиотек, запуск чужих продуктов,
изменение Core и миграция данных не выполнялись. Замеров производительности
этих продуктов и проверки PF на 400 000 строк в этом исследовании нет.

## Ответ о зависимости и собственных драйверах

SQLAlchemy — внешняя библиотека. Её выбор добавит зависимость PF и обязанности
по фиксации версии, поставке, совместимости и обновлению. Для конкретной СУБД
нужен соответствующий DB-API клиент. SQLite можно обслуживать стандартным
модулем Python sqlite3; серверные СУБД требуют своего клиента.
[SQLAlchemy: установка и DBAPI](https://docs.sqlalchemy.org/en/21/intro.html#installing-a-database-api),
[SQLAlchemy: диалекты](https://docs.sqlalchemy.org/en/21/dialects/index.html),
[Python sqlite3](https://docs.python.org/3/library/sqlite3.html).

Вопрос «все крупные продукты пишут свои драйверы?» требует различать уровни:

1. Клиент СУБД реализует подключение и протокол, например psycopg или PyMySQL.
2. Backend/диалект приводит особенности СУБД к общему API ORM или SQL-библиотеки.
3. Модели и прикладной слой реализуют предметные операции продукта.

Django и SQLAlchemy поддерживают собственные общие адаптеры поверх DB-API.
Рассмотренные CMS и магазины на Django переиспользуют этот слой. Это не модель
«каждый продукт заново пишет клиент PostgreSQL и универсальный SQL-компилятор».
DB-API унифицирует интерфейсы соединений и курсоров, но не устраняет различия SQL
и гарантий разных СУБД. [PEP 249](https://peps.python.org/pep-0249/),
[Django: базы и драйверы](https://docs.djangoproject.com/en/6.1/ref/databases/).

## Сопоставление продуктов

| Продукт | Как устроен доступ к данным | Подключения и изменение схемы |
| --- | --- | --- |
| Django | Собственный ORM: классы моделей, поля и API запросов; SQL зависит от backend. | Общие настройки БД, backend-адаптеры и внешние клиенты СУБД; миграции входят в Django. Для изменения существующей схемы документация рекомендует отдельный мигратор, например Alembic. [Интеграция](https://flask-sqlalchemy.palletsprojects.com/en/stable/), [настройка](https://flask-sqlalchemy.palletsprojects.com/en/stable/quickstart/), [binds](https://flask-sqlalchemy.palletsprojects.com/en/stable/binds/). |

| Saleor | Модели товаров используют django.db.models и PostgreSQL-специфичные поля/индексы. | DATABASE_URL документирован как подключение PostgreSQL. Это выборка архитектур, а не утверждение обо всех Python-продуктах. Она показывает
два варианта: собственный общий слой у фреймворка либо переиспользование готового
слоя приложением. Отдельные модели продукта остаются его ответственностью.

## Дополнительный кандидат: Peewee

Peewee — самостоятельная внешняя ORM, поэтому замена SQLAlchemy на неё не означает
отсутствия зависимости. Документация описывает модуль с моделями, Database-классами,
поддержкой SQLite/PostgreSQL/MySQL/MariaDB и необязательными клиентами выбранных
серверных БД. SQLite использует sqlite3. Настройки соединений и операции транзакций
находятся в Database. В актуальной просмотренной документации есть средства
миграций playhouse и runner pwmigrate, включая генерацию по разнице схем.
[Обзор](https://docs.peewee-orm.com/en/latest/),
[БД](https://docs.peewee-orm.com/en/latest/peewee/database.html),
[миграции](https://docs.peewee-orm.com/en/latest/peewee/db_tools.html).

Для PF это кандидат на сравнение размера API, зависимостей и сложности поддержки,
а не заранее выбранная «бесплатная» замена. Сравнения времени запуска, памяти,
производительности и совместимости конкретных версий ещё не проводилось.

## ClickHouse: подключение не равно одинаковым гарантиям

У ClickHouse Connect уже есть SQLAlchemy-диалект: общий интерфейс не требуется
писать с нуля. Однако официальная документация диалекта явно ограничивает его
семантику: серверные commit/rollback через этот HTTP-диалект не выполняют обычную
транзакцию; стандартные unique/FK constraints не обеспечиваются; поддержка ORM
не включает обычный полный цикл обновления объектов и отношений.
[ClickHouse: поддержка и ограничения SQLAlchemy](https://clickhouse.com/docs/integrations/language-clients/python/sqlalchemy#scope-and-limitations).

Мой вывод: такой backend можно рассматривать для архива и аналитики, но нельзя
автоматически назначать владельцем оперативной уникальности, leases или атомарных
изменений только потому, что подключение создаётся через SQLAlchemy. Роль каждого
драйвера должна подтверждаться contract tests и реальными интеграционными проверками.

## Что из этого предлагается для PF

Это рекомендации по результатам сравнения, а не уже принятая реализация.

1. Сохранить собственный небольшой прикладной API: модели/репозитории журналов,
   текущих исполнений и нужных предметных операций. Выбор технической библиотеки
   должен оставаться за адаптером хранения.
2. Настройки соединений разместить в существующем PFConfig/ConfigService:
   именованные подключения, driver, database/path либо host/port, TLS,
   secret_ref, таймауты, pool и явно допустимые driver options. Bootstrap
   конфигурации не должен требовать подключения к той базе, адрес которой
   только предстоит прочитать.
3. Выбирать между ограниченным собственным адаптером на sqlite3/DB-API,
   SQLAlchemy Core и небольшой ORM после проверки потребностей PF. Свой
   тонкий PF-адаптер отличается по объёму от своего универсального ORM.
4. SQLAlchemy Core можно использовать без работы через ORM; библиотека при
   этом остаётся той же внешней зависимостью. SQLModel не устраняет её,
   поскольку сам построен поверх SQLAlchemy и Pydantic.
   [Компоненты SQLAlchemy](https://docs.sqlalchemy.org/en/21/intro.html#overview).
5. Общая база журналов с отдельными таблицами и project/session/run identity
   соответствует обсуждаемому направлению, но не заменяет разделение истории
   и оперативного учёта. Запрос текущей занятости не восстанавливает состояние
   из всех исторических запусков.
6. Миграции, backup/restore, индексы, ограниченные транзакции, пагинация,
   разграничение проектов и реакции на сетевые отказы должны быть частью
   контракта независимо от выбора ORM.
7. Для обещания «работает на 400 000 завершённых запусков» нужны реальные
   проверки планов запросов, объёма чтения и памяти, задержек обычной работы
   и остановки при параллельной архивной нагрузке. Ни одна ORM сама по себе
   не подтверждает выполнение этого требования.

## Варианты для последующей проверки

| Вариант | Добавляемые зависимости | Что PF придётся поддерживать |
| --- | --- | --- |
| Узкие репозитории и sqlite3; остальные DB-API клиенты по выбранному драйверу | Для SQLite не нужен отдельный Python ORM-пакет; серверные клиенты добавляются отдельно | SQL для требуемых операций, различия backend, схемы/миграции, соединения и contract tests |
| Репозитории поверх SQLAlchemy Core | SQLAlchemy и клиент выбранной БД; мигратор оценивается отдельно | Предметные операции PF, схема, миграции, конфигурация, адаптеры и доказанная матрица возможностей |
| Модели Peewee | Peewee и клиент выбранной серверной БД | Модели/репозитории PF, привязка поддерживаемых backend, миграции, конфигурация и contract tests |

Тянуть Django или иной web-фреймворк только ради журналов PF из изученных примеров
не следует. Их опыт полезен как образец организации моделей, конфигурации и
переиспользования доступа к данным. Конкретная библиотека PF этим исследованием
не выбрана и не установлена.

## Границы достоверности

- Источники — официальная документация и исходник Saleor; изучены 2026-10-21.
- Ссылки stable/latest/main изменяемы; версии зависимостей для PF не зафиксированы.
- Локальные знания PF подтвердили стандартный sqlite3. Поиск по доступным
  ресурсам не дал архитектурного сравнения CMS/ORM, поэтому использованы
  официальные внешние источники по явному запросу пользователя.
- Документация Odoo 20 ORM при чтении вернула timeout; она не использована
  как основание выводов о текущей архитектуре Odoo.
- Исследование не является принятием драйверов PF, результатом нагрузочного
  теста или разрешением мигрировать реальные журналы и менять устройство.
