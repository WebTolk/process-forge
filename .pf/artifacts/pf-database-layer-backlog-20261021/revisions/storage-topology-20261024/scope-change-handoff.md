# Уточнение границы SQL и поиска знаний

2026-10-24. Связано с существующей задачей
`pf-database-layer-and-journals-20261021`.

Оператор подтвердил одну основную SQL-базу рабочего места и проектные базы
в `.pf`, без самостоятельной рабочей БД для каждой подсистемы PF.
Затем оператор отдельно оставил размещение поискового индекса на исследование:
нагрузка нескольких агентов не должна страдать от индексации; для знаний
планируется будущий RAG. Бухгалтерия PF остаётся в SQLite, с возможностью
последующих SQL-адаптеров, например MariaDB.

Первоначальная формулировка primary «поисковый индекс тоже должен храниться
в базе соответствующего уровня» была предположением primary. Она не является
утверждённым требованием. Её нельзя включать в подтверждённую топологию.

Предыдущая Work:
`garage-db-storage-topology-clarification-20261024-capture-the-operator-c`;
assignment `db-storage-topology-clarification-20261024-capture-the-operator-confirme`;
capsule `4d7e6daa64acec01191eef9f1663b3b8748223dbad278a12264d05869e0f9009`.
Она остановлена на orchestration; requirements.md и current-requirements.json
не создавались. Продукт, базы и инфраструктура не изменялись.

Нужен ограниченный planning-only successor: сохранить подтверждённую SQL-модель,
исследовать разделение нагрузки SQLite и отдельную границу retrieval/RAG,
явно оставить физическое размещение поискового индекса и его backend открытыми.
Нельзя считать будущий RAG реализованным или заранее выбирать внешнюю vector DB.
Оригинальные spec, research, planning card и capsule сохраняются.
Общий планировщик агентов не относится к этой работе.
