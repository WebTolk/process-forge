## Что он делает сейчас

`RuntimeProcess.scheduler_loop`, tools/pf_runtime/service.py:558, после паузы interval=2.0 безусловно вызывает `host.tick_payload(...director=True,inspector=True)` для каждого зарегистрированного проекта. Это пауза между проходами, а не гарантированный двухсекундный период: сам проход тоже занимает время. Служебные интервалы отдельных jobs в status не ограждают эти вызовы.

`host.tick_payload`, tools/pf_runtime/host.py:1389, под общим RLock загружает состояние Host, запускает Director/Supervisor, обновляет проекцию и безусловно сохраняет состояние. Метаданные входов проекции уже кэшируются: её доля всего0.20% текущих отсчётов.

`command_supervisor_tick`, tools/processforge.py:18164, каждый раз вызывает `active_run_ids`, tools/processforge.py:12419. Та обходит все `runs/*/run.yaml` и полностью загружает каждый YAML, чтобы прочитать id/status. В текущем проекте569 таких файлов, суммарно16028005 байт. Завершённый run тоже разбирается до того, как status позволит его исключить. Внутри оставшихся активных запусков затем читаются планы, задания и состояния workers; исторические failed/recovery состояния повторно наблюдаются. Эта диагностика не исправляла и не закрывала чужие Work.

`RuntimeProcess.known_project_roots` также вызывает `host.load_state`. `host.load_state`, host.py:384, читает весь `runtime/pf-runtime-host/state.json`; `host.save_state`, host.py:402, меняет служебные поля и целиком перезаписывает его. Файл занимает37833078 байт (около36.1MiB). Он содержит проекты, сессии и отложенные захваты переписки. Он остаётся самостоятельным владельцем состояния и не стал SQL-таблицей при переносе журналов хуков. Эти операции выполняются в планировщике и на пути входящих событий.

## Граница следующего исправления

Нужно отдельно сократить повторную работу владельцев каталога запусков и состояния Host. Конкретная область для новой source Work: tools/pf_runtime/service.py, tools/pf_runtime/host.py и владелец runtime-наблюдения запусков, вызывающий active_run_ids/command_supervisor_tick. Не расширять эту задачу до общего изменения всех CLI/Work readers.

Для каталога: повторно разбирать изменившиеся документы, сохранять обнаружение новых/изменённых/удалённых run и порядок результатов. Авторитетные Work/readiness/gates должны продолжать читать актуальные данные; нельзя скрыть изменения произвольным TTL-кэшем или считать terminal-статус вечным.

Для Host: отделить небольшой рабочий реестр проектов/сессий от больших отложенных payloads и убрать полную запись неизменившегося состояния на каждом tick. Не удалять отложенную переписку ради уменьшения файла; сохранить восстановление, межпроцессные изменения и резервный путь hooks. Вариант хранения и необходимость миграции должны быть зафиксированы владельцем до реализации.

Это предложение для ограниченного следующего исправления, а не выполненная оптимизация. Повторная установка нынешнего архива, новая миграция журналов или увеличение интервала сами по себе не устранят перечисленные алгоритмы.
