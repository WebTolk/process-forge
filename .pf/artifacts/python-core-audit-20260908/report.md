### F01 — обход проектной изоляции поиска

`runtime_snapshot` проекта вычисляется, но запрос выполняется через `ResourceSearchIndex`, созданный с `index_snapshot` всего Workplace. Внутри `local_resource_search.search()` именно переданный snapshot определяет разрешённые ID. `add_private_navigation()` лишь добавляет навигацию и не удаляет запрещённые результаты.

Воспроизведение использует настоящий временный Workplace, обычное создание проекта, зарегистрированные пакеты, штатное обновление контекста и stdio MCP. Итоговый снимок проекта вручную не редактируется. Контекст `fresh`; в разрешённых ID только два ресурса проекта. Общий индекс действительно содержит контрольный документ. Для `audit-b:guide`:

- `pf.resolve`: `denied`, `not_in_project_snapshot`;
- `pf.search` по слову `ForbiddenAuditNeedle`: `total=1`, результат `audit-b:guide`, `scope_key=workplace`.

Утечка подтверждена на уровне результатов поиска: ID, путь, метаданные и факт совпадения содержимого. Возврат полного текста этим API не утверждается. Исправление: обслуживать общий индекс по снимку Workplace, а запрос выполнять с разрешающим снимком проекта. Регрессия должна иметь положительный контроль наличия запрещённого документа в общем индексе.

`git blame` связывает переключение индекса на Workplace с `1aecc18b`; ошибка уже есть в HEAD и не является следствием незакоммиченной правки документации.

### F02 — потеря файла, которым Core прежде не владел

План вычисляет `added` сравнением манифестов, но не проверяет наличие чужого файла по новому пути. Резервируются только `removed ∪ changed`; затем `added ∪ changed` безусловно записываются.

В тесте установлен старый Core, рядом создан `user-note.txt` с содержимым `USER OWNED DATA`, которого нет в старом манифесте. Новый архив впервые объявляет этот путь своим. Получено: `plan_status=planned`, `blockers=[]`, `apply_status=applied`, файл заменён на `NEW CORE PAYLOAD`, `backed_up={}`. Дополнительное принудительное разрешение перезаписи локальных изменений не передавалось.

Исправление: блокировать столкновение нового owned-пути с существующим посторонним объектом. Если предусматривается отдельная операция принятия такого файла под управление Core, она должна явно учитывать конфликт и сохранять исходное содержимое.

### F03 — старый PASS переживает более поздний FAIL

`_requirement_state()` и `_gate_state()` ищут с конца первое **положительное** доказательство, отбрасывая отрицательные до выбора актуальной записи. Поэтому история `passed → failed` всё равно считается удовлетворяющей требование.

После завершения `prepare` на этапе `build` переданы новый `prepare-ready=failed` и `brief=failed`, а собственные результаты `build` готовы. Движок сохранил отрицательные записи в истории, но вернул `stage_transitioned` и перевёл работу в `verify`.

Исправление: сначала выбирать последнее применимое доказательство по идентичности требования, затем оценивать его статус. Отдельно определить правила для исторических и текущих доказательств, повторного входа в этап и разных допустимых типов `input/artifact`. Нужны отрицательные проверки, а не только наличие старого PASS.

### F04 — SHA-256 записывается, но не защищает сохранённое доказательство

Путь и SHA-256 проверяются только при поступлении нового evidence. Сохранённые доказательства при расчёте готовности не перечитываются и не проверяются на существование или изменение содержимого.

В тесте передан существующий `brief.md`, но gate ещё не передан: результат `incomplete`. Затем файл удалён, отдельно передан положительный gate. Результат — `stage_transitioned`; следующий этап видит `brief` как `satisfied=true` с хешем уже отсутствующего файла.

Исправление: при принятии перехода проверять актуальность всех файловых доказательств, от которых он зависит. Отсутствие или изменение файла должно давать явную неполноту/устаревание. Альтернатива — хранить и использовать неизменяемую копию доказательства; текущая запись одного хеша этого не обеспечивает.

### F05 — атомарность отдельных файлов не обеспечивает атомарность завершения Work

`_complete_locked()` сначала сохраняет assignment со статусом `done`, затем run со статусом `completed`, после чего пишет итоговые документы. Между этими записями нет восстанавливаемой транзакции.

В реальном временном PF-проекте внедрён единственный `OSError` при записи финального `run.yaml`, после успешной записи assignment. На диске остаются `assignment=done`, `run=in_progress`. Повтор штатного `transition()` возвращает `work_is_terminal` из-за статуса assignment и не доводит завершение до согласованного состояния.

Исправление: журнал намерения завершить операцию и идемпотентное восстановление всей группы записей. Проверять сбои после каждого шага, включая запись summary/handoff. Обработка некорректного evidence, уже покрытая отдельным smoke, эту ситуацию не проверяет.

### F06 — блокировка действующего владельца считается протухшей через 300 секунд

`registry_file_lock()` удаляет lock при `mtime > stale_after_seconds`, не проверяя PID, владельца или его активность. Срок по умолчанию — 300 секунд. Длительная операция поэтому допускает второго писателя; первый писатель при выходе также может удалить уже чужую блокировку.

В тесте первая блокировка продолжает удерживаться живым процессом. Её возраст моделируется сдвигом `mtime` на 301 секунду; второй захват с обычным порогом успешно входит в критическую секцию. Это управляемая имитация возраста, а не ожидание пяти минут.

Исправление: согласованный протокол владения, проверка живого владельца и безопасное освобождение только собственной блокировки либо OS-lock. Механизм не должен отбирать живую блокировку только по времени.

### F07 — NameError в проверке сессий Director

`active_organized_project_sessions()` вызывает неопределённую функцию `load_json`. Достаточно одного JSON-файла в `runtime/agent-presence/*/`: падение происходит даже для `status=offline`, до проверки статуса.

Публичный путь вызова — `workplace-mode set --director-enabled false` без `--force`. Воспроизведение непосредственно исполнило функцию на временном каталоге присутствия и получило `NameError: name 'load_json' is not defined`. Происхождение строки: `9a751ae8`.

Исправление: использовать существующий корректный JSON-reader и проверить случаи пустого реестра, offline, активной organized-сессии и повреждённого JSON. Наличие данных не должно превращать проверку в traceback.

### F08 — отсутствует функция вычисления стандартного пути отчёта

Если у worker нет `expected_report_artifact`, `normalized_orchestrator_plan()` вызывает несуществующую `default_expected_report_artifact(worker_id)`. Воспроизведён `NameError` на плане с одним worker и пропущенным необязательным значением. Явно указанный путь маскирует дефект.

Ветка доступна при `orchestrator-plan validate --write-normalized` и формировании отчёта о разрешённой конфигурации. Происхождение строки: `11af7608`.

Исправление: единый существующий механизм стандартного пути отчёта и проверка публичной команды с пропущенным полем. Простая проверка импорта/синтаксиса недостаточна; Pyflakes обнаруживает ошибку без запуска процесса.

### F09 — отсутствующий unchanged-файл не восстанавливается и не блокирует обновление

`build_plan()` замечает отсутствующие owned-файлы и помещает их в `missing_owned`, но это не становится блокером или списком записи. Если хеш пути одинаков в старом и новом манифестах, файл остаётся в `unchanged` и никогда не записывается из архива.

Удалён `dir/c.txt` из старого Core; новый архив содержит тот же файл с прежним хешем. План показывает отсутствие, apply возвращает `applied`, версия становится `2.0.0`, но `dir/c.txt` по-прежнему отсутствует.

Исправление: восстанавливать отсутствующие owned-файлы из проверенного архива либо явно блокировать повреждённую установку. Финальная проверка должна сверять фактическое содержимое с новым манифестом.

### F10 — пересекающиеся источники расходятся в таблицах documents и FTS

Один файл индексируется дважды, например источниками `.` с `**/*.md` и `guide.md`. `INSERT OR REPLACE` заменяет запись `documents` с новым rowid; последующее удаление FTS использует новый ID и оставляет старую строку FTS.

Подтверждено: один физический документ, `total=2`, реальная выдача содержит одну запись; `next_limitstart=1`, хотя следующая страница пуста. Проверка `verify_files=True` при этом возвращает `fresh`.

Исправление: устранять дубли логических документов до записи и согласованно удалять старую строку FTS при замене. COUNT и выдача должны опираться на один и тот же набор действующих документов.

### F11 — явно заданный файл обходит исключения индексирования

В `_iter_source_files()` ветка `base.is_file()` проверяет только расширение и размер и сразу возвращает файл. Проверки `source.include/source.exclude` находятся только в ветке обхода каталога.

Источник `path=secret.md`, `include=['*.txt']`, `exclude=['**/*.md']` всё равно индексирует `secret.md`. Поиск уникального `ExcludedNeedle` возвращает результат.

Исправление: единообразно применять include/exclude к файлам и каталогам, включая ресурсы, корнем которых является отдельный файл. Проверка должна подтверждать отсутствие исключённого текста в индексе.

### F12 — квадратичное накопление работы в raw ingress

Для каждого нового события отсутствует `raw_index`, поэтому вызывается `_recover_indexes()`. Она проходит все NDJSON-файлы и декодирует прежние записи. Это происходит под общей блокировкой ingress; для событий без стабильного native ID одна из проверяемых записей отсутствует постоянно.

Трассировка реального кода: **20 новых событий → 20 recovery-проходов → 190 повторных декодирований исторических записей**. Это подтверждает сумму `0+1+…+19` и рост порядка O(N²) при накоплении N новых событий; сетевое время или benchmark большой установки здесь не измерялись.

Исправление: различать обычный cache miss для нового события и необходимость восстановления после сбоя; хранить согласованный checkpoint/индекс либо восстанавливать только необработанный хвост. Сохранить дедупликацию и устойчивость к сбою между append и index.

## Почему существующие проверки этого не обнаружили

`smoke_garage_cross_project_security.py` создаёт ресурсы только в проектных снимках, но не регистрирует их в общем Workplace-каталоге. Проверка `total == 0` проходит без подтверждения, что запрещённый документ вообще находится в индексе. Собственный тест с непустым общим индексом выявил F01.

`smoke_project_resource_narrowing_search.py` проверяет нижний уровень поиска с правильным snapshot; ошибка F01 находится выше, при передаче snapshot в сервисе Garage.

Smoke обновления Core не проверяет столкновение added-пути с пользовательским файлом и отсутствующий unchanged-файл. Smoke переходов не покрывают поздний FAIL, удаление сохранённого evidence и сбой между финальными записями assignment/run. Проверка raw ingress подтверждает функциональность, но не ограничивает число сканирований истории.

Отдельно заново воспроизведён ранее известный `smoke_garage_no_hooks_sessionless.py:85`: `empty_corpus`, `total=0`. Это проблема устаревшей фикстуры. Она не объясняет и не отменяет самостоятельный дефект F01. Полный выпускной прогон после этого аудита не заявляется.

## Оценка Python-архитектуры

Полезные границы уже есть: `process_execution`, `local_resource_search`, `core_update`, `process_catalog` и отдельное ядро raw ingress. Имеются параметризованный SQL, проверка путей evidence, фиксация определения процесса, журналы и атомарная замена отдельных файлов. Эти механизмы позволяют изолированно воспроизводить проблемы.

Но `tools/processforge.py` всё ещё содержит **27 766 строк и 1 020 функций**, около 77% строк рассмотренного ядра/Runtime. В нём смешаны CLI, правила, I/O, обновления, блокировки, orchestration и выпускные проверки. Выделенные сервисы получают большой объект `core: Any`, что оставляет зависимости неявными; статические ошибки пережили множество smoke-проверок. Есть повторные определения `as_list`/`sha256_file`, тройной одинаковый вызов нормализации reasoning effort и одинаковые ветви поиска. Последние сами по себе не посчитаны отдельными дефектами.

Главный риск — согласованность между слоями: snapshot обслуживает и индекс, и авторизацию; атомарная запись файла принимается за согласованную запись операции; наличие исторического PASS принимается за актуальное доказательство. Массовое разбиение файла без предварительных регрессий эти проблемы не решит.

Предлагаемый порядок работ:

1. F01 и F02: восстановить изоляцию и защиту пользовательских данных, добавить положительные/отрицательные интеграционные проверки.
2. F03–F05: закрепить семантику актуального evidence и восстановления завершения, затем минимально исправить реализацию.
3. F06–F12: блокировки, NameError, целостность обновления/FTS, исключения и стоимость ingress.
4. Ввести обязательную статическую проверку неопределённых имён; исправить устаревшие фикстуры; выполнить полный source release-test. Для выпуска отдельно проверить чистый кандидат, архив и извлечённую копию.
5. После стабилизации постепенно выделять из монолита сервисы с узкими типизированными интерфейсами и явными границами транзакций.

## Границы уверенности

Serena не смогла извлечь символы: `Active languages: []`. IDE MCP открыта на другом проекте. Использованы AST, ограниченные чтения, Pyflakes, Git history и реальные временные сценарии.

Локальный CLI после обновления контекста видит `fresh`; подключённый MCP продолжал возвращать `snapshot_not_fresh`. Аудит оформлен и проведён через CLI проверяемых исходников. Несоответствие подключённого сервиса текущим исходникам записано как ограничение окружения, не включено в 12 подтверждённых дефектов. Runtime/host hooks/службы не перезапускались.

Попытка динамически проверить выход через файловую symlink остановилась на Windows `WinError 1314` при её создании. Ветвь обхода файлов требует отдельной проверки на системе с symlink; это **не подтверждённая находка**, в итоговый счёт не включена.
