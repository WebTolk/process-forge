# T04 adapter domain and rules

An adapter registration is trusted executable application configuration, fixed before ingest; an event is untrusted data. A registry maps exact (provider, adapter) identities to already-instantiated policy objects and rejects duplicates. No event-driven imports, command paths, registry mutation or trust flags. The default registry contains existing native Codex hooks, PF Codex worker capture and a neutral normalized Runtime compatibility adapter. Adding another provider uses a separately constructed registry supplied by trusted caller code; no Host/kernel edit.

Raw acceptance means private durable receipt only, not authorization for project effects. Host persists raw first, then checks registration and provider admission. Unknown/spoofed input remains private raw evidence with explicit adapter_untrusted/provenance_rejected diagnostics and no derived effect; raw identity conflicts retain existing kernel quarantine semantics. Registry/provider exceptions fail closed.

Adapter policy validates provider-specific event identities and content mapping and supplies neutral facts: ledger or worker authorization mode, expected worker identity/hash/path, message provenance predicate, optional final-message duplicate rule and a narrowly authenticated owned-report exception to the automatic path-text filter. Host retains current project/session binding, worker task/attempt/output-file authorization, raw/hash comparison, safe content, durable writes, deterministic IDs, deduplication and deferred capture. Trust granted to adapter code does not make event-supplied flags authoritative.

Every supplied derived event/session/project and conversation source identity must match the envelope. Codex policy validates raw hook event/session/cwd mapping and expected derived lifecycle semantics; unknown hook names may remain raw-only. Worker policy validates native input/output identity and payload provenance; neutral Host enforces current task/attempt and declared report bytes. Missing/invalid input denies before project effect. Legacy normalized Runtime events retain their existing authenticated transport contract and cannot introduce conversation content.

Generic initialization and status remain available with no Codex installation or missing optional integration module. The legacy codex_integration field and explicit install_codex_hooks action remain compatibility adapters, not generic readiness requirements. No automatic installation.

Compatibility rule for the discovered legacy batch gap: a governed run with process_execution keeps one exact process identity. A legacy task-batch run uses exact persisted task membership and that task's explicit process; only new context creation pins it. Corrupt existing run pins never fall through. This does not permit a missing/nonmember Run or regenerate an old capsule.
