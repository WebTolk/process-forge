**Исследование установки, обновления и совместимого пошагового мастера ProcessForge**

Дата: 18 октября 2026 года. Роль: `installation-worker`. Статус: исследование завершено, продуктовые изменения не выполнялись.

Для пошаговой настройки уже существует подходящая основа: `answers.yaml`, proposal, review, файловые команды и отдельные парсеры с внедряемыми обработчиками. Рекомендуется развить эту основу общим сервисом подготовки и проверки плана. Чатовый сценарий останется основным, терминальный интерфейс сможет использовать тот же сервис как дополнительный адаптер.

Установка дистрибутива, создание workplace, onboarding проекта, замена Core и перенос истории — разные операции. Мастер должен показывать их отдельно и подтверждать конкретный набор действий. Текущий код не даёт общей гарантии автоматического отката или миграции всех данных.

Использованы актуальные исходники и локальная документация: `docs/requirements.md`, руководства в `docs/getting-started/`, документы обновления и SQLite-журналов в `docs/concepts/`, `docs/ru/releases/1.2.0-migration.md`, процесс `processes/core/guided-workplace-setup.yaml`, его prompt и переданные inline-знания Python. Для анализа символов использована доступная Serena; `rg` и чтение файлов применялись для документации, парсеров и тестов. Архивные копии Python не использовались.

Сейчас пользователь проходит следующие пути.

| Операция | Реальная точка входа и поведение |
| --- | --- |
| Размещение PF | `docs/getting-started/installation.md`: распаковка релиза или source checkout, отдельное Python-окружение, установка `requirements.txt`. Это предварительные действия оператора; `workplace-init` их не выполняет. |
| Запуск CLI | `bin/pf.py`: `main()` → `exec_processforge()` → `tools/processforge.py` через тот же `sys.executable`. `bin/pf` выбирает `python3`/`python`; `bin/pf.bat` сначала использует `py -3`. Для точного выбора окружения надёжнее явно запускать его Python. |
| Создание workplace | `WorkplaceCommandParser.register_setup()` в `tools/pf_cli/parsers/workplace.py` регистрирует `init-workplace` и `workplace-init`. Оба вызывают `command_init_workplace()`. Без `--apply` печатается план; применение создаёт структуру, файлы, события и запускает `doctor-workplace`. |
| Настройка с агентом | `workplace-setup start/review/apply/status`; обработчики `command_workplace_setup_*()` находятся в `tools/processforge.py`. Сессия хранится в `setup-sessions/<session-id>/` workplace. Вопросы задаёт агент или оператор. |
| Onboarding проекта | `ProjectCommandParser` в `tools/pf_cli/parsers/project.py` направляет `init-project`, `project-init`, `project-onboard` в `command_init_project()`. Он вызывает `project_initialization.initialize_project()` из `src/processforge_core/project/initialization.py`. |
| Автоматический shortcut | `command_first_run()` последовательно вызывает инициализацию workplace и проекта. Обязательны workplace, project root и type. `--profile` отсутствует; после успешного workplace второй этап может завершиться ошибкой без общего отката. |
| Обновление ресурсов | `UpdateCommandParser` в `tools/pf_cli/parsers/update.py`, обработчики `command_update_*()` в `tools/processforge.py`: discovery → candidates → stage → verify → apply с `--confirm`; отдельно доступен rollback содержимого из backup. |
| Обновление Core | `CoreUpdateCommandParser` в `tools/pf_cli/parsers/distribution.py`: `core-update status/plan/apply/repair`. Доменная реализация находится в `src/processforge_core/maintenance/update.py`. |
| Оценка проекта после обновления | `command_project_upgrade_check()` записывает assessment. Это не миграция проекта или истории. `command_self_update_check()` читает локальный update index, а не выполняет сетевую установку новой версии. |
| Перенос истории | Отдельная утилита `tools/migrate-hook-journals.py`: `main()` → `migrate()`. Без `--apply` формирует план; применение импортирует прежние project events и соответствующие проекту raw hooks в SQLite. |

`CliApplication.run()` в `tools/pf_cli/application.py` централизует часть CLI-проверок: запрещает сочетание `--apply` и `--dry-run`, включает предварительный просмотр для обычных команд с отсутствующим `--apply` и сохраняет исключения для `workplace-setup review/status`. При добавлении другого интерфейса эти проверки нельзя терять из-за прямого вызова обработчиков.

Runtime и MCP имеют отдельный операторский путь. В `docs/getting-started/runtime-autostart.md` описаны `runtime autostart install` и `codex-mcp install`, их предварительный просмотр и явное применение. Они не являются обязательной частью файловой установки. Регистрация stdio MCP и Windows autostart Runtime также различаются по владельцу процесса и жизненному циклу.

В существующем guided setup обнаружены следующие ограничения ясности и поведения.

| Наблюдение по коду | Значение для мастера |
| --- | --- |
| `--interactive` зарегистрирован как принимаемый маркер. `command_init_workplace()` не запускает диалог; `command_first_run()` только передаёт значение дальше. Это прямо отражено в руководстве и `docs/known-limitations.md`. | Нельзя включать новые вопросы в старые команды автоматически: это изменит поведение автоматизации. |
| `command_workplace_setup_review()` формирует фиксированный результат `pass_with_conditions`. Загрузка answers использует `AnswersDocumentReader`, но данный путь не выполняет полноценную проверку схемы и всех значений. | Наличие review не доказывает корректность путей, типов, ресурсов и согласованность настроек. |
| `load_guided_workplace_answers()` при несуществующем явно переданном answers-файле может перейти к файлу сессии или defaults. | Опечатка в пути не должна выглядеть в новом мастере как успешное чтение выбранных ответов. |
| `command_workplace_setup_apply()` перечитывает answers и заново создаёт proposal. Прямой обработчик не проверяет наличие одобренного review и совпадение применяемого плана с рассмотренным. | Защита рассмотренного предложения требует отдельной проверки; процессные gates и прямой CLI-вызов имеют разные уровни контроля. |
| Тот же обработчик вызывает `command_init_workplace()` с `force=True`. | Новый мастер не должен незаметно использовать этот путь для повторной настройки существующего workplace. |
| `guided_answers_to_workplace_init_answers()` переносит только часть собранных полей. `build_workplace_files()` создаёт пустые tools/MCP registries; `first_project` остаётся предложением, а не выполненным onboarding. | Итог должен различать созданное, запланированное и требующее последующей регистрации. |
| Профиль поддерживается прямым `workplace-init --profile`, но не переносится текущим guided-конвертером. | Выбор профиля в интерфейсе требует явного расширения модели и преобразования; одного вопроса пользователю недостаточно. |
| Физический target берётся из `--workplace`, а `machine_layout.workplace_path` участвует в формировании конфигурации и подсказок. | До применения необходимо проверять согласованность этих значений. |
| `workplace-setup status` показывает наличие файлов. `session.status` не является надёжным вычисленным состоянием всего применения. | Интерфейс не должен объявлять успех по одному наличию артефактов. |
| `initialize_project()` требует существующий project root для предварительного просмотра, хотя apply способен создать новый каталог. | Для нового проекта нужно честно показывать ограничение preview; полноценный предварительный просмотр такого случая потребует отдельной доработки. |

Текущие преобразования также местами используют `bool(value)`. Новый интерфейс должен принимать настоящие логические значения и явно разбирать пользовательский ввод: строка `"false"` не должна превращаться в `True`. При этом изменение обработки существующих answers-файлов следует оценивать отдельно от добавления мастера.

Предлагаемый сценарий первой настройки состоит из следующих шагов.

1. **Определить операцию.** Предложить создание нового workplace, использование существующего или обновление Core. Кратко объяснить различие между дистрибутивом, workplace и проектом. Текущий каталог не назначать одной из этих ролей автоматически.

2. **Проверить выбранный PF и Python.** Показать версию, интерпретатор и доступность необходимых модулей. Использовать документированный read-only preflight. Отсутствующие зависимости объяснить до создания состояния; установка Python и PyYAML остаётся отдельным явно выбранным действием.

3. **Выбрать пути.** Запросить workplace, документацию, корни ресурсов и необязательный первый проект. Показать нормализованные значения. Проверить разделение заменяемого Core и изменяемых данных, совпадения целей, типы существующих объектов и containment. Не создавать каталог ради проверки права записи без согласования такого действия.

4. **Выбрать основные параметры.** Профиль, режим координации, Director capability и необходимость Director Office. Существующие defaults сохраняются. Платформы предлагаются только при явном выборе и доступных зависимостях. Опциональные настройки истории должны сохранять независимость events/raw hooks и предусмотренное наследование.

5. **Уточнить ресурсы и discovery.** Различать подключение существующего knowledge root, регистрацию инструмента, создание пакета и установку инфраструктуры. Discovery предлагается отдельно и остаётся read-only в разрешённых пределах. В answers сохраняются ссылки на секреты, а приватные машинные пути остаются в локальных материалах.

6. **Проверить ответы и построить конкретный план.** Проверить типы, обязательные значения, пути, доступность выбранных ресурсов и конфликты назначения. Для существующего workplace перейти к отдельному сценарию использования или изменения конфигурации. Создание не должно скрыто перезаписывать его файлы через legacy `force=True`.

7. **Показать итог и получить подтверждение.** Перечислить создаваемые и изменяемые файлы, выполняемые проверки, дополнительные записи сессии и отдельные последующие шаги. Предусмотреть возврат к ответам и отмену. Подтверждение связывается с конкретной версией answers/плана; изменение входов требует повторного рассмотрения. Сохранение черновика также явно обозначается как запись.

8. **Применить и показать фактический результат.** Выполнить подтверждённую операцию, сохранить evidence и результат doctor. Onboarding предложить после готовности workplace и ресурсов, с отдельным просмотром и подтверждением. Ошибка doctor или второго этапа отображается вместе с уже выполненными действиями.

Этот сценарий соответствует существующему `guided-workplace-setup`: intake → dialogue → review → apply. Сам процесс запрещает `create_terminal_only_wizard`; его prompt требует чатового диалога небольшими блоками. Терминальный интерфейс допустим как дополнительный клиент общей логики. Менять закреплённые версии процесса и одобренные артефакты ради нового интерфейса нельзя.

Для обновления нужен отдельный сценарий.

1. **Выбрать точную цель.** Различить Core archive и candidate ресурса. Показать установленную и целевую версии, выбранные roots, источник, changelog и migration guide. Не выбирать автоматически первый candidate.

2. **Проверить состояние и подготовку.** Для Core вызвать `core_status()` и `build_plan()`. План уже содержит добавления, изменения, удаления, локальные модификации, недостающие owned-файлы и blockers. `incomplete_update` направляет к рассмотрению `repair_status()`. При наличии долгоживущих процессов требуется операторское окно обслуживания; мастер не должен сам останавливать или перезапускать их.

3. **Разделить подготовку и просмотр без записей.** У общего updater refresh может обращаться к источникам, stage записывает скачанный артефакт, а verify записывает verification record. Более того, `command_update_apply()` вызывает verify **до** своей ветки `dry_run`. Поэтому `update apply --dry-run --confirm` нельзя использовать как просмотр без записей; описание этого флага в help шире фактической гарантии.

4. **Показать резервирование и границы миграции.** `apply_update()` резервирует заменяемые/удаляемые Core-файлы и сохраняет управляющие manifest/plan и журнал операций в `runtime/core-update/`. Это не полная копия workplace, проектов и SQLite. Пользовательский backup изменяемых данных остаётся отдельной подготовкой; для работающей SQLite-базы документация требует backup API.

5. **Подтвердить и применить.** Сохранить обязательный `confirm`; запросы на замену локально изменённых owned-файлов отделить от обычного подтверждения. `--force-local-modifications` не должен становиться способом обходить остальные blockers. Core применяется первым, затем выполняется только подходящая миграция workplace, объявленная в архиве. При заданном workplace CLI запускает doctor через обновлённый установленный launcher. Ошибка doctor возвращает код 2 после применения Core — интерфейс обязан показать именно это состояние.

6. **Отдельно перенести историю и проверить проекты.** `tools/migrate-hook-journals.py` сначала показывает план, затем требует `--apply`; `--skip-invalid` означает отдельное принятие пропуска повреждённых строк. Утилита сохраняет оригиналы, проверяет источники и целостность, устанавливает барьер `importing` и допускает повтор для продолжения. Обычный доступ к незавершённому импорту блокируется. Старые writers должны оставаться остановленными до завершения cutover. Assessment проекта, перенос entry contract и обновление контекста выполняются своими операциями; capsules сохраняют прежние привязки.

Границы восстановления необходимо показывать буквально:

- `recovery_assessment()` и `repair_status()` классифицируют Core-состояние как `nothing_to_repair`, `safe_to_rollback` или `manual_repair_required`. Они не выполняют автоматический откат или продолжение. После записи нового manifest сбой workplace migration оставляет новый Core и требует ручного восстановления.
- `command_update_rollback()` общего updater восстанавливает файл или дерево из backup. В этом обработчике нет обратного обновления версии в `installed-subjects`. Повторный apply того же candidate пересоздаёт его backup. Это ограниченный механизм восстановления содержимого.
- Core update не импортирует project journals. Workplace events, Ledger, telemetry и transcripts сохраняют собственные форматы и не должны массово подаваться в SQLite-мигратор.
- Обновление файлов не доказывает перезагрузку Runtime или подключённого MCP host.

Для реализации достаточно небольших границ ответственности.

Сначала целесообразно извлечь существующее поведение с доказательством совместимости. Затем в отдельном ограниченном изменении добавить строгую проверку нового wizard input и привязку подтверждения к рассматриваемому плану. Текущие обработчики такой привязки ещё не обеспечивают; её нельзя считать готовой только после переноса функций в класс.

Возможны два варианта реализации:

- **Рекомендуемый:** общий Core-сервис, прежние файловые команды и улучшенный чатовый сценарий. Это соответствует действующему процессу и создаёт основу для будущего веб-клиента.
- **Дополнительный:** терминальный адаптер того же сервиса с явным новым входом. На stdin без TTY он должен предсказуемо завершаться с инструкцией использовать answers/обычный CLI, а не ждать ввода.

Добавлять prompts в текущие `--interactive` или вводить отдельную логику установки для каждого интерфейса не рекомендуется. Внешние зависимости для предложенной основы не нужны: достаточно существующего PyYAML, стандартной библиотеки, `pathlib`, dataclasses и внедрения зависимостей через конструкторы. Контейнер зависимостей, фоновый поток и универсальная plugin-система не требуются.

При реализации затронутся соответствующие EN/RU installation/guided/update guides, prompt, при необходимости schemas/templates. Публичные перемещения и изменения должны учитываться в `checksums/processforge.sha256` и действующем packaging inventory. Общие platform/toolchain правила копировать в проектные файлы не требуется.
