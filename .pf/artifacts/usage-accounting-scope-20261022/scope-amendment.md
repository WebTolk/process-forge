## Ответственность PF

PF собирает и хранит фактические данные: токены и доступные категории, наблюдаемые интервалы работы агентов, исполнение/попытки/статусы, project/run/assignment, agent/provider/model, происхождение и полноту измерений. На этих данных строятся статистические сводки по задаче, проекту и разрешённым проектам workplace.

**Из данной функции полностью исключены** тарифы, цены моделей, денежные оценки/расчёты, биллинг, платежи, денежные потоки, распределение подписок, валюты и финансовые отчёты. Поэтому не реализуются RateCard, Valuation, valuation.py, rate/valuation tables, reported_cost/estimated_cost DTO и экспорт финансовых данных. Сценарии A15–A17 прежнего плана отменены; денежные части смешанных требований/примеров тоже не применяются. Нефинансовые правила источников, дедупликации, времени, привязки, полноты и приватности сохраняются.

Если отдельной внешней системе нужны денежные вычисления, она может использовать экспортируемые PF счётчики. Такая система не становится частью этой задачи или домена PF. Существующие приватные сырые журналы провайдера сохраняются по своему контракту, но наличие сторонних полей в raw payload не создаёт финансовый API PF.

## Хранение: рекомендуемый вариант

**Одна общая локальная SQLite-база подсистемы учёта на workplace PF, с обязательным `project_id` у атрибутированных фактов.** Это конкретная рекомендация для обсуждения; вопрос пользователя о вариантах не объявляется разрешением на создание БД. Это не общая БД для всего состояния PF и не обязательный удалённый сервер.

| Вариант | Преимущество | Цена/ограничение |
| --- | --- | --- |
| Отдельная база каждого проекта | Историю легко переносить/архивировать с проектом; данные физически разделены | Для общей статистики нужен обход всех доступных баз; недоступные/перенесённые проекты дают неполную сводку; миграции и резервирование множатся |
| Одна база учёта workplace + project_id — рекомендуется | Единые запросы по всем проектам, один формат/миграция/backup, простой доступ CLI/TUI/plugin и будущий export | История не переезжает автоматически вместе с checkout; нужен явный проектный export/import при переносе в другое workplace |
| Проектные базы + общая БД отчётов | Проектная автономность и быстрые общие сводки | Второй слой хранения, checkpoints/rebuild/freshness, разрешение дублей и дополнительных ошибок; оправдан при доказанной необходимости автономных проектных БД |

В рекомендуемом варианте первичные журналы попыток и артефакты продолжают жить в существующих проектных местах. Нормализованные статистические факты находятся в общей БД. Файл отчёта задачи — производный снимок с as_of/полнотой, а актуальная сводка — запрос к общей БД. Отдельная центральная база только для отчётов не нужна. Проектные raw logs и отчётные snapshots не являются второй авторитетной копией нормализованного учёта.

Минимальные данные: usage facts/revisions, activity facts/revisions; небольшие служебные project mappings и source cursors/capabilities. Ключи: `project_id`, существующие `run_id`/`assignment_id`/`attempt` при доказанной привязке, `agent_instance_id`, `source_id`, устойчивый `record_id`, `origin_id`, timestamps. Project display name/path не заменяет устойчивый id. Между workplace одинаковые текстовые project ids автоматически не объединяются; при будущей remote синхронизации используется явное mapping и исходный origin факта.

Общий файл не означает общедоступные данные: все запросы используют разрешённый project scope. Резервирование — общей БД; выборочный перенос проекта — явный экспорт его фактов с сохранением record/origin identity. Возможность export/import закладывается идентичностью и фильтрацией; отдельный механизм переноса не нужен до соответствующей задачи. Недоступность общей БД означает unavailable/backlog для статистики, а file-only процесс PF продолжает работать. Автоматический переход к второй проектной базе-источнику истины не вводится.

## Обновлённая реализация и развитие

1. Проверить реальные источники Codex/Kimi и их версии: usage, время, точная привязка, повторная доставка, compaction/retries/child agents и missing данные.
2. Сделать небольшой нейтральный модуль учёта: UsageRecord/ActivityInterval, нормализация, dedup/revisions, локальное хранилище и статистические запросы. Структура model/rules/service/storage — ориентир, без финансового слоя.
3. Добавить CLI/JSON и отчёт задачи, сверить task/project totals и полноту. Сохраняются нефинансовые acceptance scenarios прежнего плана; добавить проверку, что публичный usage DTO содержит только заявленные данные учёта.
4. Позднее TUI/Control Center и плагин читают одни прикладные запросы. Опциональный REST передаёт нормализованные факты и уточнения с устойчивыми id; remote может хранить свою копию для нескольких workplace. Эта будущая копия не требует проектных баз на локальном устройстве.

Никаких продуктовых файлов, новых БД, сервисов, hooks или инфраструктуры этот документационный цикл не меняет. Исходная карточка остаётся open/planning_only, прежний terminal Work не переиспользуется.
