# Сервисы PF получают свойства и версию из общего ООП-ядра

Task: `pf-services-core-properties-20261021`.
Run: `pf-core-properties-backlog-20261021`.
Статус: будущая задача; сохраняются требования, реализация не начата.

## Требование пользователя

ООП-ядро PF должно быть доступно всем сервисам PF, включая монитор и App
Server. Сервис получает свойства ядра через общий объектный контракт.
Версия ядра не должна дублироваться числовым литералом в адаптере, фасаде,
мониторе или сервере. Исправление не сводится к замене `1.2.0` на новый номер.

## Подтверждённый дефект

После штатной установки dev `1.3.0-alpha1` VERSION и installed manifest
показывают эту версию; все 1460 управляемых файлов совпадают с манифестом.
Однако строка CLI в установленном мониторе показывает `1.2.0`.

Цепочка: `command_monitor` вызывает
`collect_snapshot(workplace, core.PROCESSFORGE_VERSION)`, а фасад
`tools/processforge.py` задаёт `PROCESSFORGE_VERSION = "1.2.0"`.
Таким образом, монитор обращается к атрибуту Core-фасада, но его значение
является дублирующей константой. Само наличие доступа к фасаду не доказывает
использование канонической объектной модели ядра.

Уже существующая команда `version` читает VERSION с fallback на эту константу;
это ещё один потребитель, который нужно согласовать через общий контракт.
`RUNTIME_VERSION = "1.0.0-poc"` отображается отдельно как instance label;
его смысл и связь с версией Runtime/протокола следует явно определить.
Сохранённые фрагменты и хеши: [evidence.md](evidence.md), evidence.json.

## Предмет будущей реализации

1. Установить реальную цепочку загрузки Core и его свойств в CLI, Runtime/
   App Server, мониторе, MCP и остальных собственных сервисах PF. Проверить
   существующие классы, фабрики и composition roots; не считать фасад с
   глобальными константами готовой общей объектной моделью.
2. Определить один канонический контракт свойств/идентичности ядра и подключить
   к нему потребителей штатной композицией/внедрением зависимостей. Тонкие
   адаптеры отображают полученные данные. Не создавать отдельный парсер
   VERSION или собственный набор правил в каждом сервисе.
3. Источник свойств принадлежит фактически выбранной поставке Core.
   Проверить clean source checkout, установленный Core, dev-архив и перенос
   установки. Текущий каталог и случайная соседняя установка не выбирают
   версию вместо принадлежащего процессу ядра.
4. Отдельно описать свойства, которые действительно нужны сервисам:
   release/version, build/source identity и происхождение загрузки; проверить,
   какие другие уже существующие свойства Core сейчас дублируются. Не
   расширять это в произвольный новый сервисный фреймворк или полный рефактор.
5. Различать установленную на диске и фактически загруженную сборки.
   Идентичность уже работающего процесса не меняется от чтения нового файла
   после update. Долгоживущий Runtime/MCP сообщает свою загруженную сборку;
   сравнение с установленной даёт понятную необходимость reload/reconnect.
6. Разделить версию release/Core, компонентную версию Runtime и версии
   протокола/схемы/spec. Не переименовывать всё в номер текущего релиза и не
   менять исторические процессы, capsules, dependency versions или immutable
   evidence ради совпадения цифр.
7. Убрать дублирующие release-константы и ложные fallback-значения.
   Отсутствующие/недоступные метаданные дают честное unknown с причиной;
   повреждение источника не маскируется заранее зашитой старой версией.
8. Сохранить работу console/file-only сценариев: получение свойств ядра не
   должно автоматически запускать Runtime/MCP, выполнять сетевые запросы,
   обновлять контекст или сканировать историю/реестр знаний.

## Критерии приёмки

- На одинаковой поставке CLI, монитор, App Server/Runtime и MCP используют
  один объектный контракт Core и согласованно показывают его идентичность.
  Проверяются фактические обращения, не только совпадение строк.
- Для source, установленного Core и собранного dev-архива наблюдаемые свойства
  соответствуют их реальному источнику. Включить prerelease/dev и неизвестные
  или повреждённые метаданные; не использовать только один вручную выбранный
  номер версии как тестовые данные.
- После update без restart старый процесс продолжает сообщать старую загруженную
  сборку, новая CLI видит свою новую поставку; после реального restart/reconnect
  загруженная идентичность меняется. Новый независимый stdio-процесс не заменяет
  приёмку реально подключённого MCP-хоста.
- Сохраняются опубликованные CLI/MCP параметры, ошибки, payloads и режимы.
  Необходимое изменение схемы сначала проектируется и версионируется.
  Диагностика не раскрывает секреты и приватные пути в публичном выводе.
- Регрессия исходного случая: архив и manifest `1.3.0-alpha1` не сочетаются
  с выданной за актуальную версию Core константой `1.2.0` в новом процессе.
  Runtime protocol/spec versions не подменяются release version.
- В конце будущей реализации — полные применимые PF-тесты и Python QA
  зарегистрированными инструментами PF и с локальными Python знаниями;
  отдельный commit и push обоих dev remote, GitVerse через токен, readback SHA.

## Связанные работы и граница

`pf-upgrade-integrated-verification-20261019` остаётся общей задачей сценария
обновления и проверки загруженных версий. Новая карточка фиксирует конкретный
дефект источника свойств и архитектурный контракт их потребления сервисами;
результат должен стать входом интегрированной проверки обновления.

Завершённая `pf-cli-mcp-context-consistency-20261019` касается freshness/
readiness и происхождения контекста; её статус не меняется и её выполнение
не подменяет исправление release identity. Последнее операторское обновление
`pf-device-dev-update-20261021` уже завершено; повторять apply или перезапуск
ради регистрации этой карточки не нужно.

Карточка `planning_only`, `writer=false`, без прав записи продукта и без
запуска Work/воркеров. Исполнение требует отдельного актуального Work
с конкретными границами после разрешения пользователя.
