# Первый вход Kimi в PF: проверка evolve и сравнение источников знаний

Основание: пользователь уточнил, что Kimi впервые работал с PF, с чистой установкой и без локальной памяти агента. Это делает отчёт ценным наблюдением первого входа, но не превращает каждое его объяснение причины в подтверждённый дефект PF.

## Что подтверждается или заслуживает сохранения

1. **Не хватает готового примера scope/evidence рядом с ошибкой.** В этом запуске Codex также получил `execution_mode_invalid`: я первоначально использовал неподдерживаемое имя режима, а разрешённые значения пришлось смотреть в source. MCP signature допускает string/object, но не перечисляет enum режима. Для gate evidence пришлось проверить исторический assignment: различие `kind: artifact` / `kind: gate` и `status: approved` не раскрывается в кратком work.state. Память сокращает поиск знакомого места, но не устраняет пробел интерфейса.
2. **Девять стадий и множество отдельных артефактов для анализа создают заметную нагрузку.** Текущая review Work также проходит полный software-feature-development@1.2.1, хотя продукт не меняется. Предложение отдельного ограниченного review/assurance process заслуживает обсуждения. Самовольно пропускать стадии или расширять scope нельзя. Оценка Kimi «80%» субъективна: временного исследования в отчёте нет.
3. **Перегруженный outbox неудобно исследовать через листинг.** Bounded summary/count/sample полезнее полного вывода. Сам факт накопления и отсутствие удобного пользовательского пути — полезная обратная связь. Автоматическую очистку по возрасту нельзя считать уже разрешённым решением.
4. **Связь host hook -> raw ingress -> Ledger/events/chat и process event -> outbox стоит показывать явно.** Kimi смешал эти маршруты в доказательствах. Это и ошибка его проверки, и сигнал, что новичку трудно увидеть разные уровни.

## Где диагноз или рекомендация нуждаются в поправке

| Утверждение Kimi | Проверка текущего состояния | Оценка |
| --- | --- | --- |
| PF надо добавить регистрацию по первому host hook | Source Host._ensure_hook_session уже делает это для trusted adapters; fixture SessionStart регистрируется без заранее bound MCP session | Возможность существует; для его результата подтверждены дефекты интеграции/installed registry |
| --evidence-file не поддерживает массив | CLI help прямо обещает object or array; WorkTransitionCommand.execute расширяет список; изолированный тест передал оба объекта без изменения реальной Work | Рекомендация добавить array support избыточна; пример/подсказка остаются полезными |
| Шаблонов нет | Pinned process объявляет assignment-template, artifact-template, review-template, handoff-template | Шаблоны есть; готовая выдача нужного шаблона и artifact/evidence scaffold — другой вопрос. Отсутствие понятного пути к ним нельзя отрицать наличием имён |
| Нет dry-run transition | В текущем CLI work-transition действительно нет --dry-run; pf.work.state даёт текущие incomplete requirements | Разумное предложение; work.state полезен как preflight, но не эквивалентен проверке предлагаемого evidence |
| Glob ничего не находит / ls убит лимитом вывода — сломан PF | Это наблюдение об инструменте/host и размере вывода; воспроизведения дефекта PF glob в отчёте нет | Сохранить пользовательскую боль, не объявлять подтверждённой поломкой PF |
| Windows quoting / ls в cmd — проблема PF | Ограничения выбранной оболочки и неверный формат команд не доказывают дефект PF API | Полезны shell-aware примеры и structured MCP arguments; не все затруднения требуют новой функции PF |
| Свежий snapshot не дал закрыть orchestration из-за stale derived reports/capsule | В этом ревью свежий тот же snapshot и session absent не мешают переходам с корректным gate/handoff evidence | Его причинное объяснение не подтверждено; конкретный work.state указывает gate_evidence_missing/handoff_note_required |
| Process outbox доказал исправность Kimi hooks | Найдены PF process.stage/supervisor события, а Kimi acceptance не выполнен | Разные доказательства; общий PASS чрезмерен |

Память их не заменяет |
| **Локальная память Codex на устройстве** | Быстрый поиск прошлых PF заметок; по Kimi релевантных прежних результатов не найдено. Общие подсказки о старте с .pf, сохранении dirty state и различии source/installed/connected evidence помогли выбрать порядок проверок | Это историческая навигация, а не доступ, разрешение или подтверждение текущей исправности. Важные факты заново проверены в текущем запуске |
| **Общие знания модели** | Как читать Python/TOML/JSON и Git diff; почему byte hash меняется при CRLF/LF; как различать raw receipt и occurrence identity; как организовать изолированный fixture и оценить достаточность тестов | Это объяснения и гипотезы. Контракт Kimi и поведение PF я подтвердил установленным исходником и исполнением probes |
| **Действующие инструкции пользователя/host** | Запрет product fixes в ревью, startup contract, предпочтение Serena, локальная документация и ограничения инструментов | Это отдельный источник правил; нельзя приписывать их памяти или делать вид, что PF автоматически выдал все эти знания |

Сравнение показывает существенный риск оценки зрелости PF по опытному агенту: знакомый агент заранее знает, где искать capsule, каким должен быть gate evidence и что исходники не равны установленному сервису. Он способен восстановить недостающие связи из памяти и опыта, а новичок видит тупик или начинает угадывать. В этом запуске часть такой работы тоже была ручной: поиск enum режима, образца evidence, реального host payload и причины installed/source расхождения.

Успешное выполнение опытным агентом поэтому ещё не доказывает самодостаточность первого входа. Воспроизводимый критерий улучшения: агент без долговременной памяти по стартовому контракту и self-description PF получает корректный scope, нужные материалы и следующий допустимый шаг, а ошибки дают минимальный рабочий пример. Это предложение для последующего проектирования, не реализованная новая функция.

## Как использовать отчёт Kimi дальше

Сохранить исходное наблюдение неизменным, рядом вести проверенный статус причин и рекомендаций. Приоритетные темы — self-description scope/evidence, честная граница host/source/installed acceptance, понятный путь к текущим templates и ограниченный процесс для анализа. Не регистрировать автоматически дублирующие задачи на уже существующие array support и session enrollment. В этом ревью backlog и память агента не изменялись.
