## Статус и границы

Это будущая очередь. Run `pf-upgrade-maintenance-backlog-20261019` остаётся `draft`; все пять карточек — `open`, режим `planning_only`, `writer=false`, без областей записи и капсул выполнения. Реализация не начата, срок и целевой релиз не назначены. Нумерация задаёт порядок карточек внутри этого Run и не меняет приоритет существующей ближайшей задачи окна PF App Server.

Карточки фиксируют будущие результаты и критерии приёмки. Они не предоставляют прав на изменение продукта, обновление устройства, запуск/перезапуск Runtime, MCP, Agent Ledger, PF App Server или monitor. Перед будущей работой нужны свежий PF context, проверка актуальности постановки, исследование/проектирование и новая явно ограниченная Work; разрешения регистрации не переносятся на реализацию. Текущий рефакторинг и завершённые OOP-задачи не переоткрываются.

## Что установлено отчётом

- Обновление завершено с условиями: установленное ядро и Runtime проверены на 1.2.0; подключённый MCP требовал перезапуска хоста. Новый изолированный MCP проверялся отдельно.
- Состояния проектных контекстов `stale`/`broken` существовали до обновления; отчёт не связывает их появление с обновлением.
- Монитор в конце отчёта визуально принят оператором. Однократный вывод при первом запуске связан с `TERM=dumb`; `partial` статистики Work связан с некорректной записью Run.
- Это свидетельства соседнего устройства на момент отчёта; текущий запуск регистрации не повторяет обновление или эксплуатационные проверки на этом устройстве.

## 1. Совместимость обновлений

Определить поддерживаемые исходные версии и проверять полный переход на целевую версию, включая команды руководства в исходном CLI.

Основание: При обновлении 1.1.0 → 1.2.0 установленный CLI 1.1.0 не поддерживал --workplace-root; оператор использовал обновлятор из проверенной распаковки 1.2.0.

Полные критерии приёмки и границы находятся в [карточке задачи](../../assignments/pf-upgrade-compatibility-matrix-20261019.yaml).

Результат задаёт входные условия для pf-upgrade-integrated-verification-20261019. Обновления живых устройств в текущую регистрацию не входят.

## 2. Полный цикл обновления

Спроектировать и реализовать единый управляемый сценарий обновления с достоверным итогом по установленному ядру, реестрам, Runtime и подключённому MCP.

Основание: В отчёте обновление ядра, синхронизация трёх реестров и проверка загруженных компонентов выполнялись отдельными действиями; MCP текущего хоста оставался запущенным до обновления.

Полные критерии приёмки и границы находятся в [карточке задачи](../../assignments/pf-upgrade-integrated-verification-20261019.yaml).

При будущем планировании использовать результаты pf-upgrade-compatibility-matrix-20261019, pf-maintenance-sqlite-journals-20261019 и pf-health-readiness-statistics-20261019. Регистрация не разрешает обновлять устройство или перезапускать инфраструктуру.

## 3. Сохранность данных

Включить согласованное резервирование SQLite, предварительную проверку журналов и сохранение повреждённых строк в штатный сценарий обслуживания.

Основание: SQLite-индекс резервировался через backup API. В старом журнале найдена строка с начальными NUL; её байты сохранены отдельно, корректные записи импортированы после отдельной проверки с --skip-invalid.

Полные критерии приёмки и границы находятся в [карточке задачи](../../assignments/pf-maintenance-sqlite-journals-20261019.yaml).

Результат используется pf-upgrade-integrated-verification-20261019. Исправление старых данных соседнего устройства сейчас не выполняется.

## 4. Монитор в Windows

Поставлять готовый пользовательский запуск монитора в отдельном интерактивном Windows-терминале и понятно объяснять режим одного снимка.

Основание: Первый запуск монитора унаследовал TERM=dumb и завершился после снимка. Отдельный интерактивный запуск с локально очищенным TERM был визуально принят оператором.

Полные критерии приёмки и границы находятся в [карточке задачи](../../assignments/pf-windows-monitor-launch-20261019.yaml).

Связанная существующая задача: pf-app-server-window-ux-20261019, Run pf-app-server-window-backlog-20261019. Это координационная связь, а не разрешение менять её приоритет или начинать реализацию.

## 5. Понятная диагностика

Независимо показывать здоровье службы, готовность каждого проектного контекста и полноту доступной статистики.

Основание: При ready у Runtime проектные контексты оставались stale/broken ещё с состояния до обновления; агрегат Work был partial с нижней границей из-за некорректной записи Run.

Полные критерии приёмки и границы находятся в [карточке задачи](../../assignments/pf-health-readiness-statistics-20261019.yaml).

Результат используется pf-upgrade-integrated-verification-20261019 и учитывается в pf-app-server-window-ux-20261019 без объединения их областей реализации.

## Связи и будущая последовательность

Сначала определить политику поддержки и матрицу переходов, требования к сохранности данных и семантику диагностики. Единый сценарий обновления должен использовать эти результаты; итоговые проверки матрицы выполняются на готовом сценарии. Запуск монитора согласуется с существующей [задачей окна PF App Server](../../assignments/pf-app-server-window-ux-20261019.yaml), сохраняя выбор между информативной консолью и системным треем и отдельный пользовательский запуск монитора.

Это связи для будущего планирования, а не запуск зависимых задач. В этой регистрации зависимости lifecycle не редактируются вручную и уже существующая карточка не меняется.
