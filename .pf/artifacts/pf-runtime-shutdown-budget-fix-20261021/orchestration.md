# Уточнение границы исправления остановки Runtime

Поручение: решить текущую небольшую проблему обновления и блокировки перезапуска
из-за лимитов. Общий слой БД и перенос журналов остаются в отдельной будущей
задаче `pf-database-layer-and-journals-20261021`.

Контекст PF fresh/continue; отдельная Work создана с узкой областью записи:
модуль runtime.metrics, существующая smoke-проверка и их строки inventory.
Assignment и неизменяемая capsule прочитаны; конфликтов писателей нет.
Работа выполняется одним исполнителем. Продуктовые файлы не изменялись.

Штатная проверка остановки использует Budget статистики: 512 записей каталогов,
128 файлов, 4 MiB и 0,5 секунды. Превышение бюджета оставляет running неизвестным,
и HTTP shutdown закономерно возвращает 409. Этот результат не равен занятости.

Повторное полное наблюдение установленным нативным observer в 06:00 UTC:
два проекта, 333 чтения файлов (включая cache), 4596 записей каталогов,
coverage=complete, running=0, ошибок нет, длительность 0,8042 секунды.
Настройки работающего Runtime не менялись. Свежая статистика leases:
coverage=complete, held=0. Это наблюдение не фиксирует будущие старты или HTTP
запросы и не подменяет решение оператора об обходе busy guard.

Перед зависимыми действиями пользователю предложен выбор:

1. Разово завершить уже подготовленное обновление каноническим `server stop
   --force` после повторной проверки окна обслуживания, без изменения кода.
2. Выполнить узкое исправление кода guard, его полный цикл PF/Python assurance,
   отдельный коммит/push в оба remote, затем обновить устройство.

Ответ ожидается. Force, apply и перезапуск не выполнялись. Операторское обновление
сохраняет исходные selectors; эта Work не расширяет его capsule и не заменяет
будущую задачу БД. После выбора зафиксировать окончательную границу и продолжить
соответствующую Work. При выборе разового обновления продуктовая реализация
данного исправления не требуется.

Источники: текущий PF context/Work/capsule, runtime.metrics, HTTP shutdown,
существующая smoke_runtime_metrics, концепция runtime-monitor. Локальные Python
знания разрешены через pf.work.resolve: pathlib (ошибки ФС, resolve и symlinks),
Python practices pep20 (явность и сохранение ошибок). Подробные приватные receipts
обновления сохранены в его разрешённой временной области.

## Выбранная граница

Пользователь ответил «Да, разрешаю» на прямой запрос разовой канонической
остановки с `--force`, установки подготовленного dev и запуска монитора.
Этот вариант выполнен в исходной операторской Work. Продуктовая реализация
данного отдельного исправления не запрашивается; Work закрывается штатной
отменой с сохранением capsule и истории. Guard и его бюджеты не менялись.
