# R02: фундамент хранения и совместимый переход

Дата: 2026-10-24. Статус: orchestration / investigation pending.

Оператор поручил начать выбранный блок R02 и необходимую ему архитектурную
часть R12 в режиме 1-1-4. Основной агент занимается только оркестрацией.
Реализацию, технический анализ и проверки выполняют четыре нативных shell-воркера
PF; независимый ревьювер начинает после завершения реализации.
Драйвер всех исполнителей: codex-exec, модель gpt-6.1-sol, reasoning high.
Текущая нативная схема PF принимает уровни до high включительно.

## Граница результата

Сначала зафиксировать владение данными, собственный SQL API/драйверы PF,
версии схем и протокол перехода; затем реализовать согласованный первый срез
оперативного состояния/истории на SQLite с существующими потребителями.
История из 400 000 завершённых запусков не должна требовать полного чтения
для определения текущей активности/защиты остановки. Публичные CLI/MCP,
параметры, payloads, ошибки, файловый режим, процессы и привычная работа
существующих пользователей сохраняются. Поддерживаемый переход выполняется
готовым кодом без обязательных LLM-вызовов, с проверкой, восстановлением и
правдивым результатом. Конкретную границу первого переноса определяют исполнители
по текущим владельцам и согласованному архитектурному контракту.

## Принятые оператором решения

- Одна основная SQL-база на рабочее место и одна внутри .pf каждого проекта;
  таблицы предметных областей в общей базе соответствующего уровня.
- Поисковый индекс хранится в отдельной базе как производные данные.
- Каноническое состояние проектной задачи принадлежит проекту; рабочее место
  получает сводку и ссылки. Один владелец записи каждого факта, без двух
  независимых истин в Markdown и SQL.
- Собственный API и классы драйверов PF доступны Core и процессам; SQLite
  является первым backend, сменяемость предусмотрена контрактом. Новые
  серверные драйверы, универсальная ORM и полный SQL builder не входят в первый срез.
- Версионируемые пакеты знаний и внешний рабочий каталог сохраняют свои роли;
  будущий RAG не заменяет SQL-учёт. Общий планировщик агентов не включён.
- Простота Garage и контроль версий/изменений под капотом обязательны.
- Последнее поручение оператора разрешает разработку; исторические записи
  implementation_authorized=false описывают предыдущий этап регистрации.

## Команда и последовательность

| Участник | Первая волна | Область записи первой волны |
| --- | --- | --- |
| W1 | Владение данными, доменная модель и границы совместимости | ../w1-domain/** |
| W2 | Собственный SQL API, драйверы, PFConfig и минимальная схема | ../w2-driver/** |
| W3 | Текущая активность, история, потребители и 400k acceptance | ../w3-runtime/** |
| W4 | Миграция, существующий updater, откат и сценарии старых пользователей | ../w4-migration/** |
| Reviewer | Независимое ревью реализованных байтов и доказательств | отдельная Work после реализации |

Первая волна пишет только исследования и план реализации; код не меняет.
Оркестратор сводит результаты и фиксирует совместимый контракт и точное
непересекающееся владение файлами. Реализация идёт через отдельные scoped Work,
связанные с принятыми входами. Проверяющие запускаются после реализации.
Каждый завершённый вклад получает отдельный коммит; общий main-worktree index
и чужие изменения сохраняются. Один и тот же SHA доставляется в origin/dev и
gitverse/dev с readback. Подготовку candidate/коммитов выполняет назначенный
нативный исполнитель; основной агент контролирует доказательства.

## Приёмка

Архитектурные источники перечитываются до реализации. Для изменённого кода:
релевантные pytest, Ruff lint и format check, mypy типизированной области
через разрешённые PF Python QA tools. Обязательны реальные команды, версии,
байты/коммит, exit codes, ограничения; регрессии старого контракта и проверка
конкуренции/возобновления миграций. Полный ZIP/установка не заменяют source
доказательства и не запускаются без отдельного поручения.
