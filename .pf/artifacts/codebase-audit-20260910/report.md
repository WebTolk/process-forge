## Как принимались результаты

Исходные shell-запуски завершились ошибкой backend HTTP 403 без отчётов.
При продолжении первичный агент сохранил предыдущие runtime records,
assignments и capsules и намеренно выпустил новые капсулы для повторных запусков
в тех же границах. Драйвер `codex-exec`, модели `gpt-5.6-luna`: ядро medium,
MCP и хуки high. Никаких параллельных изменений продуктовых файлов не разрешено.

Отчёты исполнителей:

- [Ядро](audit-core/report.md).
- [MCP](audit-mcp/report.md).
- [Runtime и хуки](audit-hooks/report.md).

Каждый принятый дефект проверен первичным агентом на настоящем Core/MCP или
collector в одноразовом окружении. Сохранены положительные контроли: lowercase
session работает; обычный отчёт после двух collect даёт одно сообщение.
Проблемы sandbox исполнителей не приняты за ошибки продукта.

Уточнение старой диагностики: дедупликация raw сама по себе не прерывает повторный
capture. Реальная ошибка — повторный отказ `unsafe_automatic_content` после
прохождения авторизации. Гипотеза об устаревшем MCP-процессе тоже недостаточна:
независимые процессы показали разное представление одного classifier path.

Статус принятия конкретных worker reports и результаты PF находятся
в [проверке результатов](recovery-20260911/acceptance.md).
Три audit-воркера завершились с кодом 0, итоговые проверенные редакции отчётов
штатно собраны через PF. Запуск процесса сам по себе не считался успехом.

## Валидация и границы

[Проверка доказательств и сохранности исходников](recovery-20260911/source-preservation-and-evidence.json):
651 файл совпадает с исходными SHA-256. Код продукта не изменялся.
Независимые повторные проверки содержат фактические отрицательные результаты
продукта; PASS проверки доказательств означает воспроизводимость находок.

Полный release-test, сборка, установка, публикация и обновление инфраструктуры
не выполнялись. Нативная проверка Windows symlink-границ остаётся отдельным
пунктом будущих регрессионных тестов. Исторические успешные тесты и релизные
артефакты не выдаются за новый прогон или новую релизную квалификацию.

## Передача на исправление

Для восстановления обычного MCP work.start сначала рекомендуется A09.
Затем приоритетны A01–A03; A02 предшествует изменению политики содержимого A06.
Задачи A02/A07/A09 последовательно владеют `tools/processforge.py`, A03/A04/A10 —
`service.py`, A02/A06 — `host.py`. Нельзя запускать для них параллельных writers.
Каждое исправление требует отдельной управляемой области, отрицательного
контроля до правки, регрессии после неё и независимой приёмки.
