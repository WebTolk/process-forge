# T02 local resource/search source map

Read-only map for primary integration; no architecture verdict.

## Existing index contract

- `src/processforge_core/local_resource_search.py:60-104`: reusable `ResourceSearchIndex(project_root, snapshot, workplace_root)` API (`status`, `refresh`, `maintenance_tick`, `search`). Functional entry points include `authorized_roots`, `build_index`, `index_status`, `search` at `:291-337,626-672,681-760,806-897`. There is no Work-specific search/resolve entry point in this module.
- Index authorization comes from `snapshot.local_search_resources`; pre-selection fallback reads `snapshot.resolved.knowledge_resources/templates/template_resources`, explicitly not `available_knowledge_resources` (`:163-175`). Grant ids are `id` or `resource_id` (`:270-288`). `_snapshot_checksum` uses `snapshot.checksum`, then `sha256`, then `id` (`:107-116`).
- Resource input shape in current project snapshots (`tools/processforge.py:10514-31`): `{id, resource_id, package_id, kind, title, description, version, fingerprint, path_ref, status, load_policy:"snapshot_authorized", indexing}`. Template records can use `path_ref:{registry:"templates",id:...}` and explicit indexing sources (`:10538-63`).
- Example registry record shape is normalized by `resource_record_from_package` (`tools/processforge.py:8683-8711`): public `id` is `<package>:<resource>`, plus logical `resource_id`, package, kind/title, load/index policy, `path_ref`, versioning, generation, fingerprint and indexing policy. Absolute paths are represented by private path refs instead of copied into the public snapshot. `public_resource_path_ref` yields registry refs, package-relative refs, or private refs (`:9517-28`); resolver rejects traversal and unavailable refs (`:9763-9821`).

## Material policy and generation evidence

- Index policy normalizes `fulltext|metadata|none`; legacy `index_policy` maps to these modes, while an unspecified direct-caller policy has a compatibility fulltext default (`local_resource_search.py:214-267`). Source entries carry `{path,mode,include,exclude,role}`; paths resolve under authorized roots, and fulltext files are text-suffix allowlisted, <=1,000,000 bytes, include/exclude filtered, and symlink/escape checked (`:201-211,352-408`; `TEXT_SUFFIXES`/`MAX_FILE_BYTES` at `:20-27`).
- Metadata mode indexes a generated summary of title, description, resource/package ids, kind, version, root ref and source role/path; it does not read every file under a source tree (`:410-422,443-480`). Fulltext mode adds declared source text and fingerprints file text; each document hash includes resource fingerprint, policy hash and relative path (`:483-501`). `smoke_resource_indexing_policy_acceptance.py:127-144` proves metadata search finds resource metadata but not PHP body text; fulltext markdown markers are searchable.
- `resource_generation` prefers generation/resolved_generation/updated_at/generated_at, then fingerprint value (`tools/processforge.py:9088-95`). `resource_fingerprint` preserves a declared value with `sha256:` prefix or hashes id/kind/version/generation/path_ref; `resolved_resource_instance` carries resolved version/generation, instance id, fingerprint, path ref and reproducibility (`:9098-9155`). `resource_record_from_package` copies these declarations into resource records (`:8708-11`).
- Derived index generation is a 16-hex SHA-256 prefix over snapshot checksum, sorted allowed resource ids and per-document fingerprint map (`local_resource_search.py:605-623,626-635`). `index_status(..., verify_files=True)` recomputes documents and returns `stale/document_fingerprint_changed` on mismatch (`:734-740`); maintenance then refreshes/rebuilds (`:784-803`). Search results expose `index_generation`, snapshot checksum provenance, resource id, relative/path ref, metadata and `match_reason` (`:865-897`), but not a separate Work resource-generation field.

## Shared index, current service and fixtures

- Workplace physical DB is `workplace/runtime/search/local-resource-search.sqlite`; project-local fallback is `.pf/runtime/local-resource-search/search.sqlite` (`:506-511`). Workplace scope is one DB built from registered catalogue and templates (`tools/processforge.py:23686-23734`). Query SQL filters FTS rows by the resource ids from the supplied snapshot (`local_resource_search.py:812-860`); a fresh shared index does not itself prove coverage for a Work grant.
- Current `garage.ResourceSearchService` checks project snapshot freshness, refreshes/verifies the whole Workplace index and searches the current project snapshot (`src/processforge_core/garage.py:106-150`). Its readiness counts whole-index resource/document totals and can report `ready` when the selected-project coverage is zero (`:111-132`). `ResourceResolveService` resolves only a resource selected in current project snapshot, returning `denied/not_in_project_snapshot` otherwise (`:154-186`). MCP currently exposes `pf.search`/`pf.resolve`, not `pf.work.search`/`pf.work.resolve` (`tools/pf_runtime/mcp_server.py:26-27,161-213`).
- `smoke_workplace_search_index.py:93-106` is the smallest shared-DB authorization fixture: same DB, project A searches granted fulltext resource; project B cannot see it but can search its own metadata grant; `pf.resolve` stays project-snapshot scoped. `smoke_resource_indexing_policy_acceptance.py:121-155` covers selected-vs-unselected resources, metadata/fulltext, mutation verification and version switch. `smoke_project_init_local_search_mcp.py` covers source CLI/MCP, safe path refs, session/project mismatch and index maintenance. `smoke_project_resource_narrowing_search.py:84-155` covers version-aware selection/provenance and metadata/fulltext boundaries. `smoke_empty_workplace_has_no_domain_resources.py` and `smoke_garage_real_joomla_search.py` cover empty catalogue and realistic content/source-tree mixes.

These helpers provide bounded integration surfaces: current snapshot loader/root resolver in `garage.py:318-336`, selected/current-resource helper in `garage.py:352-366`, project resource index/search at `local_resource_search.py:806-897`, and reusable temp fixture helpers in `tools/garage_search_smoke_support.py`. A Work grant can therefore be represented to existing search as a narrower resource snapshot, while current authorization, stage subset, selected material version and index coverage need their own Work-aware provenance in the primary service layer.
