# Investigation and impact

Live source baseline: 26fa80a261f62fb0a276dea4bdcb0cb6eb2afa70; src/tools/docs/VERSION clean at entry. Diagnostic report and public-summary.json reread. The prior installed-handler measurements attribute 92.484% of one 17.337 s call to summary and automatic Work state; the two warm calls still parse 2689 documents each. These are prior measurements of the unchanged implementation, not measurements of the proposed design.

Sources inspected with Serena: CurrentWorkService.items/summary; WorkProjectionPolicy; WorkRecordCatalogService.records; WorkSelectionService; ProcessExecutionService catalog, completion-intent and publication composition; CompletionIntentReadService and CompletionIntentValidationService; WorkDocumentPublisher; YamlDocumentReader; YamlParseCache.load. Local document docs/concepts/document-reads.md requires current-content reads and forbids trusting equal size/mtime. Read architectural clarification, concrete Core domain map/refactoring plan, prior compact YAML read architecture and canonical exact Work selection plan. Selected local Python practices read through PF-resolved resource. PF project-artifacts metadata search did not expose individual architecture documents; used bounded filename discovery after resolution, then exact reads. Serena is working.

Findings: summary uses task-active OR run-active while catalog uses task-active AND run-active OR valid completion intent. Summary synthesizes a fallback row for a missing assignment and a row for a run without tasks; catalog skips missing/invalid membership. Ordering and first-assignment handling differ. Catalog preference uses session and (updated_at, created_at, assignment_id), not the first compact summary row. Canonical exact selection already bypasses the catalog and must retain final live reads.

Completion intent is a separate per-run YAML file. Its presence is insufficient: native validation checks fingerprint, owner, final payload, process/snapshot pins and paths. Plan loads full current documents only for runs with such journals, invokes the existing validation owner, and does not retain its authority result across requests.

Write paths include atomic WorkDocumentPublisher temp+replace, native completion replay, legacy atomic and direct task writes, and possible external file edits. Therefore notifications/mtime/TTL alone cannot establish freshness. Cache must remain content-addressed; request-level reuse limited to an explicit read pass, never arbitrary enclosing request lifetime.

Impact: common metadata acquisition and composition only; public CLI/MCP shape, native selection/summary policies, full reads, errors, source validation and file-first use remain contractual. No proposed speedup or memory footprint has been measured. Investigation complete and impact understood for a design-only task.
