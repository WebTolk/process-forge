## 1) Документированная/выпускаемая Python-CLI поверхность (публичный контракт)

Подтверждённый публичный контракт (документация + CLI-сборка):
1. Точка входа: `bin/pf.py` как пользовательский CLI-скрипт.
2. Основной код CLI: `tools/processforge.py` с `argparse`-интерфейсом.
3. Публично описанный релизный поток (`release`):
   - `release-check`
   - `release-test`
   - `release-pack`
   - `release-archive-test`
   - `clean`
   - `examples-check`
4. Для публичного выпуска используется фильтр `--public` у `release-test`, который должен ограничивать набор проверок внутренними «gate» уровня публичности.
5. В `docs/release-checklist.md` зафиксирован обязательный порядок проверки перед релизом и требование проверки диффа на хвостовые символы (`git diff --check`).
6. В `docs/getting-started/agent-prompts.md` и QUICKSTART-материале указана рекомендуемая модель запуска из корня репозитория.

Ключевые публичные точки, которые фактически присутствуют в коде и ожидаемо должны поддерживаться:
- `python bin/pf.py` (дистрибутивный запуск)
- `python tools/processforge.py` (внутренний прямой запуск CLI-ядра)

- кандидат на ограждение при росте surface-совместимости.

## 3) Правила упаковки / включения в архив

Наблюдения по inclusion:
1. `.processforge-releaseignore` явно исключает приватные и временные артефакты:
   - `.pf/runtime/`, `.pf/artifacts/`, `.pf/reviews/`, `.pf/handoffs/`, `.pf/runs/`, `.pf/contexts/`, `.pf/assignments/`, `.pf/dogfooding/`, `.pf/private-notes/`, `.pf/cache/`, `.venv/`, `.idea/`, `dist/`/`build/` артефакты и служебные временные файлы, pycache и др.
2. `dist/` содержит release-меня и манифесты; актуальный архивный выпуск формируется в `processforge-*-current-*.zip` с `.manifest.json`.
3. По состоянию манифестов, в релизный архив включаются:
   - core CLI (`bin/pf.py`, `tools/*.py`),
   - runtime- и документационные папки (`docs/**`, `packages/**`),
   - `checksums/**`,
   - прочие проектные исходники, не попавшие под `releaseignore`.
4. `tools/validate-public-cleanliness.py` дополнительно проверяет нейтральность и безопасность публичной поверхности (в т.ч. запреты на абсолютные пути, marker-пути, платформозависимые артефакты и «русскую» кодировку в местах, где это может ломать cross-платформенную проверку).

## 4) Direct-script import / запуск

Подтверждено поведение запуска:
- `bin/pf.py` делегирует выполнение в `tools.processforge` (основной модуль CLI) и служит стабильной пользовательской точкой входа.
- Непосредственный запуск `python tools/processforge.py` технически возможен и используется в коде/сценариях.
- Это формирует явный Python-публичный контракт в форме «интерпретируемый модульный CLI», но устойчивым API считается лишь то, что закреплено документами и процессной практикой.

## 5) Smoke suites / проверочные наборы

Набор smoke-проверок для релиза:
- В коде релизной команды используется запуск smoke-команд из `tools/` по шаблону `smoke_*.py`.
- Это делает набор расширяемым и зависимым от фактического набора файлов в репозитории.
- На данный момент конкретный перечень smoke-скриптов лучше считать динамическим, а не фиксированным фикс-листом.
- Концептуально это важно для совместимости: новый файл `tools/smoke_*.py` становится неявным участником релизной политики, даже без явного упоминания в документах.
