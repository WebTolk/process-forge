# Python Core Refactor Audit

## Основание и допущения
Сводка построена только по разрешённым источникам: мастер-промпту, Phase A артефактам и точечным чтениям `tools/processforge.py` и `tools/pf_runtime/*`. Ссылки даны в формате `path::symbol` или `path:line`. Там, где отдельный символ в коде не выделен в разрешённом срезе, пометка дана как **не до конца локализовано**.

## Общая картина
- Главный владелец почти всей предметной и orchestration-логики сейчас: `tools/processforge.py`; это подтверждают Phase A инвентари и dependency map.
- Runtime уже вынесен файлово в `tools/pf_runtime/*`, но остаётся зависимым от монолита через shared helpers и динамические/ленивые импорты.
- Наиболее естественные первые границы ядра по текущему коду: `process_catalog`, `process_definition`, `process_runtime`, `worker_runtime`, `common infrastructure`, поверх них thin adapters для CLI/Runtime/MCP.
- Наиболее рискованные зоны для extraction: process-definition contract, handoff/routes, work-state/projectors, worker lifecycle, runtime-driver resolution, release/public-surface gates.

## Поперечные зависимости и наблюдения
- Самые опасные shared seams для первого extraction: `resolve_process_definition`, `validate_process_contract`, `emit_process_event`, `resolve_runtime_driver`, `build_worker_process_command`, `write_agent_run_state`, `work_state_payload`, `ingest_event`.
- Наиболее перегруженные helper-узлы по dependency map: `check`, `rel`, `safe_id`, `as_list`, `now_utc`, `load_yaml_document`, `locate_flow_root`, `dump_yaml`, `require_flow_root`, `emit_process_event`. Их надо выносить тематически, а не в новый `utils/common`.
- Runtime/MCP уже близки к thin adapters, но пока держатся на `tools/processforge.py` через shared helpers и import seam; это подтверждает приоритет extraction Process Definition slice раньше полного runtime split.
- Для зон `Iteration`, `Agent Director`, части `Run` и части `update subsystem` в разрешённом срезе не хватает точной локализации символов; их границы сейчас подтверждены артефактами Phase A, но не исчерпывающе подтверждены точечным кодовым чтением.

## Рекомендуемая первая граница ядра
Первый вертикальный slice естественно проходит по `Process Definition loading -> normalization -> validation -> doctor -> route/handoff contract checks`, с минимальным shared infrastructure слоем (`paths`, `ids`, `yaml_io`, `checks`, `schema_access`). Это даёт:
- один источник process/business logic для CLI сейчас и для Runtime/MCP/Web позже;
- минимальный риск вторжения в live runtime lifecycle;
- прямое соответствие уже принятым контрактам Process/Stage/Gate/Artifact/Evidence/Transition;
- подготовку thin-adapter migration path без немедленного переписывания `tools/pf_runtime/*`.

## Основные риски Phase B/C
- Нельзя переносить process slice, не зафиксировав compatibility policy по `technical_obligations`, `gates`, `handoff_required`, `context-*` и route-related aliases.
- Нельзя трогать `current-work-state` и projectors как первый slice: они зависят от event ingress и runtime host, а не только от process contract.
- Нельзя оставлять две реализации route/handoff или worker lifecycle: временный wrapper допустим, duplicate logic нет.
- Нельзя превращать extracted shared code в бесформенный `common/helpers/utils`; каждая новая единица должна иметь узкую предметную ответственность.
