# Event Schema Reconciliation

## Краткий вывод
Фактический канон для project event journal уже есть: `schemas/event-envelope.schema.json` для `.pf/runtime/events/events.ndjson`. Append-time JSON Schema validation не доказана ни для одной из обязательных схем: текущий код пишет/нормализует JSON, а полная schema-проверка выполняется только отдельными валидаторами после записи или вообще отсутствует.

## Смежная ingress schema, важная для следующего шага
`schemas/pf-runtime-agent-event.schema.json` не входит в обязательную девятку master prompt, но это единственный явный кандидат на adapter input contract. `tools/pf_runtime/codex_hooks.py:46-70` создаёт именно такой raw payload family, а `tools/pf_runtime/host.py:439-469,569-599` ingest-нормализует его в canonical event envelope. При этом instance validation этой schema в runtime не найдено; `tools/validate-process-forge-schemas.py` проверяет только сам schema-файл структурно (`804-813`), не входные payloads.

## Решения, которые ограничивают дальнейшую ingress-архитектуру
- Не вводить новую параллельную canonical event schema: внутренний journal уже должен нормализоваться в `event-envelope`.
- Если нужен отдельный ingress contract для адаптеров, брать отдельную adapter-specific input schema (`pf-runtime-agent-event`), а не `process-event`/`processforge-event`/`agent-session-event`.
- `session-telemetry` и `chat-message` оставить отдельными потоками; в central journal хранить только event facts и ссылки/хэши, не полные transcript payloads.
- `hook-delivery` и `hook-result` считать только outbound/status contracts.
- `process-event`, `processforge-event`, `agent-session-event`, `chat-transcript` не расширять без появления реального runtime consumer.
- Не смешивать project и workplace streams: project journal это `.pf/runtime/events/events.ndjson`, а workplace `runtime/events/events.ndjson` уже может содержать другой shape, например `resource_management_event` из `tools/processforge.py:8771-8811`.
