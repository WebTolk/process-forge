# Регистрация задачи по полноте журнала разговора

2026-10-24. Основание: прямое поручение оператора создать задачу по исправлению
журналирования после обнаруженного пропуска ответов.

## Контекст и план

Регистрационная Work: `garage-pf-chat-journal-gap-registration-20261024-register-the-operator-r`.
Assignment: `pf-chat-journal-gap-registration-20261024-register-the-operator-requeste`.
Контекст свежий; капсула valid, read/write_artifact; продуктовая запись запрещена.
Один исполнитель, без subagents. План: проверить точный случай и существующие
карточки, сохранить spec/evidence, создать draft Run и planning-only Assignment
штатным CLI, проверить регистрацию и доставить только собственные артефакты.

## Область и исследование

Наблюдение основано на приватной стенограмме PF и исходном журнале той же сессии.
Найдены четыре финальных ответа, отсутствующие в PF. Исследованы документы
chat-relay и Garage/simple и связанные завершённые исправления capture.
MCP-чтение чата вернуло missing_session; использован разрешённый файловый путь.
Корневая причина не установлена; чтение не изменяло историческую стенограмму.

Новая задача дополняет широкий backlog чата конкретной проблемой полноты.
Связанные завершённые Work и их капсулы сохраняются. Переход registration Work
через стадии означает выполнение документальной регистрации, а не готовность
будущего исправления.

## Предметные правила и решение

Сообщение — отдельная запись с ролью, источником и идентичностью сессии/хода.
Готовый ответ отличается от промежуточного потока. Повтор доставки одного
сообщения и два разных сообщения с одинаковым текстом различаются.
Доступность стенограммы, покрытие событий и включённость захвата — отдельные факты.

Архитектурное решение регистрации: отдельная будущая карточка без продуктовых
прав; точные исходные тексты и локаторы приватны, публичное свидетельство содержит
timestamps, хеши и результат сопоставления. Дизайн исправления ещё предстоит.
Изменения внутренних механизмов, миграции и восстановление истории не выполняются.

## Проверки и сдача

Проверки регистрации: parse JSON/YAML, существование и хеши исходных свидетельств,
наличие ровно одной новой карточки в draft Run, planning_only, writer=false,
отсутствие product grants и workers, сохранность предыдущих входов и Git index.
Результаты будут записаны в validation.json и native receipts.

pytest/Ruff/mypy, проверка браузера и независимое code review неприменимы к
регистрации без изменения исполняемого кода. Ревью содержания карточки выполняет
основной агент; независимое review относится к будущему исправлению.
ZIP/build/install/Core apply не требуются: сдаётся только документальная
постановка через Git, без выпуска продукта и изменения инфраструктуры.

## Передача и вывод

Следующему исполнителю: начать с spec.md и приватного evidence locator,
установить причину пропуска, затем подготовить ограниченный план исправления
и квалифицировать реальный маршрут хоста. Неполные логи уже могут искажать
восстановление прошлых решений; полнота должна иметь наблюдаемые границы.
