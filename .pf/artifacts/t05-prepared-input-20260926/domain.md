# T05 prepared execution domain

Prepared input is a private, versioned, immutable delivery artifact for exactly one (project, run, assignment, context, attempt). It is derived from the accepted execution_contract, not a new Work or a rebuilt capsule. It carries capsule byte/contract/intent hashes, effective stage, scope/actions, required outputs, source/material provenance and bounded contents or file references. Driver/model/reasoning and transport are not authority and do not alter semantic input identity.

Preparation validates current assignment intent, required source integrity/capabilities, fresh current authorization and pinned snapshot/material. Every requested workspace grant must match pinned selection, current project authorization and stage subset; unmatched, revoked, changed or unresolved grants fail explicitly before process launch. Empty requested sets grant no additional workplace bodies. Metadata-only knowledge yields metadata only; no inferred corpus/root access. Nonknowledge registry grants need pinned/current selection match and successful resolution, not mere existence in a registry.

Required local source files remain inside declared read scope and T03 bounds. Deliver at most 64 KiB inline per text source and 256 KiB total inline; larger/binary material uses checksummed bounded file references and explicit truncation. Prepared JSON has a fixed 4 MiB ceiling. Resource material verification retains T02 limits. No automatic whole-corpus copy. Runtime private paths are allowed only inside private delivery state; public contracts retain portable references.

Attempt manifests live under an attempt directory and are never overwritten. State/command records point to the manifest plus checksum. A deliberate prepare creates the next attempt; concurrent/duplicate active start keeps the existing attempt. Failed preparation cannot mark an attempt ready or start a process. Immediately before start, revalidate prepared integrity/current access. Source or permission drift requires explicit repair/successor, never silent regeneration.

All drivers receive the prepared file pointer. The worker reads it directly; it must not call pf.work.start, reselect the process or bootstrap context. Native readers may read only declared references. Builtin generic-shell gets a provider-neutral wrapper to record starting/heartbeat/final exit; Codex retains its own wrapper with the same prepared input. This does not prove OS network/filesystem sandboxing or model quality.

Collection validates the exact prepared context/attempt and current outputs under lifecycle lock. A per-attempt receipt pins output bytes and stable collection event IDs. Repeating collection with the same receipt is idempotent; changed output bytes after collection are rejected. A new attempt cannot silently collect an unchanged leftover output: preparation records output baseline, and collection requires attributable new/changed files. Restart may repair missing completion effects using durable receipt and stable IDs. Ordinary governed primary stage transitions remain distinct from compatibility worker task completion.
