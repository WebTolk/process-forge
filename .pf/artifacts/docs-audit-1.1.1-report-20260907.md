Дата: 2026-09-07. Аудитор: основной агент, без делегирования.
Run: `garage-audit-pf-documentation-against-the-current-codebase-for-1-1-1-pre`.

## Вердикт

**Документация пока не готова к выпуску 1.1.1: подтверждены 8 расхождений — 5 P1 и 3 P2.**
P1 означает необходимость исправления до выпуска: инструкция препятствует штатной работе либо пропускает существенную часть процедуры. P2 — локальная ошибка, недостаточная полнота или вводящее в заблуждение описание, которое также следует устранить в предрелизной правке. P0 не обнаружены в проверенном объёме.

Это завершённый аудит, а не исправление документации и не разрешение на релиз. Продуктовые файлы не менялись. Записаны только частные материалы аудита и состояние `.pf`. Предыдущая незакоммиченная правка `required_output_checks` сохранена.

## D01 — P1: все пять команд управления индексом в RU-инструкции несовместимы с CLI

Документ: `docs/ru/concepts/resource-search-index.md:76` (команды на строках 76–80), также описание maintenance на строках 84–94.

Каждая команда `search-index status/refresh/rebuild/doctor/tick` содержит `--project-root`. Текущий CLI этот параметр не принимает: пять примеров дают argparse exit 2, `unrecognized arguments: --project-root AUDIT_VALUE`.

Код: `tools/processforge.py:26185` и следующие определения пяти subparser; `workplace_search_runtime_snapshot` на строке 23428; `command_search_index_refresh` на строке 23612. CLI обслуживает каталог Workplace с `--workplace`, а авторизация поиска проектным snapshot остаётся отдельным уровнем. Русский текст также продолжает предписывать периодический tick по проектам со свежими snapshot. Английский `docs/concepts/resource-search-index.md:80` уже показывает Workplace-команды.

Влияние: русскоязычный оператор не может выполнить опубликованную процедуру обслуживания индекса.

Исправление: синхронизировать RU-команды и модель maintenance с реализацией Workplace; не удалять описание проектной авторизации поисковых запросов. Пример: `python bin/pf.py search-index status --workplace <workplace>`.

Приёмка: все пять примеров разбираются текущим parser; в изолированном Workplace проходят status/refresh/doctor/tick; текст не требует обхода проектов для CLI maintenance.

## D02 — P1: специализированный промпт предписывает устаревший штатный жизненный цикл

Документы: `prompts/task-batch-execution-agent.md:8`, команды на строках 18–19, 34, 42–43; `docs/getting-started/task-batch-workflow.md:6`; `docs/ru/getting-started/task-batch-workflow.md:6`.

Промпт требует check-in/check-out, ручных `session-start`, `run-create`, `task-complete`, `run-complete`, `session-end` без ограничения на операторскую диагностику/совместимость. Обе вводные инструкции task batch также начинают с низкоуровневого жизненного цикла, не объясняя его статус.

Текущий контракт: `templates/project-agents-template.md:12` описывает `pf.work.start`, `pf.work.state`, `pf.work.transition` и закреплённую capsule; строка 29 ограничивает низкоуровневые команды совместимостью/диагностикой. `templates/process-agent-prompt.md:7` задаёт тот же цикл. `docs/concepts/runtime-mcp.md:48` запрещает обычному агенту создавать ручные production session id. Завершение последней стадии реализовано в `src/processforge_core/process_execution.py`, а не требует отдельной ручной команды завершения Run.

Влияние: агент, которому дали специализированный промпт, получает взаимоисключающие указания и может остановиться на искусственной зависимости от сессии либо обойти декларативные стадии.

Исправление: основной промпт и вводный сценарий перевести на Garage work API до `run_completed`; совместимый CLI-вариант явно отделить и объяснить его аудиторию. Раздел `Advanced Task Batch Run` в общем runbook уже помечен advanced — сам факт наличия такого раздела ошибкой не является.

Приёмка: агент по опубликованному основному промпту завершает изолированную работу без ручной Ledger-сессии; проверяются именно специализированный промпт и обе вводные страницы, а не только шаблон AGENTS.

## D03 — P2: полный пример task batch оставляет блокирующую задачу открытой

Документ: `docs/getting-started/task-batch-workflow.md:14`.

Пример создаёт `task-001-docs` и `task-002-tests` на строках 14–15, завершает только первую на строке 28, затем вызывает `run-complete` на строке 31.

Код: `tools/processforge.py:20423`, `_command_run_complete_locked`, отклоняет завершение при любой незавершённой блокирующей задаче. Проба с документированным состоянием и подменённым чтением Run воспроизводит `FAIL: blocking tasks are not done: task-002-tests` до любых записей.

Исправление: если совместимый пример остаётся, показать выполнение и завершение обеих задач или создать только одну; не объявлять вторую неблокирующей ради обхода проверки.

Приёмка: последовательность целиком выполняется в тестовом проекте и заканчивается завершённым Run без незавершённых блокирующих задач.

## D04 — P1: MCP-справка обещает старт только по objective, не описывая обязательный выбор при неоднозначности

Документы: `docs/concepts/runtime-mcp.md:39`, `docs/ru/concepts/runtime-mcp.md:44`.

Обе версии утверждают, что агент передаёт только непустой `objective`. Это достаточно не во всех разрешённых конфигурациях.

Код: `tools/pf_runtime/mcp_server.py:148` принимает и передаёт `process_id`; строка 216 объявляет его в схеме. `src/processforge_core/process_execution.py:583` возвращает `process_choice_required` при нескольких допустимых процессах без явного выбора. `default` — рекомендация, а не автоматический выбор при неоднозначности. Актуальное пояснение уже есть в `docs/concepts/garage-core.md:21` и строках 113–116.

Влияние: агент следует основной MCP-справке, повторяет тот же запрос и не получает новую работу в multi-process проекте.

Исправление: описать `process_id`, единственный допустимый процесс, закреплённый текущий Run и ответ с кандидатами; показать повторный start с выбранным разрешённым процессом. Не советовать менять manifest ради старта.

Приёмка: примеры EN/RU покрывают одну и несколько разрешённых процессов, отказ для неразрешённого процесса и сохранение pin текущего Run. Свежий `smoke_multi_process_work_capsule` уже подтверждает поведение реализации.

## D05 — P1: пример front matter не задаёт путь обязательного результата

Документ: `docs/concepts/assignment-front-matter.md:25`.

Показано `required_outputs: [".pf/artifacts/example-report.md"]`. В этой форме строка является идентификатором результата, а не путём.

Код: `tools/processforge.py:12403`, `normalize_required_outputs`, преобразует строку в `{id, type, required}`, без `path`. Контракт задания использует эту же нормализацию на строке 12744 и переносит результаты в capsule на строке 12953. `required_output_checks` на строке 12464 возвращает `FAIL: required output has no path: pf-artifacts-example-report-md`.

Доказательство: проба извлекает YAML именно из опубликованного fenced-примера, нормализует его и вызывает текущую проверку. Это не утверждение о запуске полного сценария создания capsule; связь с capsule проверена по исходному коду.

Исправление: заменить элемент явной записью:

```yaml
required_outputs:
  - id: example-report
    path: .pf/artifacts/example-report.md
    type: markdown
    required: true
```

Приёмка: пример даёт ожидаемый `missing` до создания файла и `PASS` после создания; ошибки `has no path` нет. Проверять не только синтаксис YAML, но и нормализованный output contract.

## D06 — P1: русская процедура первого управляемого обновления пропускает миграцию Workplace

Документы: `docs/ru/getting-started/update-system.md:50` (plan/apply на строках 50–51); `docs/ru/concepts/core-update-manifest.md` не содержит соответствующего раздела миграции.

Английская процедура `docs/getting-started/update-system.md:48` передаёт `--workplace-root <workplace>` в plan и apply; английская справка `docs/concepts/core-update-manifest.md:42` объясняет добавочную миграцию runtime driver и последующий doctor. В русском варианте параметра и объяснения нет.

Код: `src/processforge_core/core_update.py:236`, `workplace_migration_plan`, немедленно возвращает `status: not_requested`, если `workplace_root` отсутствует. Это подтверждено чистым вызовом функции без чтения архива или применения обновления. Миграция `updates/migrations/1.1.0-workplace-runtime-drivers.yaml` добавляет отсутствующие defaults `codex-exec` и регистрацию, сохраняя существующие значения.

Влияние: Core может обновиться, но ожидаемая миграция существующего Workplace по русской процедуре не будет запрошена.

Исправление: синхронизировать русские plan/apply и описание сохранения конфигурации, post-update doctor, явного подтверждения оператора. Не подменять обновление командой `workplace-init`.

Приёмка: одинаковый план EN/RU на копии прежнего Core/Workplace; отсутствующие defaults добавляются, пользовательские значения сохраняются; в отчёте apply зафиксирована проверка Workplace. Реальное обновление установленной копии не входило в этот аудит.

## D07 — P2: в основном агентском маршруте не хватает полного примера transition/evidence

Документы: `docs/getting-started/agent-prompts.md:42` и `docs/ru/getting-started/agent-prompts.md:45` перечисляют context/search/resolve/start, но не дают законченного примера `state → transition → run_completed`; `docs/concepts/declarative-process-execution.md:21` описывает evidence только в общем виде. `docs/index.md:26` и аналогичный RU-индекс направляют к старому общему runbook, но не включают новые `garage-core.md` и `declarative-process-execution.md`.

Код: `src/processforge_core/process_execution.py:802`, `_gate_state`, признаёт только `passed`, `approved`, `not_applicable` для gate evidence. Проба показывает, что естественное, но неверное `status: pass` не удовлетворяет gate. Идентификаторы evidence должны соответствовать текущим требованиям `pf.work.state`.

Это пробел документации, а не утверждение, что переходы вообще нигде не описаны: MCP-концепт и новый декларативный концепт содержат их краткое описание.

Исправление: добавить в связанный с индексом runbook один законченный сценарий с реальными полями artifact/gate evidence, `notes`, обработкой отсутствующего evidence и продолжением до `run_completed`; дать явные ссылки на актуальные концепты в обеих языковых версиях.

Минимальная форма данных (id и пути нужно брать из конкретного текущего контракта, файлы должны реально существовать):

```json
{
  "outcome": "completed",
  "notes": "Результат записан, проверка завершена; следующая стадия определяется процессом.",
  "evidence": [
    {"kind": "artifact", "id": "task-result", "path": ".pf/artifacts/result.md"},
    {"kind": "gate", "id": "all-blocking-tasks-completed", "status": "passed", "path": ".pf/artifacts/result.md"}
  ]
}
```

Приёмка: исполнимый пример проверяется на процессе с обязательным artifact и gate; отсутствие результата блокирует переход, исправленное evidence позволяет продолжить, последняя стадия завершает Assignment и Run автоматически.

## D08 — P2: описание валидатора контрольных сумм не соответствует его поведению

Документ: `docs/validation/validation.md:21`.

После команды без флагов написано, что она создаёт inventory и проверяет checksum-поля immutable context packages. Фактически команда по умолчанию проверяет существующий публичный inventory; запись требует `--write`. Проверки capsule/context checksum-полей этот скрипт не выполняет.

Код: `tools/validate-process-forge-checksums.py:130`, `main`: ветка записи только для `args.write`, иначе `check_inventory(root, output)`; состав inventory ограничен публичными файлами.

Исправление: разделить `--check`/default и `--write`; отдельно указать соответствующие context/capsule doctors, не приписывая их гарантии inventory-валидатору.

Приёмка: документация точно отражает read-only default; пример записи явно помечен как изменение inventory; проверки неизменяемых контекстов названы отдельно.
