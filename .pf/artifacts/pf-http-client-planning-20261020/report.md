# Будущий вопрос: HTTP-клиент PF и MCP

Зарегистрирована карточка `pf-http-client-mcp-feasibility-20261020` в отдельном draft Run `pf-http-client-future-backlog-20261020`: open/planning_only, writer=false, без продуктовых разрешений и execution capsule. Отдельный scope сохраняет незавершённую uptime Work и её точные selectors.

Вопрос: почему агенты создают временные сценарии HTTP-вызовов при наличии urllib.request/http.client и полезен ли общий клиент/CLI либо MCP-инструмент. Будущая оценка должна опираться на реальные повторяющиеся сценарии, существующие средства PF, различать транспорт и предметную обвязку и допускать решение о повторном использовании без нового инструмента.

Критерии включают минимальный контракт при оправданном MCP-варианте, авторизацию/секреты, ограничения ответов/времени, редиректы, отмену, идемпотентность, понятные ошибки и изолированные примеры. Все временные сценарии ошибкой не объявляются. Реализация и обращения к пользовательским API сейчас не выполнялись.

Использован выбранный PF ресурс docs.python:root/standard-library.md. Справочные страницы: [urllib.request](https://docs.python.org/3/library/urllib.request.html), [http.client](https://docs.python.org/3/library/http.client.html). Внешнее подтверждение наличия стандартного HTTP-клиента было избыточным; дальнейшая работа использует локальные Python-знания PF в первую очередь.

Native task-doctor и future run-doctor PASS, exit 0. Продуктовый Python не менялся: pytest/Ruff/mypy реализации HTTP здесь неприменимы. Это регистрация будущего вопроса, а не выполнение такой реализации. После последнего уточнения пользователя исполняется ровно одна продуктовая задача — uptime; затем коммит/push и остановка.
