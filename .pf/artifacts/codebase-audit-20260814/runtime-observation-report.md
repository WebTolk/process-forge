# Runtime Observation Report

## Итоговый статус
- **FAIL** (подтверждены 2 дефекта в жизненном цикле worker-run).

## 1) Повторный `worker-run start` может перезапускать уже выполняющийся процесс без защиты по состоянию задачи
- **Серьёзность:** Высокая (жизненный цикл/длительность/долговечность состояния)
- **Файлы/линии:**
  - `tools/processforge.py:17673-17680` — `command_worker_run_start` всегда вызывает `prepare_worker_run(...)` без проверки текущего `state.status`.
  - `tools/processforge.py:17653-17660` — `prepare_worker_run` всегда перезаписывает состояние задачи в `ready/manual_required`.
  - `tools/processforge.py:17021` + `tools/processforge.py:18014-18015` — список `AGENT_RUN_START_SKIP_STATUSES` используется только в `supervisor`-цикле, а не в ручном `worker-run start`.
- **Предусловие/репродукция:**
  1) Запустить задачу через `worker-run start --detach`.
  2) До завершения процесса выполнить второй `worker-run start` той же задачи.
- **Ожидаемое:** второй запуск должен быть отвергнут как уже-running (или явное подтверждение пересоздания).
- **Фактическое:** второй запуск создаёт новый процесс и перезаписывает durable-состояние, что может потерять привязку к первому pid и породить гонки/утечки следов.

## 2) Аргумент `--wait` в `worker-run start` фактически не используется
- **Серьёзность:** Средняя (API поведение/ожидаемость запуска)
- **Файлы/линии:**
  - `tools/processforge.py:25068-25070` — `--wait` объявлен в CLI.
  - `tools/processforge.py:17694` — в `command_worker_run_start` берётся только `--detach`; ветка `--wait` не применяется.
- **Предусловие/репродукция:**
  `worker-run start --wait` (с или без `--detach`) — поведение отличается от описания help: у команды нет управления режимом ожидания на основе `--wait`, только `--detach` влияет на поведение.
- **Ожидаемое:** флаг, присутствующий в CLI, должен участвовать в принятии решения о синхронном/асинхронном запуске.
- **Фактическое:** параметр игнорируется для ручного запуска.
