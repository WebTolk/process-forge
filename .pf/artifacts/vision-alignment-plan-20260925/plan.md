## Цель

PF сохраняет проверяемое состояние проекта и процесса и выдаёт сменному
исполнителю ограниченный контракт текущей работы. Знания, инструменты,
шаблоны и разрешения должны относиться к конкретной Work и её стадии.
Провайдерные интеграции подключаются через адаптеры; техническое сопровождение
работы выполняется общими механизмами PF.

Опора: [общее видение](../reference-projections/processforge-general-vision.md).
Фактическая база: [baseline.md](baseline.md).
Подробные задания: [tasks.md](tasks.md).

## Предлагаемые архитектурные ограничения

1. Источником процессных фактов остаются файлы PF. Проекции восстанавливаются
   из них и не становятся самостоятельным источником истины.
2. Work закрепляет версию контракта, процесс и допустимый набор ресурсов;
   стадия выбирает только подмножество внутри этих границ.
3. Текущие запреты доступа имеют приоритет над историческими разрешениями.
   Отзыв доступа блокирует чтение с понятной причиной. Новый ресурс B не
   добавляется к Work с ресурсом A неявно.
4. Обновление контекста Work требует явного перехода: новая Work либо новый
   связанный контекст по утверждённой схеме. Существующие immutable capsules
   и определения процессов не переписываются.
5. Project-level context/search/resolve остаются отдельным режимом навигации.
   Чтение для активной Work должно явно идентифицировать Work и её поколение.
6. Набор контекста содержит источники, ссылки, правила доступа и требования
   к результатам. Он не обязан содержать весь корпус знаний или единый
   текстовый промпт для всех моделей.
7. Общие механизмы безопасности проверяют полномочия, принадлежность данных,
   целостность, дубликаты и пути. Специфику событий провайдера знает адаптер.
8. MCP и CLI используют один прикладной контракт; подготовленный файловый
   вход допускает исполнителя без MCP и без сетевого соединения.
9. Автоматическая проверка файлов/хэшей/событий не подменяет смысловое ревью.

Эти ограничения — вход для T01. Точные API, схема регистрации адаптеров,
версии и названия новых модулей выбираются на стадии architecture-plan.

## Процесс исполнения

Каждый самостоятельный срез проходит software-feature-development:
orchestration → intake-scope → investigation → domain-modeling →
architecture-plan → implementation → code-assurance → release-delivery → evolve.
Номера T00–T07 — задания плана, а не идентификаторы стадий PF.

Перед изменениями: актуализировать исходную базу, создать/выбрать Work через
pf.work.start, прочитать pf.work.state и выданную капсулу, закрепить допустимые
файлы. Стадии переводить только объявленным outcome и evidence; следующую
стадию выбирает PF. Общие файлы передаются последовательно одному писателю.

Для каждого среза нужны scope, investigation/impact, domain rules,
architecture/implementation plan, changed-files/change-summary, review,
test-report и handoff по обязательствам текущей стадии. Уже выполненная
сверка — входное исследование; она не означает прохождение этих gates.

## Приёмка всей основной последовательности

- Work после обновления проекта не получает новый контекст неявно.
- Отозванный или отсутствующий ресурс даёт явную диагностику; устаревшая
  капсула не становится способом обойти текущие ограничения.
- Required resources, scope, tools/templates/capabilities и outputs доступны
  из одного согласованного контракта, а не собираются агентом по догадкам.
- Изменение стадии не расширяет права и не меняет immutable-контекст на месте.
- Новый тестовый провайдер диалогов подключается через доверенный адаптер;
  подмена provider/adapter, неправильный hash или session не принимаются.
- Generic-shell исполнитель без MCP проходит путь вход → результат →
  evidence → продолжение другой сессией; тест не требует внешней модели.
- Codex-интеграция сохраняет прежний функционал и проверки безопасности.
- Остановка/повтор/восстановление не теряют доказательства и не дублируют
  завершение стадии, сообщения или побочные эффекты.
- Документация EN/RU точно различает реализованные контракты, адаптеры и
  будущую фильтрацию данных.

## Поставка и ограничения

В план не включены установка/перезапуск Runtime, MCP или Ledger, обновление
установленного Core/Workplace, публикация релиза, глобальная миграция проектов,
массовое закрытие исторических runs или общий рефакторинг tools/processforge.py.
Готовые интеграции со всеми провайдерами и установка локальной модели также
не являются критерием приёмки этой последовательности.

Для локальной поставки release-delivery должен явно фиксировать применимость
и evidence. Если понадобится релиз, потребуется отдельная квалификация
чистого кандидата: source → archive → extracted distribution. Она не заменяется
сфокусированными smoke-проверками и не означает разрешения публикации.
