# Независимый review: `ledger-hooks-mcp-next-stage-20260814`

## Итоговая оценка
**FAIL** — найдены 2 критических пробоя безопасности/изоляции, требующие исправления до прод-использования.

## Критерий: cache authority (источник истины для маршрутизации сессий)
- **PASS**
  В рантайме при обращении сессии используется Ledger как основной источник:
  - `ledger_session()` напрямую читает `core.find_agent_presence(...)` и явно помечает Runtime state как «не авторитетный» кэш.
  - `project_for_session()` берёт `project_root` из presence-данных Ledger, затем сверяет `project_id`.
  - `remember_session()` помечает запись как `"cache_only": True`, что соответствует концепту кэша.

### Оценка
- Выбор источника истины соответствует целевой архитектуре (Ledger + durable события).
- Нагрузочно-резилиентная проверка в `ingest_event()` сохраняет контроль: событие для неизвестной сессии отклоняется, кроме стартовых событий.

## Критерий: cross-project leakage (утечка между проектами)
- **FAIL**
  `tools/pf_runtime/mcp_server.py` допускает обход проверки проекта через параметр `project_root`, даже если сессия принадлежит другому проекту:
  - `tool_result()` напрямую вызывает `host.project_state_payload(..., project_root_ref=arguments.get("project_root"))`/`work_state_payload`/`resolve_payload`.
  - В `host.project_for_session()` при наличии `project_root` проверки сессии вообще не делается.
  - Проверка привязки сессии к проекту (`assert_session_project_scope`) существует в HTTP-маршрутизации `service.py`, но в MCP-слой не используется.

### Риск
Любой сессионный токен может читать состояние произвольного проекта при передачи `project_root`, что нарушает изоляцию и может раскрыть состояния и ресурсы другого проекта.

## Критерий: hook reliability (надёжность hooks)
- **PASS (с оговорками)**
  `codex_hooks.py` корректно нормализует поддерживаемые события и деликатно игнорирует неподдерживаемые/невалидные входы (без падения CLI), что повышает отказоустойчивость.
- Есть осознанный soft-fail: исключения в `main()` также возвращают `{"status":"ignored"}`.

### Риск/ограничение
Случайные/неожиданные payload могут быть молча проигнорированы. Это приемлемо для наблюдательного адаптера, но уменьшает диагностическую видимость; для production-критичных цепочек полезны метрики/теле-метки на `ignored`.

## Критерий: MCP read isolation (изоляция MCP чтения)
- **FAIL**
  См. раздел про cross-project leakage. MCP является read-only по API (`pf.project_state`, `pf.work_state`, `pf.resolve`, `pf.workplace_state`), но изоляция между проектами нарушена из-за передачи и доверия `project_root` без принудительной привязки к сессии в MCP-обработчике.
- Дополнительно: ошибки MCP-результатов отдаются в `result` с `isError: True`, но это не нивелирует утечку read-привилегий.

## Критерий: daemon lifecycle regression (регрессии жизненного цикла daemon)
- **FAIL**
  Конкретная регрессия: endpoint `/shutdown` не защищён токеном.
  - В `service.py` авторизация выполняется только для всех путей кроме `"/shutdown"` (`if self.path != "/shutdown" and not self.authorize():`), то есть запросы `POST /shutdown` могут пройти без `Authorization`.
  - Это делает daemon stop доступным без проверки подлинности клиента.

### Риск
Незаконное/случайное завершение службы runtime.

## Рекомендуемые корректирующие шаги (без редизайна)
1. MCP (`mcp_server.py`): перед любыми `project_root` вызовами в `tool_result()` принудительно валидировать сессионную привязку к проекту через `host.project_for_session` + `host.assert_session_project_scope`-аналог/аналогичную проверку.
2. Добавить единый path-level guard в MCP на уровень проекта, либо удалить возможность `project_root` из внешнего ввода для read-tool-ов, если сессия уже известна.
3. `Runtime` HTTP handler (`service.py`): закрыть `/shutdown` той же авторизацией, что и остальные методы.
4. Добавить regression smoke:
   - `PF_MCP_SESSION_ID` с project_root другого проекта должен получать отказ.
   - `POST /shutdown` без токена должен возвращать 401.
