# Готовность PF к публичному релизу — 15 октября 2026 года

Текущий dev-результат **не готов к новому стабильному публичному релизу**.
Проверенный исходный срез следует зафиксировать и продолжить ограниченные работы.
Незавершённый ООП-рефакторинг сам по себе не блокирует выпуск: готовность
определяют поддерживаемое поведение, контракты и доказательства поставки.

[Аудит от 14 октября](../audits/pf-audit-20261014.md) зафиксировал 264 PASS /
3 FAIL из 267 проверок, четыре ограниченных нарушения и наблюдения Runtime/
бюджетов. Эти результаты относятся к указанной в аудите ревизии и не являются
полной приёмкой каждой последующей правки.

## Текущее состояние

- HTTP-метод Runtime `read_body` по-прежнему передаёт отрицательный
  Content-Length в `read(-1)`, принимает короткое тело с завершённым JSON
  и допускает неконечные JSON-числа. Точное текущее тело метода проверено
  с инертными потоками; положительный контроль, oversize и некорректная длина
  проверены отдельно. Доказано поведение reader, а не сетевая атака, зависание
  сокета или DoS.
- Для нативного prepare/start остаётся вопрос terminal governed Work и повторов
  failed worker attempts из PF-AUDIT-04. Новый MCP-фасад отклоняет терминальную
  Work до нативного вызова; это не исправляет прежний CLI-путь и не доказывает
  атомарный допуск между разными lifecycle.
- Текущие изменения MCP проверяют объявленные границы массивов до business
  dispatch при сохранении схем. Исправление проверяют направленные контрпримеры
  и контроли. Они не заменяют полную приёмку накопленного релизного кандидата.
- Прежние MCP-операции сохраняют выбор каталога необязательной диагностики
  по project ID. Текущий изолированный контроль `pf.resolve` создаёт диагностику
  в другом каталоге с тем же ID до предметной проверки. Новые инструменты проходят
  собственный допуск до такой диагностики; прежний маршрут требует исправления.
- Исходники, чистый кандидат/архив, установленный Core, Runtime и фактически
  подключённый MCP требуют отдельных доказательств. Подключённый процесс может
  расходиться с текущей source CLI или сохранять старые инструменты после
  изменения файлов на диске.
- Наблюдались длительное создание Work в большом рабочем каталоге и отсутствие
  выбранных Python-текстов в prepared input. Проверенные копии знаний PF
  позволили продолжить внутри действующего scope. Нужны измерение и исправление
  этих путей; недоказанный общий диагноз производительности и обход полномочий
  не требуются.

## Условия стабильного выпуска

1. Исправить framing и допуск terminal Work с положительными, отрицательными
   и retry-контролями; классифицировать остальные ошибки поддерживаемой поверхности.
2. Воспроизвести либо локализовать прежние сбои регистрации Runtime и превышения
   штатного бюджета task batch. Увеличенный timeout не заменяет прохождение бюджета.
3. Выбрать новую версию, подготовить changelog, migration notes и исходный коммит.
   Существующие immutable assets и теги сохраняются.
4. Один раз квалифицировать накопленный чистый кандидат: schema/cleanliness/
   checksums, полный source suite, архив/хеш/provenance и полный extracted suite,
   затем применимые clean install/update и свежие проверки подключённого хоста.
5. Выполнить [контракт публикации](../maintainers/release-publishing.md), подтвердив
   точные tag, commit, assets и update channel после выпуска.

Пока подтверждённые блокеры сохраняются, для dev-итераций нужны относящиеся
к изменению проверки. Полный публичный и архивный цикл относится к кандидату,
способному пройти условия выпуска. Процент готовности не выводится из числа
классов, завершённых задач или доли успешных исторических тестов.
