# Готовность PF к публичному релизу — 15 октября 2026 года

Текущий dev-результат **не готов к новому стабильному публичному релизу**.
Проверенный исходный срез следует зафиксировать и продолжить подготовку 1.2.0.
Незавершённый ООП-рефакторинг сам по себе не блокирует выпуск: готовность
определяют поддерживаемое поведение, контракты и доказательства поставки.

[Аудит от 14 октября](../audits/pf-audit-20261014.md) зафиксировал 264 PASS /
3 FAIL из 267 проверок, четыре ограниченных нарушения и наблюдения Runtime/
бюджетов. Эти результаты относятся к указанной в аудите ревизии и не являются
полной приёмкой каждой последующей правки.

## Текущее состояние

- HTTP-метод Runtime `read_body` теперь отклоняет некорректную, отрицательную
  и чрезмерную длину до чтения, короткое тело до разбора и неконечные JSON-числа,
  включая переполнение float. Направленные проверки инертных потоков и
  изолированного HTTP-сервера подтверждают исходное исправление, корректное
  байтовое чтение, авторизацию и продолжение обработки после отказов. Команду
  `python tools/smoke_runtime_http_body.py` следует выполнить вместе с проверками
  накопленного кандидата. Полная приёмка кандидата, установленного Runtime и
  подключённого хоста остаётся отдельной; сетевая атака, зависание сокета и DoS
  не заявляются.
- Нативные prepare/start теперь отклоняют терминальную управляемую Work до
  подготовки и запуска провайдера. Наблюдение отделяет сбой worker attempt от
  жизненного цикла assignment; повторы действующей Work и поддерживаемые legacy
  retries сохранены. Существующий smoke восстановления подготовленного
  исполнения покрывает исходное исправление и границы побочных эффектов.
  Атомарный допуск между разными lifecycle locks этим ограниченным исправлением
  не доказан; накопленный кандидат, установка и подключённый хост проверяются
  отдельно.
- Текущие изменения MCP проверяют объявленные границы массивов до business
  dispatch при сохранении схем. Исправление проверяют направленные контрпримеры
  и контроли. Они не заменяют полную приёмку накопленного релизного кандидата.
- Необязательная диагностика прежних MCP-операций теперь проверяет канонический
  путь привязанного каталога вместе с project ID. Одиннадцать проверок настоящего
  журнала и диспетчера сохраняют ответы и устраняют две записи в чужой каталог
  с тем же ID. Подробности — в [отчёте](audits/mcp-diagnostic-root-20261016.md).
  Установленное ядро и подключённый хост проверяются отдельно.
- Ограниченное исправление Windows-диагностики установлено; полный исходный
  smoke теперь проходит при остановленном общем Runtime. Условия и бюджеты
  сохранены, прежние отказы остаются историческими. См.
  [текущий dev-отчёт](releases/dev-journal-lock-20261016.md).
- Исходники, чистый кандидат/архив, установленный Core, Runtime и фактически
  подключённый MCP требуют отдельных доказательств. Подключённый процесс может
  расходиться с текущей source CLI или сохранять старые инструменты после
  изменения файлов на диске.
- Наблюдались длительное создание Work в большом рабочем каталоге и отсутствие
  выбранных Python-текстов в prepared input. Проверенные копии знаний PF
  позволили продолжить внутри действующего scope. Нужны измерение и исправление
  этих путей; недоказанный общий диагноз производительности и обход полномочий
  не требуются.
- Измеренное узкое место проверки областей устранено общим владельцем в Core
  для создания Work, supervisor и планов. Отсев по буквальным префиксам и один
  отложенный нормализованный список сохраняют решения, причины и порядок
  конфликтов. Медиана пяти проверок областей на настоящем проекте — 1,782 с;
  полное создание Work и установленное ядро измеряются отдельно. Подробности,
  сравнительные замеры и остаточные затраты каталога/неоднозначных масок —
  в [отчёте о задержке](audits/work-start-scope-latency-20261015.md).

## Условия стабильного выпуска

Предыдущая dev-итерация установила накопленные исправления из исходника
`61a7b74cfa7b1812641d7cef85760449dccb06be`. Точный архив, нативная транзакция,
исходные установленные проверки и замеры описаны в
[отчёте о dev-установке](releases/dev-fast-work-20261016.md). Медиана обычного CLI
Work state —1,355501 с; отдельного прогретого постоянного stdio —0,0493904 с.
Условия запуска различаются. Нативные task batch 52,82/180 с и long-lived Runtime
54,54/240 с проходят прежние бюджеты. Направленная source/archive/installed
приёмка этой dev-итерации завершена.

Блокеры стабильного выпуска сохраняются: восстановленный общий Runtime занимает почти одно ядро и остаётся degraded; последний полный замер создания Work до этой поставки составлял около 19 с; новый замер нужен отдельно. Не завершены
полные накопленные suites, version/changelog и проверка настоящего подключённого
хоста. Новый профиль указывает на HTTP-приём событий и перестроение обязательств
стадий. Условия и бюджеты не ослаблялись. Канонический выбор и prepared YAML не
закрывают эти отдельные пути; OOP-эпики открыты. Публичная 1.2.0 требует подробного
отчёта о готовом кандидате и отдельного одобрения пользователя.


1. Проверить исправления framing и допуска terminal Work в накопленном
   кандидате с положительными, отрицательными и retry-контролями;
   классифицировать остальные ошибки поддерживаемой поверхности.
2. Воспроизвести либо локализовать прежние сбои регистрации Runtime и превышения
   штатного бюджета task batch. Увеличенный timeout не заменяет прохождение бюджета.
3. Подготовить changelog, migration notes и исходный коммит для 1.2.0.
   Существующие immutable assets и теги сохраняются.
4. Один раз квалифицировать накопленный чистый кандидат: schema/cleanliness/
   checksums, полный source suite, архив/хеш/provenance и полный extracted suite,
   затем применимые clean install/update и свежие проверки подключённого хоста.
5. Выполнить [контракт публикации](../maintainers/release-publishing.md), подтвердив
   точные tag, commit, assets и update channel после выпуска.

Пока подтверждённые блокеры сохраняются, для dev-итераций нужны относящиеся
к изменению проверки. Полный публичный и архивный цикл относится к кандидату,
способному пройти условия выпуска. Процент готовности не выводится из числа
классов, завершённых задач или доли успешных исторических тестов.
