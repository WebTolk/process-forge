# Декларативное исполнение процесса

ProcessForge исполняет Process YAML через единый `ProcessExecutionService`.
Определение процесса содержит только данные: без Python plugins, callbacks,
dynamic imports и исполняемого кода.

Обычный путь агента:

`pf.context -> pf.work.start(objective, process_id?) -> текущее состояние Work -> работа ->
pf.work.transition(outcome, evidence, notes?) -> возвращённое состояние -> ... -> run_completed`

`pf.work.start` выбирает объявленную `initial_stage` либо первую executable
stage, а затем закрепляет эффективное Process definition, версию, fingerprint,
context snapshot и immutable Assignment capsule. Изменение Process YAML не
меняет уже начатый Run. При нескольких разрешённых процессах без явного выбора
возвращается `process_choice_required`: выберите предложенный `process_id` и
повторите start. `default` — рекомендация, а не автоматический выбор.

`pf.work.state` возвращает текущий контракт исполнения: Process, Run,
Assignment, stage, required inputs, obligations, artifacts, gates, blockers и
allowed outcomes.

`pf.work.transition` принимает outcome, evidence и optional notes. Линейный
маршрут следует порядку `stages[]`; минимальное ветвление задаётся
`outcomes[].next_stage`. Агент никогда не передаёт следующую stage, а
`process_transitions` остаются механизмом межпроцессных переходов.

## Свидетельства и восстановление после отказа

Например, стадия `task-result-fixation` может требовать артефакт `task-result`
и gate `all-blocking-tasks-completed`. Сначала создайте файл результата,
действительно проверьте блокирующие задачи и запишите результат проверки.
Затем передайте аргументы в `pf.work.transition`:

```json
{
  "project_root": "<project-root>",
  "run_id": "<returned-run-id>",
  "assignment_id": "<returned-assignment-id>",
  "context_id": "<returned-context-id>",
  "outcome": "completed",
  "notes": "Результаты задач и проверки записаны; работа готова к ревью Run.",
  "evidence": [
    {"kind": "artifact", "id": "task-result", "path": ".pf/artifacts/result.md"},
    {"kind": "gate", "id": "all-blocking-tasks-completed", "status": "passed", "path": ".pf/artifacts/result.md"}
  ]
}
```

Это пример конкретной стадии: берите идентификаторы, обязательства и допустимый
outcome из своего `pf.work.state`. Сохраняйте точные селекторы из start/resume;
без привязанной сессии передавайте их в каждый вызов Work. Перед записью проверьте
разрешения Assignment и капсулы. Для существующей работы используйте
[продолжение](work-continuation.md). Пути относятся к корню проекта; файлы должны
существовать. Gate принимает `passed`, `approved` или обоснованный
`not_applicable`, но не `pass`. Запись gate — подтверждение выполненной проверки,
а не автоматическое доказательство смыслового качества документа.

Если обязательного evidence не хватает, ответ содержит `action: incomplete`
и список невыполненных требований. Некорректное evidence может вернуть
`action: transition_rejected`. Оба ответа сохраняют текущую стадию. Выполните
недостающие проверки, исправьте evidence и повторите переход. Не обходите отказ
ручной правкой YAML. После
`stage_transitioned` используйте полную текущую проекцию Work из ответа. Если её
нет, а также после неопределённого результата, переподключения или параллельных
изменений вызовите `pf.work.state`. Повторное чтение того же состояния не нужно
после каждого успешного перехода. Продолжайте до `action: run_completed`, а не
только до первого успешного перехода.

[Пример структуры state и перехода на английском](../../concepts/declarative-process-execution.md).

Последний успешный transition завершает Assignment и Run, пишет summary и
handoff, обновляет projection и публикует события `process.stage.*`.

Ручные `run-create` и `task-complete` относятся к отдельному
[batch-сценарию](../getting-started/task-batch-workflow.md). Для завершения
управляемой Work не добавляйте `run-complete` или `run-summary`: завершением
владеет последний переход. Жизненный цикл сессии хоста остаётся отдельным.

## Внутренние итерации и вложенная работа

Один Run может включать повторные исследования, уточнения домена и архитектуры,
согласованные редакции плана, реализацию и локальные проверки цельного результата.
Это не требует перехода после каждой правки или итоговой приёмки и публикации
после каждой итерации. Используйте только действия и outcomes текущего контракта:
это описание не добавляет обратных маршрутов или разрешения редактировать файлы.
См. [границы Run и итерации](process-definition-run-task-iteration.md).

Крупное поручение воркеру может проходить собственный полный процесс, вложенный
в родительский цикл. Основной агент проверяет и интегрирует его результат;
завершение дочерней работы не завершает и не публикует родительскую автоматически.

## Результаты исполнителя и продолжение работы

Исполнитель может получать [подготовленный вход](prepared-input.md) без MCP.
Сбор результата сохраняет основной управляемый Run, стадию Assignment и
неизменяемую капсулу. Основной агент проверяет результат и передаёт
свидетельства для перехода стадии. Старые задачи имеют отдельный совместимый
путь завершения; повторный сбор и восстановление квитанции не должны
дублировать события завершения.

Смена настроек исполнителя или соединения не разрешает менять цель, снимок и
набор ресурсов. После подключения сверяйте идентичность Work, текущую стадию
и принятые свидетельства с долговечными файлами. Обязательства стадии выводятся
из закреплённого процесса и текущего назначения без перезаписи капсулы.
См. [контекст Work](work-context.md) и [ресурсы Work](work-resources.md).
