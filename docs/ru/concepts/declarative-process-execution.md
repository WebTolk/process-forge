# Декларативное исполнение процесса

ProcessForge исполняет Process YAML через единый `ProcessExecutionService`.
Определение процесса содержит только данные: без Python plugins, callbacks,
dynamic imports и исполняемого кода.

Обычный путь агента:

`pf.context -> pf.work.start(objective, process_id?) -> текущее состояние Work -> работа ->
pf.work.transition(outcome, evidence, notes?) -> возвращённое состояние -> ... -> run_completed`

`pf.work.start` выбирает объявленную `initial_stage` либо первую executable
stage, а затем закрепляет эффективное Process definition, версию, fingerprint,
context snapshot и immutable Assignment capsule. Изменение Process YAML не
меняет уже начатый Run. При нескольких разрешённых процессах без явного выбора
возвращается `process_choice_required`: выберите предложенный `process_id` и
повторите start. `default` — рекомендация, а не автоматический выбор.

`pf.work.state` возвращает текущий контракт исполнения: Process, Run,
Assignment, stage, required inputs, obligations, artifacts, gates, blockers и
allowed outcomes.

`pf.work.transition` принимает outcome, evidence и optional notes. Линейный
маршрут следует порядку `stages[]`; минимальное ветвление задаётся
`outcomes[].next_stage`. Агент никогда не передаёт следующую stage, а
`process_transitions` остаются механизмом межпроцессных переходов.

## Свидетельства и восстановление после отказа

Например, стадия `task-result-fixation` может требовать артефакт `task-result`
и gate `all-blocking-tasks-completed`. Сначала создайте файл результата,
действительно проверьте блокирующие задачи и запишите результат проверки.
Затем передайте аргументы в `pf.work.transition`:

```json
{
  "project_root": "<project-root>",
  "run_id": "<returned-run-id>",
  "assignment_id": "<returned-assignment-id>",
  "context_id": "<returned-context-id>",
  "outcome": "completed",
  "notes": "Результаты задач и проверки записаны; работа готова к ревью Run.",
  "evidence": [
    {"kind": "artifact", "id": "task-result", "path": ".pf/artifacts/result.md"},
    {"kind": "gate", "id": "all-blocking-tasks-completed", "status": "passed", "path": ".pf/artifacts/result.md"}
  ]
}
```

Это пример конкретной стадии: берите идентификаторы, обязательства и допустимый
outcome из своего `pf.work.state`. Сохраняйте точные селекторы из start/resume;
без привязанной сессии передавайте их в каждый вызов Work. Перед записью проверьте
разрешения Assignment и капсулы. Для существующей работы используйте
[продолжение](work-continuation.md). Пути относятся к корню проекта; файлы должны
существовать. Gate принимает `passed`, `approved` или обоснованный
`not_applicable`, но не `pass`. Запись gate — подтверждение выполненной проверки,
а не автоматическое доказательство смыслового качества документа.

Если обязательного evidence не хватает, ответ содержит `action: incomplete`
и список невыполненных требований. Некорректное evidence может вернуть
`action: transition_rejected`. Оба ответа сохраняют текущую стадию. Выполните
недостающие проверки, исправьте evidence и повторите переход. Не обходите отказ
ручной правкой YAML. После
`stage_transitioned` используйте полную текущую проекцию Work из ответа. Если её
нет, а также после неопределённого результата, переподключения или параллельных
изменений вызовите `pf.work.state`. Повторное чтение того же состояния не нужно
после каждого успешного перехода. Продолжайте до `action: run_completed`, а не
только до первого успешного перехода.

[Пример структуры state и перехода на английском](../../concepts/declarative-process-execution.md).

Последний успешный transition завершает Assignment и Run, пишет summary и
handoff, обновляет projection и публикует события `process.stage.*`.

Ручные `run-create` и `task-complete` относятся к отдельному
[batch-сценарию](../getting-started/task-batch-workflow.md). Для завершения
управляемой Work не добавляйте `run-complete` или `run-summary`: завершением
владеет последний переход. Жизненный цикл сессии хоста остаётся отдельным.

## Подсказки по evidence

Общая проекция Work для CLI и MCP содержит дополнительное поле
`evidence_guidance`. Для активной Work с валидным закреплённым контекстом и
готовыми разрешениями оно показывает невыполненные требования, допустимые kind,
поля идентификатора и статусы, примеры и объяснения существующих диагностик.
`transition_template` сохраняет возвращённые селекторы. Замените заполнители
реальными данными и передавайте свидетельства после выполнения работы. При
нескольких outcome выберите один из предложенных. Для завершённой, невалидной
или заблокированной Work шаблон действия не выдаётся.

Ниже приведены условные ID; берите идентификаторы из своего ответа PF:

| Требование | Корректная запись | Некорректная запись и причина |
| --- | --- | --- |
| Artifact `change` | `{"kind":"artifact","artifact_id":"change","status":"ready"}` | `{"kind":"gate","id":"change","status":"approved"}`: неверный kind. |
| Input `brief` | `{"kind":"input","input_id":"brief","status":"present"}` | `{"kind":"input","id":"brief-typo","status":"ready"}`: неверный ID. |
| Evidence `review` | `{"kind":"attestation","evidence_id":"review","status":"ready"}` | `{"kind":"attestation","artifact_id":"review","status":"ready"}`: ID указан не в том поле. |
| Gate `build-ready` | `{"kind":"gate","gate_id":"build-ready","status":"approved"}` | `{"kind":"gate","id":"build-ready","status":"pass"}`: недопустимый статус. |
| Обоснованное исключение | `{"kind":"gate","gate_id":"optional-check","status":"not_applicable","reason":"Интерфейс не менялся","evidence":["reviewed-diff"]}` | Запись без reason или с пустым списком подтверждающих evidence отклоняется. |

Artifact, input и required evidence принимают статусы `ready`, `present`,
`passed`, `approved` и обоснованный `not_applicable`. Gates принимают `passed`,
`approved` и обоснованный `not_applicable`. Для artifact используются `artifact_id`
или `id`; для input подходят также записи artifact и поля `input_id`,
`artifact_id` или `id`; для required evidence — kind `attestation`/`evidence` и
`evidence_id` или `id`. У gate непустой `gate_id` имеет приоритет перед `id`.
Готовность определяет последняя совпавшая запись, в том числе неуспешная.
Inputs и входные gates используют накопленные evidence, выходы и выходные
gates — evidence текущей стадии. Дополнительная или несовпавшая запись может
сохраниться, но не удовлетворить требование. `unmatched_evidence` объясняет
несовпадение и не вводит нового отказа.

`conditional_next_entry_gates` берётся из закреплённого процесса для каждого
доступного outcome. Эти gates уже могут быть подтверждены накопленными evidence;
подсказка не оценивает их готовность и не выбирает маршрут. Если переход вернул
`entry_gate_evidence_missing`, используйте соответствующий условный пример.
Обязательный текст передачи работы передавайте в `transition.notes`.

В существующем контракте evidence поле `path` необязательно. Если оно указано,
нужен существующий обычный файл внутри разрешённого корня проекта. Несуществующий
`missing.md`, выход через `../outside.md`, каталог или абсолютный путь не подходят.
PF вычисляет хеш файла сам и заменяет переданный `sha256`. Отсутствие сохранённого
хеша или изменение файла после подачи оставляет требование невыполненным.
Проверьте и повторно подайте реальный файл: подсказки не исправляют и не принимают
его автоматически. Ошибки нормализации сохраняют прежние коды блокеров;
`evidence_guidance.request_errors` добавляет объяснения и индексы записей.

Подсказки не читают файлы, не расширяют разрешения и не меняют решение о принятии
evidence или переходе. Их словарь совпадает с правилами проверки готовности.

## Рекомендательная проверка артефактов

При новой подаче evidence можно указать текстовый артефакт и объявить требования:

```json
{
  "kind": "artifact",
  "artifact_id": "test-report",
  "status": "ready",
  "path": ".pf/artifacts/current-test-report.md",
  "authoring": {
    "required_sections": ["Итог", "Результаты"],
    "placeholders": ["{{result}}"]
  }
}
```

PF сохраняет `evidence.authoring_review`: замечания, охват проверки и хеш
проверенных байтов. Переданные клиентом результаты такой проверки заменяются.
Для Markdown, обычного текста и rST размером до 1 MiB проверяются строгий UTF-8,
известные заполнители шаблона артефакта и явно объявленные маркеры, наличие и
заполнение обязательных Markdown-разделов, простые встроенные Markdown-ссылки.
В каждом списке объявления допускается до 32 непустых строк длиной до 200
символов; некорректное объявление получает предупреждение. Отсутствующий раздел
и оставленный `<summary>` обнаруживаются. Код в ограждённых/отступных блоках и
между обратными кавычками исключается из текстовых эвристик; раздел с одним
кодом может считаться заполненным. Язык текста и доля ASCII не определяют качество.

Для локальных ссылок проверяется только существование цели внутри разрешённого
корня проекта. Содержимое целей не читается, запросы к внешним URL не выполняются.
На запись проверяется не более 64 простых встроенных ссылок и сохраняется до 32
замечаний. `limits_reached` сохраняет причины ограничения, даже если список
замечаний усечён. Полный синтаксис Markdown, внешние URL, якоря и ссылки через
отдельные объявления этим не валидируются. Для неподдерживаемого формата, большого,
нечитаемого или изменившегося во время проверки файла явно указывается пропуск
или неполный охват; успешная содержательная проверка не заявляется.

Структурная проверка `not_applicable` сохраняется: нужны причина и подтверждающие
evidence. Конкретное объяснение принимается. Голые `N/A`, `not_applicable` или
`не применимо` получают просьбу пояснить контекст; известные незаполненные маркеры
причины/подтверждения также отмечаются. Это предупреждения, а не решение об
истинности объяснения. Прежние правила пути, хеша и статуса продолжают действовать;
документ, целиком состоящий из голого N/A под заголовком, также получает
предупреждение. Конкретное объяснение с evidence не считается такой отпиской;
замечания по тексту не создают новых блокеров перехода.

Общая проекция CLI/MCP `authoring_review` показывает сохранённые наблюдения для
`current_stage` и `last_completed_stage` с ID стадии и индексом evidence. Поэтому
замечания видны и после успешного перехода. Проверяется только новая подача;
чтение state не перечитывает и не переписывает исторические файлы или evidence.
Старые записи без проверки имеют статус `not_recorded`. Хеш относится к байтам
во время подачи; актуальность файла по прежнему определяют отдельные проверки
свежести. Учтите замечания перед подачей исправленной версии: автоматическая
проверка не доказывает смыслового качества результата.

## Внутренние итерации и вложенная работа

Один Run может включать повторные исследования, уточнения домена и архитектуры,
согласованные редакции плана, реализацию и локальные проверки цельного результата.
Это не требует перехода после каждой правки или итоговой приёмки и публикации
после каждой итерации. Используйте только действия и outcomes текущего контракта:
это описание не добавляет обратных маршрутов или разрешения редактировать файлы.
См. [границы Run и итерации](process-definition-run-task-iteration.md).

Крупное поручение воркеру может проходить собственный полный процесс, вложенный
в родительский цикл. Основной агент проверяет и интегрирует его результат;
завершение дочерней работы не завершает и не публикует родительскую автоматически.

## Результаты исполнителя и продолжение работы

Исполнитель может получать [подготовленный вход](prepared-input.md) без MCP.
Сбор результата сохраняет основной управляемый Run, стадию Assignment и
неизменяемую капсулу. Основной агент проверяет результат и передаёт
свидетельства для перехода стадии. Старые задачи имеют отдельный совместимый
путь завершения; повторный сбор и восстановление квитанции не должны
дублировать события завершения.

Смена настроек исполнителя или соединения не разрешает менять цель, снимок и
набор ресурсов. После подключения сверяйте идентичность Work, текущую стадию
и принятые свидетельства с долговечными файлами. Обязательства стадии выводятся
из закреплённого процесса и текущего назначения без перезаписи капсулы.
См. [контекст Work](work-context.md) и [ресурсы Work](work-resources.md).
