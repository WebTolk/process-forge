# Необязательная диагностика

Диагностические записи ProcessForge дают дополнительную информацию об операции или локальной ошибке. Они не являются фактами процесса или аудиторскими доказательствами и не заменяют обязательный журнал событий. Режим `off`, отключённый приёмник или потеря диагностической записи не должны отключать обязательное событие, менять результат операции или скрывать явную ошибку.

## Настройка

Команда `pf diagnostics-configure --project-root . --profile diagnostic --duration 120`
показывает план смены профиля. Добавление `--apply` атомарно сохраняет его
в существующем формате `.pf/diagnostics.json` v1. Можно выбрать один точный
`--run-id` или `--session-id`; без них меняется уровень проекта. Прочие настройки
и области сохраняются. Блокировки действуют и внутри редактируемого уровня;
ошибочные, слишком большие файлы и ссылки отклоняются. Подробные профили
`diagnostic`/`trace` действуют 1..900 секунд, по умолчанию 600; прочие очищают
срок выбранного уровня. План показывает приоритеты окружения и аргументов,
не создаёт журналов, блокировок или каталогов. Применение сериализует изменения.
Работающий процесс использует уже прочитанную конфигурацию до следующего
штатного обращения к ней; отдельного протокола удалённого переключения нет.
Обязательные события процесса сохраняют прежнее поведение.

Настройки проекта находятся в `.pf/diagnostics.json`; их версия 1 описана в [`diagnostics.schema.json`](../../../schemas/diagnostics.schema.json). Минимальный пример:

```json
{
  "schema_version": 1,
  "profile": "normal",
  "sink": "jsonl",
  "work": {
    "run-example": { "components": ["mcp", "context"] }
  },
  "sessions": {
    "session-example": { "threshold": "warning" }
  }
}
```

В `work` ключом служит точный идентификатор run, в `sessions` — точный идентификатор сессии. Каждое значение задаёт такой же набор параметров, как настройки проекта, включая `locked`. Порядок: значения по умолчанию, проект, соответствующая Work, соответствующая сессия, JSON из `PF_DIAGNOSTICS`, затем параметры команды. `locked` запрещает последующим уровням менять указанное поле. Числовые пределы можно только ужесточать относительно уже действующего уровня. При неверной конфигурации используется безопасный профиль `quiet` с приёмником `stderr`; ошибка конфигурации показывается в диагностике, не меняя результат операции.

Профили задают детализацию по умолчанию: `quiet` — `warning`; `normal` — `info`; `diagnostic` и `trace` — `debug`; `off` отключает необязательные записи. Порог включает выбранную серьёзность и все более серьёзные уровни.

| Серьёзность | Значение Python |
|---|---:|
| debug | 10 |
| info | 20 |
| notice | 25 |
| warning | 30 |
| error | 40 |
| critical | 50 |
| alert | 60 |
| emergency | 70 |

Стандартные уровни Python сохраняют свои значения; для `notice`, `alert` и `emergency` действует соответствие ProcessForge. Настройка глобального root logger Python не выполняется. Пустой список `components` означает все инструментированные компоненты; непустой ограничивает сбор указанными именами. Приёмники: `jsonl`, `stderr`, `both`, `none`.

Подробный сбор (`diagnostic`, `trace` или порог `debug`) требует абсолютного времени `expires_at` в формате ISO 8601 с часовым поясом, не более чем на 15 минут вперёд. Допускаются `Z` и числовые смещения, например `+00:00`; при проверке срок сравнивается как момент времени UTC. Параметры вызова, включающие детализацию, получают ограниченный временный срок автоматически. По истечении времени или лимита подробных записей режим возвращается к `normal`. Не сохраняйте в конфигурации проекта постоянно действующее будущее время: задавайте срок на ограниченное исследование. `PF_DIAGNOSTICS` содержит JSON-объект параметров и применяется на уровне текущего вызова; параметры CLI также являются последним уровнем.

Жёсткие пределы по умолчанию, которые можно только уменьшить: запись 16 КиБ, строка 2 048 символов, глубина 6, 32 элемента контейнера, 8 кадров стека, 32 span, 1 МиБ на JSONL-файл, 8 МиБ суммарно, 8 файлов вместе с активным, хранение 7 дней и 10 000 подробных записей. Входной файл конфигурации ограничен 64 КиБ. Пределы записи, файла и общей квоты должны быть совместимы. По умолчанию отладочные записи не прореживаются; `sample_every` можно увеличить.

## Интерфейс CLI

Предусмотренные общие параметры указываются перед подкомандой:

```text
pf --diagnostic-profile diagnostic --diagnostic-threshold debug --diagnostic-components mcp,context --diagnostic-sink both diagnostics-status --project-root .
pf diagnostics-status --project-root . --run-id example-run --session-id example-session
pf diagnostics-export --project-root . --output diagnostics-export.json --run-id example-run
```

Фильтры запуска и сессии у `diagnostics-status` необязательны. Экспорт также поддерживает `--request-id`, `--since` и `--until`; подставьте нужные идентификаторы и время, а для результата выберите новый файл.

Эти команды реализованы в исходном дереве. Их наличие всё равно зависит от фактически используемого дистрибутива Core: файлы исходного checkout сами по себе не доказывают, что установленная сборка содержит ту же реализацию. При сравнении записывайте идентификатор источника/сборки. Это руководство не предписывает обновление установки или перезапуск.

`diagnostics-status` предназначена только для просмотра эффективных значений и их источников, блокировок, ошибок настроек, срока подробного режима и ограниченных счётчиков здоровья текущего процесса. Каждая сохранённая каноническая запись также содержит снимок счётчиков на момент записи. `diagnostics-export` читает только диагностические JSONL ProcessForge, фильтрует записи по request/run/времени, санитизирует локальный пакет и создаёт новый файл без перезаписи существующего. Команда не исправляет контекст, не перезапускает службы и не отправляет данные наружу. Перед передачей проверьте получателя и содержимое санитизированного пакета.

При неверной конфигурации сбор закрывается в режиме `off`; в stderr может выводиться фиксированное несекретное уведомление о состоянии, чтобы оператор заметил fallback. Оно не содержит отвергнутых значений и не обходит заблокированный приёмник или политику приватности.

## Приватность и ошибки приёмников

По умолчанию диагностика не записывает prompt, исходную нагрузку запроса, переменные среды и содержимое файлов. Ключи и значения, похожие на секреты, редактируются до передачи приёмникам. Локальная запись может содержать локальные рабочие пути; при экспорте абсолютные пути заменяются отметкой о приватном пути. Размер и глубина контекста ограничены. Экспорт ограничен 4 МиБ входных и выходных данных и 2 000 записями; повреждённые или слишком большие записи отклоняются либо отмечаются как усечённые в манифесте.

Частные JSONL-файлы хранятся в `.pf/runtime/diagnostics/`; также можно выбрать `stderr`. Счётчики записей, фильтрации, потерь, усечения, ошибок сериализации/приёмника и истечения срока детализации относятся к текущему процессу. Каждая сохранённая каноническая диагностическая запись содержит снимок счётчиков. При потере важной необязательной диагностики выводится ограниченное предупреждение в stderr. Оно не заменяет обязательный журнал процесса: имена событий, значения серьёзности, дедупликация и обработка ошибок этих журналов остаются отдельным контрактом.

`PF_CODEX_HOOK_DEBUG=1` включает временный подробный профиль hook-диагностики. В stderr выводятся канонические санитизированные диагностические записи; протокольный stdout hook остаётся без изменений. Исходная нагрузка hook и его полный результат не печатаются.
