# Garage Core

Garage — входной уровень ProcessForge для проекта с контекстом `.pf/`.
Он помогает человеку и агенту понять правила проекта, найти разрешённые знания
и проверить доступ до начала изменений. Work закрепляет процесс, границы работы,
свидетельства и передачу результата, чтобы работу можно было проверить и продолжить.
Перед настройкой см. общие [требования](../requirements.md).

## Три уровня

1. **Garage: чтение контекста.** `pf.context` показывает проект, актуальность
   снимка, разрешённые ресурсы и текущую работу. `pf.search` ищет в выбранном
   корпусе, `pf.resolve` разрешает выбранный ресурс перед открытием.
2. **Управляемая работа.** `pf.work.start` закрепляет определение и версию
   процесса, снимок и неизменяемую капсулу Assignment. `pf.work.state` показывает
   текущую стадию, обязательства, артефакты, проверки и допустимые outcomes.
   `pf.work.transition` принимает outcome и evidence; следующую стадию выбирает PF.
3. **Forge: координация.** Runtime, Agent Ledger, хуки, Director и аренды записи
   добавляют управление исполнителями и телеметрию по требованиям проекта.
   Наличие сессии или запущенного Runtime само по себе не переключает режим.

## Порядок работы

1. Прочитайте корневой `AGENTS.md`; `.pf/AGENTS.md` — явный резервный вход для
   проекта, который ещё не перенёс инструкции.
2. Вызовите `pf.context` с `project_root`. Без MCP используйте существующий CLI
   и проверьте снимок командой `project-context-check`. При отсутствующем,
   устаревшем, неверном или заблокированном контексте остановите зависимую работу.
3. Для знаний проекта используйте `pf.search`, затем `pf.resolve` перед открытием
   ресурса. Выполните разрешённый анализ.
4. Для новой цели вызовите `pf.work.start`. Для продолжения выберите и возобновите
   точное [продолжение Work](work-continuation.md); новая формулировка цели
   не является способом выбрать прежнюю работу.
5. Сохраните возвращённые `run_id`, `assignment_id` и `context.id`. Без привязанной
   сессии передавайте эти селекторы в каждый вызов состояния и перехода Work.
   Сверьте Assignment и неизменяемую капсулу: идентичность, область чтения/записи,
   разрешённые действия и обязательства. Для ресурсов Work используйте
   `pf.work.search` и `pf.work.resolve` с точными селекторами.
6. Выполните обязательства текущей стадии и передайте outcome и evidence в
   `pf.work.transition`. Используйте возвращённое полное состояние; после
   переподключения или неопределённости перечитайте `pf.work.state`.
7. Повторяйте до `action: run_completed`. Последний переход автоматически
   сохраняет summary и handoff; завершение Run не закрывает сессию приложения.

При `process_choice_required` выберите один из предложенных `process_id` и
повторите start. `default` — рекомендация; при неоднозначности нужна явная воля
пользователя. Не выбирайте первую или самую новую Assignment.

Ручные `run-create`, `task-create`, `task-complete` относятся к расширенному
[batch-сценарию](../getting-started/task-batch-workflow.md). Их не нужно добавлять
к обычному циклу управляемой Work. Примеры evidence и восстановления приведены
в [декларативном исполнении](declarative-process-execution.md).

## Поиск и границы доступа

Поиск сообщает `ready`, `empty`, `stale` или `blocked`. Свежий `empty` означает
отсутствие документов в разрешённом корпусе: разрешение выбранного профиля
проекта и старт Work при этом могут оставаться доступны. Общий SQLite-индекс
принадлежит workplace и строится из зарегистрированных пакетов и шаблонов.
Выбранный локальный профиль проекта может разрешаться без попадания в этот индекс.

Доступный каталог знаний — диагностические сведения. Только выбранные ресурсы
могут участвовать в поиске и разрешении. Метаданные ресурса не дают права читать
его содержимое. Для больших деревьев исходников применяется навигация по
метаданным, если манифест не разрешает ограниченный полнотекстовый набор.
Поиск не переходит к обходу всего диска, домашнего каталога или веба.

Чтение Work пересекает закреплённые ресурсы, текущие права и ограничения стадии.
Готовность общего индекса не доказывает полноту знаний конкретной Work.
См. [ресурсы Work](work-resources.md) и [контекст Work](work-context.md).

## Runtime, MCP и передача исполнителю

Необязательный app-server запускает планировщик Runtime для workplace.
Отдельный stdio-процесс MCP запускается и управляется приложением-хостом.
Файловая работа Garage не требует app-server, хуков или Ledger-сессии.
Обычный агент не устанавливает и не перезапускает инфраструктуру для получения
контекста. См. [модель Runtime](runtime-model.md) и [MCP](runtime-mcp.md).

Исполнитель может получить [подготовленный вход](prepared-input.md) без MCP.
Сбор его результата не продвигает основную Work: основной агент проверяет
результат и передаёт evidence. После смены исполнителя сверяйте точную идентичность
с сохранённой передачей работы; ни handoff, ни рекомендация следующей работы
не разрешают запуск внешней сессии или изменение инфраструктуры.
