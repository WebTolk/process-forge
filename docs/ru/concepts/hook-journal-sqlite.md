# Журналы проекта в SQLite

Журналы сохраняют приём хуков и факты, нужные проверкам Work. Это приватные
рабочие данные, отдельные от публичных артефактов и отчётов. Требования к SQLite
и хранилищу приведены в общих [требованиях](../requirements.md).

Каждый проверенный проект владеет двумя локальными базами:

| Файл | Владелец и назначение |
| --- | --- |
| `.pf/runtime/events/events.sqlite3` | `ProcessEventJournal`: уникальные ID приёма, необязательная история событий, ожидающая обработка хуков, последние факты проверок |
| `.pf/runtime/agent-events/hooks.sqlite3` | `RawHookJournal`: исходные идентификаторы, необязательные данные провайдера, незавершённый вход, результат обработки и карантин |

Соединение открывается на одну операцию. Запись использует WAL, явные транзакции,
`synchronous=FULL` и ограниченное ожидание занятой базы. SQLite последовательно
обслуживает писателей на одном компьютере; отдельный сервер БД не нужен.
Используйте локальное хранилище: WAL не предназначен для общей БД на сетевой
файловой системе нескольких компьютеров. Файлы БД, `-wal` и `-shm` не входят
в поставку. Для резервной копии работающей базы используйте SQLite backup API,
а не копирование одного файла БД.

Уникальность ID обеспечивается SQL. Добавление записи не перечитывает историю
для поиска дубликата. Индексы поддерживают выборку по ID, последней записи и
назначению; страницы используют курсор `after` и `limit` от 1 до 1000.
Пропуски последовательности допустимы: курсор не является номером строки.
Полный обход нужен для явного экспорта, диагностики, миграции или пересборки истории.

Приём сырых данных фиксируется до действий проекта. Между разными владельцами
нет одной общей транзакции: стабильные ID и сохранённый незавершённый вход
позволяют повторить обработку. Отложенную отправку проектным хукам повторяет
повторный приём либо такт Runtime. Миграция не добавляет запуск внешних команд
или сетевых API.

`logging.raw_hooks` и `logging.events` наследуют настройки workplace и независимо
переопределяются проектом. Отключение истории сохраняет минимальные ID,
незавершённую обработку и последние факты проверок. Оно не останавливает Work
или доставку сообщений. Текст разговора хранит отдельный владелец стенограммы;
история событий ссылается на него. Настройки не стирают прежние данные и не
обещают физическое безопасное удаление. См.
[настройки журналов](../../authoring/workplace-configuration.md#project-history-and-raw-hooks).

## Какие журналы остаются NDJSON

Миграция затрагивает две базы проекта, перечисленные выше. Независимые владельцы
сохраняют свои форматы:

| Область | Файл | Назначение |
| --- | --- | --- |
| Workplace | `runtime/events/events.ndjson` | События ресурсов и подготовки материалов |
| Workplace | `runtime/agent-ledger/sessions.ndjson` | История сессий Agent Ledger |
| Проект | `.pf/runtime/telemetry/<session-id>.ndjson` | Телеметрия сессии |
| Проект | `.pf/runtime/chat/transcripts/session-<identity-digest>.ndjson` | Приватные сообщения разговора |

Чтение стенограмм поддерживает и прежние файлы с именем сессии. Не передавайте
эти независимые потоки мигратору проектных журналов и не переименовывайте их
в SQLite. См. [телеметрию](session-telemetry.md), [чат](chat-relay.md) и
[ресурсы workplace](workplace-resources.md).

## Временная утилита миграции

`tools/migrate-hook-journals.py` переносит прежний `events.ndjson` проекта и
только его сырые записи из общих сегментов
`<workplace>/runtime/agent-events/raw/v1/` либо прежнего локального каталога
проекта. Сохраняются ID, оболочки событий, порядок источника внутри каждого
журнала и ссылки на исходные записи. Файлы читаются потоком; SQL проверяет
повторные и конфликтующие ID. Исходные файлы не переписываются и не удаляются.

Перенос выполняет оператор: штатно остановите прежних писателей, сохраните
резервную копию и не запускайте их до готовности обеих баз и перехода всех
потребителей на новый Core. Утилита не останавливает службы и не обновляет
установку. Проверки хешей, состава источников, количества строк и целостности
не могут предотвратить запуск старого писателя после завершения переноса.

```sh
python -B tools/migrate-hook-journals.py --project-root <project-root> --workplace <workplace-root>
python -B tools/migrate-hook-journals.py --project-root <project-root> --workplace <workplace-root> --apply
```

Без `--apply` показывается план; базы проекта не создаются. Неверные строки
блокируют применение. После просмотра диагностики можно явно пропустить
повреждённые строки через `--skip-invalid`; конфликты идентичности всегда
останавливают перенос. Отчёты содержат приватные пути и хранятся в приватных
свидетельствах оператора.

Импорт фиксирует барьер `importing` в обеих базах. Обычное чтение и запись
отклоняют незавершённый импорт. Исправьте источник или окружение и повторите
ту же команду: совпадающие ID не вставляются повторно. Оба владельца получают
`ready` только после проверки. После переключения оставьте старые файлы
замороженными: новые записи в них не копируются в SQLite автоматически.

Утилиту можно удалить после переноса нужных проектов. Изменение исходников,
перенос реальных журналов и переподключение Runtime/MCP — отдельные проверки.

Справка: [WAL](https://sqlite.org/wal.html),
[планирование запросов](https://sqlite.org/queryplanner.html),
[UPSERT](https://sqlite.org/lang_upsert.html),
[Python sqlite3](https://docs.python.org/3/library/sqlite3.html).
