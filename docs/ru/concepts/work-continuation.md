# Продолжение существующей работы

Для возобновления используйте `continuation`. Новая формулировка цели в `work-start` не выбирает прежний Work: совместимое сопоставление учитывает только регистр и пробелы. Продолжение не создаёт Run, assignment или капсулу и не расширяет разрешения.

1. Получите актуальный `pf.context`. Вызовите `pf.continuation.status` без идентификатора для просмотра кандидатов. Несколько кандидатов дают `choice_required`, отсутствие — `not_found`; новая работа не создаётся.
2. Выберите точные run, assignment и context. Передайте их в `pf.continuation.create` вместе с `continuation_id`. Дополнительно доступны `expected_artifacts`, `handoff_id` и `instruction`. По умолчанию выполняется предварительная проверка; только `apply: true` сохраняет ссылку v2 с контрольной суммой капсулы.
3. `pf.continuation.status` с идентификатором разделяет готовность ожидания и самой работы. Ожидаемые файлы должны существовать внутри проекта, handoff — иметь статус returned/finalized. Проверяются identity, неизменность входов, разрешения, актуальный контекст, стадия и ресурсы.
4. `pf.continuation.resume` повторно проверяет Work под блокировкой Run и возвращает `selectors` и `work_state`. При наличии идентификатора сессии выбор закрепляется за ней. Без него ответ содержит `selection: explicit_selectors_required`: передавайте полученные run/assignment/context в последующие `pf.work.state` и `pf.work.transition`. Общего неявного выбора для всех сессий нет.

Эквивалентные команды CLI:

```text
pf continuation-status --project-root . --json
pf continuation-create --project-root . --id resume-feature --run feature-run --assignment feature-task --context-id feature-task-capsule --apply --json
pf continuation-resume --project-root . --continuation resume-feature --json
pf work-state --project-root . --run feature-run --assignment feature-task --context-id feature-task-capsule --json
```

Повторное возобновление идемпотентно. Повреждённая или завершённая работа, активный worker или lease вызывают отказ без подстановки другой задачи. Новая запись в очереди не вытесняет явный выбор сессии. Сначала сохраняется запись выбора, затем производная отметка resumed; после сбоя повтор восстанавливает отметку с новой проверкой Work, не выполняя переход стадии повторно. Частичный результат явно обозначается как `selection_committed`, `marker_recovery_required: true`.

Старые записи v1 сохраняют логику ожидания и явно возвращают `work_resumed: false`, `legacy_binding_required`. Для реального продолжения создайте отдельную точную ссылку v2; автоматической миграции нет. Совместимое создание Work без scope остаётся доступным, но `work_state.execution_readiness` показывает недостающие разрешения, а исполнимое продолжение блокируется. Явные read-only назначения поддерживаются.

## Отмена

`pf.work.cancel` / `pf work-cancel` принимает точные run, assignment, context, checksum капсулы и причину. Необязательные evidence должны ссылаться на существующие файлы проекта. По умолчанию выполняется предварительная проверка, запись требует явного apply. Отменяется только указанное назначение; другие активные назначения Run сохраняются.

Активный или подготовленный worker и действующая lease блокируют отмену. Процессы не останавливаются, leases не отзываются. Журнал намерения позволяет повторить тот же запрос после частичного сбоя; до восстановления переходы Run блокируются. Неожиданные параллельные изменения останавливают восстановление. Капсула, process pin и история стадий сохраняются. Отмена не означает успешного завершения, удаления данных или их отката.

Проверки исходников, архива, установленного Core и подключённого host учитываются отдельно. Изменение исходников не перезагружает работающий MCP.
