# Владение выполнением в Linux

Linux использует настоящий user/PID namespace и сохранённые pidfd процессов
carrier/init. Process group не доказывает отсутствие всего дерева. Смерть init
завершает оставшиеся процессы namespace, включая потомков с отдельной сессией.
Windows продолжает использовать отдельный Job с запретом breakaway.

Обычный вложенный запуск наследует проверенный внешний namespace и возвращает
обычный `Popen` без отдельного владельца. Вложенная попытка с долговечным
token/receipt остаётся запрещённой: `linux_nested_owned_launch_unsupported`.
Контроллер долговечной попытки должен работать в поддерживаемом контексте procfs
собственного PID namespace. Формат долговечных v1 receipts не расширяется.

Для временного шага потребителя `spawn_owned(argv, independent=True)` запрашивает
новый независимый user/PID namespace, в том числе внутри проверенного внешнего
namespace. До GO требуются реальное создание ядром и проверка сохранённых точных
pidfd carrier/init, birth, namespace и связи родитель/потомок. Остановка нового
владельца затрагивает только новый namespace и ждёт его завершения; внешний
владелец продолжает работать. Сам флаг не предоставляет полномочий.

Режим временный: явные `token`, `receipt_path` или `identity`, включая пустую
identity, отклоняются как `linux_ephemeral_durable_inputs_unsupported`.
Идентификатор `linux-pidns-ephemeral-v1` не принимается долговечным reopen и
проверкой process identity. Поддержка долговечного восстановления не заявляется.
Сохраняйте `process.native_job` до завершения cleanup. `close()` освобождает
дескрипторы и сам по себе не останавливает работающий namespace.

Procfs может принадлежать предковому PID namespace. Helper получает PID для
proof-путей из fdinfo настоящего сохранённого pidfd. Контроллер переводит известный
procfs PID init через `NSpid` и свою глубину namespace, открывает pidfd по локальному
PID и проверяет точный procfs PID, birth и namespace до GO. Скрытый, некорректный,
переиспользованный, недоступный PID, соседний namespace или противоречивые
наблюдения запрещают запуск до входа target. Поиск PID и process groups не
создают права сигнализации.

`Popen.pid` остаётся локальным PID, а `wait()` ждёт carrier до завершения всех
потомков. Чтобы получить более ранний результат launcher, адаптеру нужен отдельный
закрытый канал результата; затем он останавливает сохранённого владельца и ждёт
подтверждённого завершения дерева до удаления fixture. На Windows этот же флаг
сохраняет существующее поведение отдельного Job; другие неподдерживаемые платформы
отклоняют независимый запрос.

Нужны Linux с разрешёнными user/PID namespaces, читаемый procfs и Python 3.11+
с pidfd API. Отказ ядра, seccomp/AppArmor или ошибка доступа не считаются успехом.
Это гарантия времени жизни процессов, а не изоляция файловой системы или сети.
Квалификация требует настоящих Windows/Linux проверок; skip и недоступный backend
не заменяют обязательные сценарии. Полное описание долговечного выполнения:
[English](../../concepts/linux-owned-execution.md).
