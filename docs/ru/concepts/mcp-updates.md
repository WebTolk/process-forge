# MCP-соединения и обновление Core

Stdio-вход — `tools/pf_runtime/mcp_server.py`. Транспортный процесс сохраняет
каналы host и для каждого backend-запроса запускает фиксированный native-вход в новом
дочернем процессе. Совместимое обновление Core обслуживает следующий запрос без
замены соединения host. Транспорт хранит подписки discovery, но не состояние
Work, разрешения или исполняемый бизнес-Core.

Каждый child заново проходит native publication/admission, проверку запроса и
существующие привязки project/session/Work. Новый процесс сам по себе не
доказывает storage safety. Native adoption, publication identity, epoch и реальное
исключение писателей остаются у прежних владельцев. Неполная или несовместимая
публикация может отказать в запросе при работающем транспорте.

На MCP ping отвечает сам транспорт. Это подтверждает его работоспособность, но
не готовность Core или storage. Некорректный протокол отклоняется до business Core
dispatch.

Заявленная версия MCP остаётся `2024-11-05`. Доступны прежние typed tools и
ресурс метаданных `pf://core/identity`. Ресурс сообщает loaded identity
исполняющего Core, включая явный unknown/partial при недоступных метаданных
дистрибутива. Метки версии не доказывают целостность payload. Другие URI не
разрешают чтение файловой системы.

После ответа backend транспорт сравнивает fingerprints каталогов tools/resources.
Для уже запрошенного клиентом каталога он отправляет
`notifications/tools/list_changed` или `notifications/resources/list_changed`, а
для изменившегося ресурса с активной подпиской —
`notifications/resources/updated`. Изменение обнаруживается при следующем запросе;
idle polling отсутствует. Перед использованием изменённых tools клиент должен
обновить callable schemas. Поведение настоящего host проверяется отдельно от
wire-клиента.

При сбое backend результат mutation может оставаться неизвестным. Транспорт
возвращает tool error с `outcome: unknown` и `automatic_retry: false` и не повторяет
запрос. Перед восстановлением caller проверяет точный durable Work или receipt
операции. Stderr backend не передаётся модели. Следующий явный запрос может
обратиться к восстановленному backend через те же каналы.

Выполнение backend ограничено watchdog в 120 секунд; host может задать
--backend-timeout-seconds. Timeout также означает неизвестный исход и не разрешает
повтор mutation или остановку воркеров с отдельным владельцем. Ответы разделяются
только LF; Unicode-разделители строк внутри JSON сохраняются как данные.

Внутренний вход `--backend-request` и метаданные результата
`processforge/backend` образуют транспортный контракт версии 1. Это интерфейс
фиксированного дистрибутива, а не выбор executable моделью или новый grant.
Совместимые выпуски Core сохраняют согласованный протокол и ранее опубликованные
callable contracts. При необходимости нового транспортного контракта требуется
явное обновление host connection. Bridge не переводит произвольные поколения MCP
и не перезагружает Python-модули на месте.

Обслуживание установки PF Core и обновление пакетов имеют самостоятельные
жизненные циклы. Обычное обновление пакета не запрашивает workplace maintenance и
не требует паузы всех проектных агентов. Package locks, verification, metadata и
rollback сохраняют прежних владельцев. Пакетная операция соблюдает уже действующий
native fence для общей области. Ни обновление каталога, ни package update не
меняют immutable capsule и закреплённые разрешения активного Work.

Source integration tests используют настоящий stdio-вход и изолированные
consumer-дистрибутивы: меняют исполняемую логику Core, проверяют UTF-8 каталога,
подписки, сбой backend и session mismatch. Они не заменяют приёмку sealed native
publication, установленного Core и настоящего host.
