# Корень проектного процесса

Каноническое состояние процесса ProcessForge хранится в `.pf/`. В новых и явно
мигрированных проектах корневой `AGENTS.md` содержит полный минимальный контракт
входа K для выбранного загрузчика инструкций клиента. Это не ссылка на START
и не перенос состояния процесса в корень репозитория.

```text
project/
  AGENTS.md
  .pf/
    AGENTS.md
    agent-entry.json
    process-forge.yaml
    process-forge.local.yaml
    hooks.yaml
    contexts/
    assignments/
    artifacts/
    logs/
    handoffs/
    reviews/
    runtime/
```

Корневая и скрытая проекции содержат одинаковый K; `.pf/AGENTS.md` дополнительно
содержит расширенные инструкции. `.pf/agent-entry.json` фиксирует идентичность
контракта и проекций. START больше не нужен и автоматически не создаётся.
Существующие файлы остаются нетронутыми; отсутствие START не влияет на
готовность, doctor и repair.

В старом проекте без корневого входа явно читайте `.pf/AGENTS.md` до применения
проверенного [плана миграции](agent-entry.md). Статус `legacy_or_unmigrated`
описывает вход отдельно от свежести контекста и готовности проекта. Проверка
и просмотр стартового промпта сами проект не мигрируют.

В репозитории, который намеренно хранит свой процесс PF, публикуйте корневой
`AGENTS.md`, `.pf/AGENTS.md`, `.pf/agent-entry.json`, публичный манифест,
конфигурацию hooks, снимки контекста и проверенные артефакты. Сохраняйте текст
пользователя вне управляемых секций. Секреты и локальные абсолютные пути туда
не входят. Игнорируйте `.pf/process-forge.local.yaml`, `.pf/runtime/`,
`.pf/private-notes/` и `.pf/cache/`.

Если `.pf/process-forge.yaml` отсутствует, используйте явное подключение проекта:

```text
pf project-onboard --project-root <project-root> --workplace <workplace-root> --type <project-type> --apply
```

`init-project` сохраняется как совместимое имя команды. Наличие K и соблюдение
его внутреннего предела 4096 байт не подтверждают доставку клиенту или
соблюдение суммарного лимита инструкций. См. [политику совместимости](agent-entry.md).
