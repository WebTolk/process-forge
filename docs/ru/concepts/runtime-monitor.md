# Локальный монитор Runtime

`pf monitor` показывает состояние существующего workplace Runtime и работает
только на чтение. **Q**, **Esc** и **Ctrl+C** закрывают монитор; сервер продолжает
работу. Команда не запускает, не останавливает, не чинит и не устанавливает службы.

Запуск из исходной рабочей копии (укажите свой каталог workplace):

```sh
python -B tools/processforge.py monitor --workplace ./workplace
python -B tools/processforge.py monitor --workplace ./workplace --once --ascii --no-color
python -B tools/processforge.py monitor --workplace ./workplace --json
```

В поставке с этой командой доступен и launcher `python bin/pf.py monitor ...`.
Изменение исходников само по себе не обновляет установленный Core.
Список флагов: `pf monitor --help`.

В интерактивном терминале между наблюдениями проходит две секунды;
`--interval` принимает конечное число от 1 до 60. Параллельных опросов и попыток
«догнать» пропущенные обновления нет. При изменении размеров экран перестраивается,
при обычном обновлении перерисовываются только изменившиеся строки. На маленьком
экране первым остаётся состояние Runtime, второстепенные строки опускаются.
Вывод монохромный; поддержан `--no-color`. Флаг `--ascii` или кодировка вывода,
отличная от UTF-8, включает ASCII. Режим Windows VT меняется только для output
handle монитора и восстанавливается при штатном выходе и обработанной ошибке.

`--once`, перенаправленный вывод, отсутствие терминального ввода или неподдерживаемый
терминал дают один обычный текстовый снимок. `--json` всегда выдаёт один JSON-объект
без заставки, цветов и управляющих последовательностей. Unicode в JSON экранирован;
это ограниченная проекция, а не полный dump состояния. Код 0 означает полученное
наблюдение, включая offline/unknown; 2 — неверные аргументы; 1 — внутренний отказ.

## Значение показателей

| Поле | Источник и ограничение |
|---|---|
| Runtime lifecycle | Совпадение lock/state, ограниченная проверка PID и loopback readiness; orphaned/stale не превращаются в ready |
| Health | Сохранённое здоровье Runtime; считается текущим только при ready и свежем state |
| State age | Возраст service.json: старше 15 секунд — stale; отсутствующее, ошибочное или будущее время — unknown |
| Scheduler | Сохранённые результаты jobs и их свежесть; это не проверка живого потока scheduler |
| Registered projects / cached sessions | Записи кэша и его свежесть; не число активных работ или агентов |
| Присутствие сессий | Записи Agent Ledger online/stale/offline с проверкой TTL; online не означает занятость |
| Работники | Записи со статусом running; это не проверка процесса ОС |
| Work | Записи Run in_progress и blocked; blocked не означает ожидание пользователя |
| Аренды | Действующие непросроченные, истёкшие и неактивные записи; конфликты не вычисляются |
| Ожидание пользователя, события, очередь, MCP и hooks | Unknown: общего достоверного контракта пока нет |
| CLI / instance versions | Версия запущенной команды и записанная версия Runtime; совпадение не доказывает равенства сборок |

Readiness может сочетаться с degraded health. Неудачная проба и смена владельца
показывают неопределённость. `/readyz` не даёт криптографического подтверждения
identity; повторное чтение lock/state проверяет локальную согласованность.
Сам по себе существующий PID не доказывает владения Runtime.

Монитор читает только известные service/lock/host-cache files. Service и cache
ограничены 1 MiB каждый, lock — 64 KiB, scheduler — 32 строками. Превышение размера
или ошибка чтения дают причину, например `cache_oversize`, и unknown вместо числа.
Для заполнения пробелов проекты не сканируются. Порог 15 секунд — правило свежести
монитора, не гарантия частоты heartbeat; долгий проход scheduler может его превысить.

Новые сборки Runtime помещают компактный снимок `metrics` в `service.json`
не чаще раза в десять секунд. Снимок привязан к экземпляру сервера и устаревает
через 45 секунд по собственному времени наблюдения. После остановки, смены
владельца, при устаревшем или ошибочном снимке активность неизвестна.
Монитор предпочитает компактные сведения о регистрациях большому историческому
кэшу. Для старого сервера сохраняется прежний режим с неизвестными показателями.

Наблюдение выполняется независимо от планировщика проектов. Оно читает до 4 MiB
существующего кэша регистраций и проверяет наличие манифеста проекта, не собирая
контекст и не воспроизводя события. Долгий проход планировщика не задерживает
публикацию; недоступные проекты оставляют покрытие неполным.

Для каждой группы Core независимо ограничивает обход: 512 элементов, 128 файлов,
128 KiB на запись, 4 MiB суммарно, до 128 проектов и одна секунда с проверкой
между файловыми операциями. Глубина фиксирована; ссылки и junction отклоняются.
Неполное покрытие, ошибочная запись или достигнутый лимит дают `partial`: точные
значения JSON равны null, а `observed` и `>=N` означают нижнюю границу.
Канонические записи сессий имеют приоритет над прежними дублями. При перерисовке
журнал не сканируется. Это не атомарный снимок всех проектов и не гарантия срока
выполнения операции внутри ОС.

Проба готовности использует только числовой loopback HTTP, общий сетевой deadline
0,75 секунды и ограничения размера заголовков/ответа. Redirects, proxy, DNS и tokens
не используются. Проверка PID на Windows ограничена по времени. Чтение файлов
зависит от отзывчивости выбранного локального хранилища. Удалённые адреса не поддержаны.

## Эксплуатационные границы

Не создаются workplace, tokens, projections, журналы и файлы диагностики.
Общие diagnostic flags не включают запись для этой команды. В окно не выводятся
имена проектов из записей, session IDs, prompts, сырые ошибки, token values и
локальные root paths. Для различения окон используются basename выбранного
workplace, проверенные поля версии и PID. Управляющие символы нейтрализуются.

Штатный выход восстанавливает курсор и режим терминала. Принудительное завершение
ОС может помешать восстановлению терминала, но не останавливает сервер.
Управление вынесено в команды `pf server start|run|status|stop|restart` или
`python bin/pf-server.py ...`. `run --console` выводит заставку только в терминале;
`status --json` использует ту же проекцию без записи. Прежние команды `runtime`
совместимы. Команды запускают Python; отдельного нативного файла нет.

`server stop/restart` проверяют поддержку защищённой остановки текущим сервером.
На время проверки сервер приостанавливает приём новых операций. Работающий или
неопределённый работник, выполняющийся запрос или проход планировщика запрещают
остановку. Старый сервер без этой возможности также получает отказ. `--force`
явно выбирает прежний режим. Проверка не блокирует независимые запуски CLI/MCP.
`diagnostics-configure` показывает план смены профиля; запись требует `--apply`.
Закрытие монитора профиль не меняет. Значок в трее, нативная упаковка и удалённый
веб остаются отдельными задачами.
Существующие контракты: [Runtime MCP](runtime-mcp.md), [диагностика](diagnostics.md).
