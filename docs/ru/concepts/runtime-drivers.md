# Рантайм-драйверы

Рантайм-драйвер описывает, как ProcessForge готовит или запускает задачу для
отдельного исполнителя. Это необязательный слой: базовый драйвер `manual`
только создаёт материалы запуска и ждёт, что задачу выполнит человек или
внешняя рабочая среда.

Встроенные драйверы:

- `manual`: готовит состояние запуска и не стартует процесс.
- `generic-shell`: запускает явно указанную программу с аргументами.
- `codex-exec`: запускает исполнителя через Codex CLI с проверенными
  подготовленными входными данными.
- `test-echo-worker`: локальный проверочный исполнитель, который пишет
  ожидаемый отчёт.
- `test-shell-agent`: локальный проверочный shell-агент, который пишет отчёт,
  stdout/stderr, process, heartbeat и exit proof artifacts.

Манифесты драйверов лежат в `templates/runtime-drivers/`, общий реестр - в
`templates/registries/runtime-drivers.yaml`. Проект может добавить локальный
реестр в `.pf/runtime/registries/runtime-drivers.local.yaml`.

Основной агент может вести Work через CLI или MCP. Если задаче нужен отдельный
исполнитель, выберите его драйвер из реестра. Команды ниже выполняются из
подключённого проекта. Выбор модели необязателен. Для запроса каталога используйте
`runtime-driver describe --project-root . --driver <driver-id> --catalog`.
Статус `unsupported` означает, что у драйвера нет каталога, а `unknown` — что
данные каталога получить не удалось.

```bash
python .pf/runtime/bin/pf.py runtime-driver list --project-root .
python .pf/runtime/bin/pf.py runtime-driver validate --project-root . --driver manual
python .pf/runtime/bin/pf.py runtime-driver describe --project-root . --driver test-echo-worker
```

В шаблонах команд разрешены только факты текущего запуска:
`{project_root}`, `{run_id}`, `{task_id}`, `{agent_run_dir}`, `{driver_id}`,
`{capsule_path}`, `{worker_prompt_path}`, `{workspace_access_path}`,
`{expected_report_path}`, `{stdout_path}`, `{stderr_path}`,
`{heartbeat_path}`, `{exit_path}`, `{agent_model}` и
`{agent_reasoning_effort}`. Неизвестный placeholder считается ошибкой
валидации.

ProcessForge всегда добавляет служебные переменные окружения:
`PF_RUN_ID`, `PF_TASK_ID`, `PF_AGENT_RUN_DIR`, `PF_AGENT_EXIT_PATH`,
`PF_AGENT_MODEL`, `PF_AGENT_REASONING_EFFORT`, `PF_PROJECT_ROOT`,
`PF_RUNTIME_DRIVER_ID`, `PF_WORKSPACE_ACCESS_FILE`, `PF_WORKER_RUN_ID` и
`PF_WORKER_TASK_ID`, `PF_WORKER_ATTEMPT`, `PF_PREPARED_INPUT_FILE` и
`PF_PREPARED_INPUT_SHA256`. Shell-драйверы не могут переопределить эти имена.

## Подготовка, выполнение и сбор результата

Подготовка исполнителя требует готового [контракта](work-context.md), явно
объявленного отчёта и права записи по его пути. PF создаёт ограниченные,
неизменяемые [входные данные](prepared-input.md) для одной попытки. Обычная
основная Work без этих объявлений к запуску исполнителя не готова. Манифест
содержит разрешённые ресурсы и проверенные ссылки на источники; он не расширяет
права назначения.

`manual` готовит вход без запуска процесса. `generic-shell` использует
`tools/prepared_executor.py`: проверяет манифест, запускает заданную команду,
записывает heartbeat и результат завершения. `codex-exec` получает тот же
манифест через свою обёртку. Такой исполнитель может работать без MCP;
фактический доступ программы к сети и файлам зависит от ограничений ОС.

Запуск готового исполнителя использует уже подготовленную попытку. Изменение
настроек или заблокированная попытка требуют явной повторной подготовки.
Сбор проверяет принадлежность результатов попытке и сохраняет квитанцию;
повторение и восстановление после гибели процесса не должны дублировать события
завершения. В управляемой Work сбор не меняет стадию основной работы. Основной
агент проверяет результат и передаёт свидетельства в `pf.work.transition`.

Для управляемой Work нативные prepare/start отклоняют терминальные assignment
(`done`, `completed`, `failed`, `cancelled`) и run (`completed`, `failed`,
`cancelled`) с причиной `work_is_terminal` до подготовки и запуска провайдера.
Прямой нативный вызов подготовки также проверяет это до записи настроек запуска.
Незавершённое восстановление отмены сохраняет прежний приоритет. Чтение статуса
и сбор уже существующего результата остаются доступными.

Сбой worker attempt отделён от жизненного цикла управляемой Work: наблюдение
сохраняет отказ попытки, не переводя assignment в `failed`. Для действующей,
готовой Work можно явно подготовить следующую попытку; уже терминальная Work
требует отдельного successor. Поддерживаемые legacy-повторы сохранены, включая
прежний запрет для legacy-задач в статусе `cancelled`.

## Codex Exec

`codex-exec` - штатный драйвер для запуска shell-агентов через Codex CLI.
Драйвер запускает `tools/codex_exec_worker.py`, который проверяет путь,
контрольную сумму и идентичность подготовленного входа, затем передаёт Codex
фиксированные инструкции и манифест. В этом режиме изменяемые prompt, тело
капсулы и указатель workspace-access повторно не читаются.

Команда `pf runtime-driver describe --driver codex-exec --catalog --project-root <путь>`
и вызов `pf.runtime_driver.describe` с `catalog: true` читают каталог моделей
настроенного Codex. Для каждой модели каталог возвращает доступные уровни
мышления и рекомендуемый уровень. `configured_defaults` показывает настройки
действующего профиля Codex. Пустой список означает, что у модели нет вариантов
уровня. Значение null означает, что Codex не сообщил варианты. Если каталог
недоступен, его статус — `unknown`. В Windows и Linux данные читаются при вызове.

Модель можно задать через `agent_model`, параметр `--model` или поле
`runtime.model` / `workers[].model` в плане. Если `PF_AGENT_MODEL` пуст,
оператор может указать `PF_CODEX_MODEL`. Без переопределения Codex выбирает
модель из своего профиля.

При подготовке и запуске PF сверяет выбранную модель и её уровень мышления с
каталогом настроенного Codex. Если указан только уровень, PF проверяет его для
действующей модели из профиля. Обёртка передаёт выбранный уровень как аргумент
`-c model_reasoning_effort="<value>"`. Без переопределения уровня действуют
настройки Codex. CLI и MCP сообщат причину, если явно заданный выбор не
подтверждён. Повторная подготовка или запуск снова читает каталог агента.

Доступ к общим знаниям, шаблонам и инструментам рабочего места решается во
время запуска. В публичных assignment и capsule остаются только id ресурсов или
`path_ref`; абсолютные пути остаются в приватных файлах среды выполнения,
включая `workspace-access.json` и манифест попытки. Старый прямой вызов обёртки
может читать workspace-access и передавать `--add-dir`; подготовленный запуск
не выдаёт через этот файл доступ к целым каталогам. Ресурс с разрешением только
на метаданные не даёт права читать его содержимое.

## Доступ к инструментам MCP

Фактические MCP-подключения и подтверждения вызовов инструментов определяются
собственной конфигурацией каждого coding agent. Декларации PF в
`workspace_access.mcp` — рекомендательные метаданные; они не предоставляют доступ
к инструментам хоста и не управляют доступностью подключений. Подготовка
сохраняет нормализованные неизменяемые декларации в `input.resources.requested.mcp`
и оставляет `input.resources.grants.mcp` пустым. Она не разрешает и не закрепляет
MCP-подключения, не проверяет их отзыв или доступность и не меняет конфигурационные
файлы агента или работающие MCP-серверы. Проверки ресурсов знаний, шаблонов и
инструментов, капсулы, обязательных источников, области файлов и действий и
файловой системы сохраняются. Это поведение совместимости не удаляет MCP-поля
или каталоги; их удаление относится к отдельной будущей работе.

## Запуск исполнителя

Для первой проверки выберите назначение, в котором объявлен ожидаемый отчёт и
разрешена запись по его пути. Возьмите идентификатор назначения из ответа PF.
Штатный тестовый драйвер запишет отчёт локально. Учётная запись модели не нужна.

```bash
python .pf/runtime/bin/pf.py worker-run prepare --project-root . --task <assignment-id> --driver test-echo-worker
python .pf/runtime/bin/pf.py worker-run start --project-root . --task <assignment-id> --driver test-echo-worker
python .pf/runtime/bin/pf.py worker-run status --project-root . --task <assignment-id>
```

Для внешнего CLI выберите зарегистрированный драйвер, настроенный на его
исполняемый файл и аргументы. В плане можно задать `runtime.default_driver`,
`runtime.model` и `runtime.reasoning_effort`, а для отдельного исполнителя
переопределить модель и уровень мышления. `orchestrator-shell-plan-apply --model <model>`
переопределяет модель плана. Указывайте модель и уровень, когда их поддерживает
выбранный драйвер. [Сбор результатов и наблюдение за исполнителем](../getting-started/runtime-driver-supervisor.md)

Программы запускаются с `shell=False`. Каждый драйвер объявляет, нужен ли ему
доступ к сети. Фактическую изоляцию обеспечивает ОС или песочница.

ProcessForge не устанавливает агентов, не создаёт агентские папки и не требует
фонового сервиса для работы реестра драйверов.
