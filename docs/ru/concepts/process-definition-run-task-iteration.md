# Process Definition, Run, Task, Iteration

Process definition описывает правила работы: стадии, роли, артефакты, gates,
события, инструменты и правила развития процесса.

Run применяет процесс к цельному результату в согласованном scope. Task делит
Run на управляемые поручения. Iteration фиксирует повторные попытки работы,
исследования, исправления, проверки или передачи результата.

Эта модель позволяет проверить, какой процесс выбран, какие задачи созданы,
какие артефакты получены и какие проверки или handoff подтверждают результат.

## Граница запуска и внутренние итерации

Один Run охватывает цельный результат, который можно проверить и принять по
явным критериям. Число файлов, время работы, коммиты и ответы воркеров сами по
себе не задают эту границу. Несколько связанных изменений могут составлять
один результат; небольшое самостоятельное исправление также может быть
полноценным результатом. Минимального размера или времени работы нет.

Внутри этой границы работа делится на задачи и итерации. Повторное уточнение
домена и архитектуры, согласованные редакции плана, реализация и локальные
проверки не требуют нового Run после каждого шага. Итоговая проверка оценивает
накопленный результат. Публикация, выпуск и установка следуют согласованной
границе поставки и требованиям проекта и пользователя.

Предыдущие свидетельства можно использовать, пока они остаются применимыми к
текущему кандидату. После изменений повторяются затронутые проверки; завершение
итерации само по себе не требует несвязанного полного набора тестов.

## Вклад исполнителя и вложенный процесс

При разрешённом делегировании исполнитель может продолжить текущую стадию по
подготовленному входу существующего Assignment. Основной агент передаёт запись
на время выполнения и проверяет результат после сбора. Смена исполнителя сама
по себе не требует нового Task или Run и не завершает родительскую стадию.

Для достаточно крупного независимого блока допустим отдельный полный процесс
воркера. Его цикл остаётся вложенным в цикл оркестратора: основной агент
интегрирует результат и свидетельства до общей приёмки. Завершение дочерней
работы не завершает и не публикует родительскую автоматически.

Связанную мелкую работу можно объединить в полезный блок. Единичное мелкое
изменение лучше оставить основному агенту, если отдельный исполнитель добавит
только расходы на координацию. Наличие воркера не обязывает создавать поручение.

Эти правила не меняют полномочия. Соблюдайте текущий контракт Work, объявленные
outcomes, защиту утверждённых артефактов и правила handoff. Нельзя расширять
scope, придумывать обратный переход или пересобирать неизменяемую капсулу.

## Граница software lifecycle

Process definition описывает жизненный цикл, а не платформенную команду сборки
или доставки. Например, `software-feature-development` содержит условные
стадии `release-delivery` и `evolve`, а сборка, пакетирование и установка
задаются через `execution_profile.delivery_profile`.
