# ProcessForge 1.2.0

ProcessForge 1.2.0 ускоряет выбор Work и чтение контекста, а также делает
восстановление после ошибок исполнителей понятнее. Перед установкой проверьте
[требования](../requirements.md), а для существующей установки выполните
[обновление и миграцию](1.2.0-migration.md). Доступность загрузки, commit
исходников под тегом и SHA-256 архива подтверждаются опубликованными файлами
релиза; эта страница сама по себе не подтверждает публикацию.

## Что меняется для пользователя

- Выбор точной Work не требует просмотра посторонней истории. При повторном
  чтении контекста повторно используется разбор неизменившихся документов,
  но текущие файлы и права всё равно проверяются. Эффект зависит от объёма
  и характера работы; большая история по-прежнему может требовать CPU и память.
- События проекта и нативных хуков хранятся в отдельных локальных базах SQLite.
  Индексы уменьшают повторное чтение истории при приёме и воспроизведении.
  Прежние журналы требуют явного переноса: установка Core не импортирует
  и не удаляет их.
- Уже собранный результат исполнителя остаётся виден как история. Устойчивый
  отказ автоматического collect отображается как необходимость восстановления,
  вместо бесконечного повторения одного отказа. Временные ошибки I/O и
  блокировок допускают повтор. Результат задачи и работоспособность Runtime
  показываются отдельно.
- Продолжение Work сохраняет выбранные Run, assignment, неизменяемый контекст
  и закреплённый процесс. Смена сессии не разрешает выбрать другое назначение
  или расширить scope. См. [продолжение Work](../concepts/work-continuation.md).
- Вход в проект использует корневой `AGENTS.md` и текущий контекст. Существующие
  START-файлы сохраняются; `agent-start-prompt` по умолчанию показывает подсказку
  без записи. Подготовленный worker следует переданному входу без подключения
  PF MCP и создания другой Work.
- Временные материалы проекта размещаются в `.pf/tmp/`. Необязательный
  app-server сообщает о старых файлах после настраиваемого числа часов,
  не удаляя их и не определяя их нужность по истории Work.
  См. [временные файлы](../temporary-files.md).

## Необязательная инфраструктура и приватность

Файловая работа в Garage доступна без PF Runtime. Runtime, координация
исполнителей и телеметрия host подключаются отдельно. Автоматические хуки
Garage по умолчанию выключены и включаются наследуемой настройкой
`runtime.garage_hooks`; обязательные проверки Forge сохраняются.

`logging.raw_hooks` и `logging.events` независимо управляют необязательной
историей. Её отключение сохраняет минимальные записи приёма и незавершённую
обработку, не останавливает явную Work или передачу переписки и не удаляет
прежние данные. Базы SQLite, WAL и файлы общей памяти храните приватно на
локальном диске. См. [настройки (EN)](../../authoring/workplace-configuration.md#project-history-and-raw-hooks).

Временные файлы репозитория храните в `.pf/tmp/`, выделяя каждому исполнителю
свою папку. При очистке сохраняйте чужие и используемые файлы.

## Перед обновлением

Сохраните локальное состояние, рассмотрите план обновления Core и перенесите
прежние журналы в согласованное окно обслуживания. Обновление Core не меняет
существующие capsules, закреплённые процессы и одобренные входы. Перезагрузка
подключённого MCP host — отдельное действие оператора; новый процесс Runtime
не подтверждает её выполнение.

Команды и проверки завершения приведены в [инструкции перехода](1.2.0-migration.md),
а поддерживаемые границы — в [ограничениях](../known-limitations.md). Проверка
на одной ОС сама по себе не подтверждает совместимость со всеми остальными.

Реализация и исторические измерения вынесены в справочник разработчика:
[чтение документов](../concepts/document-reads.md),
[журналы](../concepts/hook-journal-sqlite.md) и
[аудит выбора Work](../audits/canonical-work-selection-20261016.md).
