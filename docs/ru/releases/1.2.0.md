# ProcessForge 1.2.0 — промежуточная точка рефакторинга

Кандидат для рассмотрения; публичная публикация ожидает квалификации и явного
одобрения сопровождающего.

Версия фиксирует промежуточный результат продолжающегося рефакторинга Core.
Полный перевод CLI, MCP и Daemon на независимые службы ядра продолжается после
этого выпуска. Новые Kernel, DI-контейнер и plugin engine не являются необходимым
объёмом этой точки фиксации.

В Core уже выделены владельцы чтения Work, контекста и материалов, процессов,
каталога и snapshot, политик контекста/ресурсов, отдельных правил выбора,
evidence/completion и журналов событий. Командные и parser-классы передают
соответствующие сценарии этим службам. Общий bootstrap и часть сборки ещё
зависят от legacy facade; все пять направлений программы ООП остаются открытыми.

Принятый набор также содержит изменения скорости и восстановления: точный
проверенный выбор Work исключает чтение посторонней истории; снимки журналов
сохраняют ограниченное переиспользование при чередовании проектов; supervisor
наблюдает уже собранную попытку как исторический факт; устойчивый смысловой отказ
collect прекращает автоматические повторы с видимой причиной восстановления.
Первый и явный collect, новые попытки сохраняют полные проверки, временные ошибки
по-прежнему допускают повтор. Эти решения о поведении описываются отдельно от
структурного переноса кода.

Вход в проект использует корневой `AGENTS.md` и текущий контекст PF.
Onboarding/repair сохраняют прежние START-файлы; `agent-start-prompt` по умолчанию
показывает результат без записи, явное размещение для совместимости остаётся.

Версии релиза, процесса, схемы и startup contract имеют разные значения.
Этот выпуск не переписывает исторические капсулы, process pins и утверждённые
входы. См. [заметки по миграции](1.2.0-migration.md).

Построение CLI parser откладывает инициализацию egress до выполнения его
команды. Остальные команды избегают этой работы при запуске; implementation
identity, квалификация и защитные проверки egress сохраняют прежнюю семантику.
Изменение не зависит от платформы.

Smoke диагностики проверяет полный учёт попыток: подтверждённый append либо
явный отказ в рамках прежнего необязательного best-effort контракта. Сохранены
бюджет допуска 50 мс, проверки общего бюджета, late grant, взаимного исключения,
смешанных версий писателей и хранения. Непредсказуемые задержки файловой системы
больше не трактуются как обещание отсутствия потерь. Ядро диагностики не менялось.

Журналы событий проекта и нативных хуков теперь используют отдельные локальные
базы SQLite с транзакционным допуском и индексированным воспроизведением.
Сохранение нормализованной и исходной истории регулируется независимо; при его
отключении сохраняются минимальные квитанции и незавершённая обработка.
Существующим журналам нужен явный управляемый
[переход](../../concepts/hook-journal-sqlite.md): обновление Core само по себе
не импортирует и не удаляет прежнюю историю.

Разбор неизменившегося безопасного YAML повторно используется между запросами
в пределах процесса. LRU хранит до 4096 записей и оценочных 64 MiB; это пределы
хранения кэша, а не всей памяти процесса. Текущие байты, права и проверки остаются
источником истины, вызывающий код получает независимые значения. Поиск Run хранит
только проверенные поля идентичности и статуса. См.
[чтение документов](../concepts/document-reads.md).

Автоматические хуки Garage включаются явно через наследуемую настройку
`runtime.garage_hooks`; обязательные проверки Forge сохраняются. Допущенные
нативные хуки жизненного цикла сами регистрируют и завершают сессии. Явные операции
Work и доставка переписки доступны независимо от необязательного сохранения
истории. См. [настройку хуков](../concepts/runtime-configuration.md).

Работоспособность Runtime определяется выполнением планировщика. Ошибки workers
и требования восстановления collect остаются видимыми результатами задач.
Частичные метрики сохраняют признаки неполного покрытия и неизвестные значения.
При неудачной публикации состояния или истории удаляется только собственный
временный файл с сохранением целевого файла и исходной ошибки. Принудительное
завершение процесса или отказ удаления могут оставить временный файл. См.
[модель Runtime](../concepts/runtime-model.md).

Большая сохранённая история по-прежнему может повышать нагрузку планировщика
Runtime, стоимость получения контекста и допуска. Измерения устройства относятся
к конкретной нагрузке и не обещают универсального ускорения. Исходники, архив,
установленное ядро, Runtime и фактически подключённый host требуют отдельных
доказательств. Проверки Windows сами по себе не подтверждают Linux или macOS.

Общий аудит/чистка smoke-тестов и политика моделей лаунчера на устройстве —
отдельные последующие задачи. Публичный tag, release assets и стабильный канал
обновлений сохраняются до решения о публикации.
