# Обновление до ProcessForge 1.2.0

Эта инструкция предназначена для оператора существующей установки. Обычный
проектный агент сообщает об инфраструктурных блокерах, а обновление Core
и перезапуск служб выполняет оператор. Для новой установки используйте
[руководство по установке](../getting-started/installation.md).

## 1. Подготовка и рассмотрение плана

Проверьте [требования](../requirements.md), загрузите выбранный релизный архив
и сверьте SHA-256 с опубликованным сопроводительным manifest. Сохраните точную
версию, commit под тегом и hash в приватных доказательствах обновления.
Создайте резервную копию состояния проекта и workplace, проверьте локальные
изменения файлов PF. Временные файлы проекта храните в `.pf/tmp/`; резервные
копии приватного состояния не должны попадать в публичный релиз.

Через текущий установленный CLI проверьте состояние и план обновления по manifest.
Укажите существующий workplace, чтобы включить совместимую миграцию,
объявленную в архиве:

```bash
python <core-root>/bin/pf.py core-update status --core-root <core-root>
python <core-root>/bin/pf.py core-update plan --core-root <core-root> --archive <release-archive> --workplace-root <workplace-root>
```

Рассмотрите добавления, изменения, удаления, конфликты локальных правок
и резервные копии. План ничего не записывает. Не используйте `workplace-init`
для обновления существующего workplace. См. [подробности обновления Core](../concepts/core-update-manifest.md).

## 2. Обновление Core в окно обслуживания

Если старые процессы пишут журналы, остановите их штатным операторским способом
и не запускайте до завершения переноса. Не выполняйте несколько обновлений
Core/workplace одновременно. После рассмотрения плана явно примените его:

```bash
python <core-root>/bin/pf.py core-update apply --core-root <core-root> --archive <release-archive> --workplace-root <workplace-root> --confirm
python <core-root>/bin/pf.py core-update status --core-root <core-root>
python <core-root>/bin/pf.py version
python <core-root>/bin/pf.py doctor-workplace --root <workplace-root>
```

Локальные изменения файлов PF блокируют применение, пока оператор явно
не разрешит их замену. Неизвестные файлы сохраняются. При `incomplete_update`
остановитесь и изучите `core-update repair --core-root <core-root>`: команда
определяет нужный способ восстановления, но не обещает автоматический откат.

## 3. Перенос прежних журналов при необходимости

Установка Core не импортирует прежние журналы событий проекта и raw hooks.
Для каждого проекта с прежними журналами сохраните копии остановленных
источников, затем запустите утилиту из корня обновлённого дистрибутива:

```bash
python tools/migrate-hook-journals.py --project-root <project-root> --workplace <workplace-root>
python tools/migrate-hook-journals.py --project-root <project-root> --workplace <workplace-root> --apply
```

Первая команда показывает план без создания базы проекта. Рассмотрите
диагностику перед применением. До возобновления записи новым Core убедитесь,
что оба журнала имеют состояние `ready`. Незавершённый импорт блокирует обычный
доступ; устраните причину и повторите ту же команду для продолжения. Исходные
файлы сохраняются; последующие записи старого формата не копируются
автоматически. Уже перенесённому проекту повторный импорт ради переподключения
host не нужен.

Базы SQLite, WAL и файлы общей памяти храните приватно на локальном диске.
Для копирования работающей базы используйте SQLite backup API. Выбор источников,
проверки и восстановление описаны в [справочнике миграции журналов](../concepts/hook-journal-sqlite.md).

## 4. Проверка входа и продолжение точной Work

Перед изменением сбора истории проверьте наследуемые `logging.raw_hooks`,
`logging.events` и `runtime.garage_hooks`. Хуки Garage по умолчанию выключены;
необязательная история не останавливает явную Work или переписку.

В каждом затронутом проекте рассмотрите текущий контракт корневого `AGENTS.md`
и локальные инструкции. Существующие START-файлы сохраняются;
`agent-start-prompt` по умолчанию показывает подсказку без записи. Перенос
контракта входа — отдельная рассматриваемая операция. Версии релиза, процесса,
схемы и startup contract независимы.

```bash
python <core-root>/bin/pf.py doctor-project --project-root <project-root>
python <core-root>/bin/pf.py project-context-check --project-root <project-root> --json
```

Если контекст устарел или повреждён, выполните указанное действие оператора
до зависимой работы. Обновление Core не переписывает одобренные capsules
и закреплённые процессы. Возобновляйте существующую Work с точными селекторами
по [командному справочнику агента](../getting-started/agent-prompts.md).
Для смены scope требуется управляемая передача. Завершённая Work не запускает
новую попытку нативного исполнителя.

Если используются Runtime или подключённый MCP host, обновите их штатным
операторским способом и проверьте версию, фактически загруженную host.
Новый процесс Runtime сам по себе не подтверждает перезагрузку host.
Файловый режим не требует этих служб. Для восстановления collect сначала
проверьте текущую причину отказа и входы, затем выполняйте явный ручной сбор
или новую попытку. Старый успешный результат не подтверждает изменённые исходники.

Перед возвратом к обычной работе рассмотрите [заметки о выпуске](1.2.0.md)
и [ограничения](../known-limitations.md).
