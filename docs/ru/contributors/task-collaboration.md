# Задачи, локальный PF и GitHub

[English](../../contributors/task-collaboration.md)

Содержательная разработка ProcessForge ведётся через PF. Его проектное состояние
остаётся локальным и исключается из Git. Общие инструкции, профили знаний,
определения процессов и принятые архитектурные решения версионируются. Другой
контрибьютер создаёт собственные контекст и Work. Публичный issue не является
резервной копией локального PF.

## Выбор источника задач

[Общий профиль](../../contributors/collaboration-profile.json) задаёт `local_pf`
для текущей разработки 1.3.0. Выбранный режим записывается в дополнительные поля
локального проекта. Явное решение сопровождающего может задать режим `github`.
Появление issue или временная недоступность сети сами по себе режим не меняют.

| Правило | `local_pf`: GitHub — зеркало | `github`: GitHub — источник задач |
| --- | --- | --- |
| Где появляется задача | В локальном учёте PF или принятом поручении сопровождающего. | В существующем или новом GitHub Issue. |
| До создания Work | Определить локальную цель, границы и критерии готовности. Issue необязателен. | Прочитать issue и обсуждение; связать Work с его URL до выполнения. |
| Work и итерации | Для крупной задачи может потребоваться несколько Work и итераций. | Несколько локальных Work и контрибьютеров могут решать один issue. |
| Изменение постановки | Принять в локальном PF, затем опубликовать содержательную сводку. | Согласовать в issue, затем привести локальные Work/контексты в соответствие штатным способом PF. |
| Публичные обновления | Крупные задачи, принятые решения, блокеры, готовые части и результаты проверок. | Значимый прогресс и блокеры общей задачи. |
| Обратная связь | Рассмотреть предложения и внести принятые изменения в локальный учёт. | Перед продолжением прочитать актуальные общие решения. |

Один issue описывает ограниченную проблему или результат с критериями приёмки.
Версия 1.3.0 может включать много таких задач; для публичного учёта версии можно
использовать GitHub Milestone. Work — единица исполнения, а не копия issue.
Отдельный issue для каждого этапа или повторной попытки не нужен.

В режиме `local_pf` отсутствие доступа к GitHub не мешает разрешённой локальной
работе; публикация отмечается как ожидающая выполнения. В режиме `github`
отсутствие issue или недоступность актуального решения блокирует зависимую работу:
агент сообщает, каких входных данных не хватает. Порядок доставки через ветку,
проверки, PR и review из CONTRIBUTING действует в обоих режимах.

## Дополнительные поля связей

Это соглашение контрибьютеров в расширяемых документах проекта и assignment,
а не новые аргументы CLI или встроенный API синхронизации. Ссылки являются
метаданными, отдельными от параметров исполнения `parameters`, этапа, статуса,
прав и неизменяемых капсул. Используйте поддерживаемый маршрут редактирования
локальных метаданных; добавление URL не требует ручной правки жизненного цикла
или закреплённой капсулы.

В `.pf/process-forge.yaml` дополните объект `project`, сохраняя его существующие
идентификатор и остальные поля. Начальные значения возьмите из общего профиля:

```yaml
project:
  id: process-forge
  name: ProcessForge
  collaboration:
    task_source: local_pf
    repository_url: https://github.com/WebTolk/process-forge
    integration_branch_url: https://github.com/WebTolk/process-forge/tree/dev
    target_version: 1.3.0
```

В локальном assignment выбранной Work разместите блок на верхнем уровне.
Ниже URL-заготовки: замените их настоящими ссылками, а ещё не существующие связи
не записывайте:

```yaml
collaboration:
  issue_url: https://github.com/WebTolk/process-forge/issues/NUMBER
  branch_url: https://github.com/WebTolk/process-forge/tree/WORKING-BRANCH
  pr_url: https://github.com/WebTolk/process-forge/pull/NUMBER
```

`integration_branch_url` — общая ветка интеграции; `branch_url` — рабочая ветка
конкретной Work. Не подменяйте одно значение другим. Несколько assignment могут
содержать одинаковый `issue_url`; номер issue не заменяет точные идентификаторы PF.

Агент обязан прочитать эти поля из настоящего манифеста и выбранного assignment
при получении контекста. Сокращённый ответ `pf.context`/`pf.work.state` может их
не показывать; принятие поля схемой не доказывает доставку агенту. Используйте
разрешённый путь чтения ресурсов проекта/Work и зафиксируйте выбранные режим и
ссылки в рабочей передаче контекста. Не рассчитывайте, что неизвестные аргументы
инструмента будут сохранены.

Если ссылки уже записаны в старом варианте через `parameters`, сначала прочитайте
и согласуйте их, не создавайте конфликтующих копий. Изменение закреплённых
параметров, цели, границ или разрешённой ветки выполняется через штатный маршрут
контекста/преемника PF. Обновление публичной ссылки само по себе не разрешает
изменять контракт исполнения.

## Поведение агента

1. Прочитать общий профиль, локальные поля связей, действующий контекст PF и точную
   выбранную Work. Если режимы общего профиля и локального проекта различаются
   без зафиксированного решения сопровождающего, устранить расхождение до
   публикации или изменения постановки.
2. Если есть `issue_url`, прочитать issue и актуальное обсуждение. Применять
   приоритет выбранного режима: зеркальный issue не подменяет локальную цель.
   В режиме `github` получить URL issue до запуска связанной Work.
3. Проверить Git и соответствие `branch_url` репозиторию и рабочей копии.
   Сохранить посторонние изменения; работать в изолированной ветке/копии для
   выбранной области. Расхождение требует согласования, а не принудительного
   переключения ветки или сброса файлов.
4. Выполнять этапы PF, сохранять доказательства и точные идентификаторы Work.
   Читать только необходимые знания. Первичная настройка и диагностическое
   чтение допускаются до Work; отсутствие готовности PF блокирует содержательное
   выполнение, но не явно порученную подготовку среды и инструкций старта.
5. На этапе публикации или доставки разместить разрешённую публичную сводку
   в связанном issue/PR: решения, результаты, проверенные ревизии/платформы и
   оставшаяся работа. Сохранять чужой текст и обсуждение. Локальные пути, капсулы,
   учётные данные, сырые журналы и непроверенные черновые рассуждения остаются
   приватными.
6. В режиме `local_pf` создать зеркальный issue, когда публикация разрешена и
   полезна; сохранить полученный URL и далее обновлять эту же задачу. Перед
   созданием проверить локальную связь и репозиторий на существующий issue/PR.
   В режиме `github` обновлять общую задачу, не создавать параллельную копию.
7. Сохранять настоящие URL рабочей ветки и PR по мере их появления. URL описывает
   связь; публикация, push, merge и закрытие выполняются в рамках поручения,
   процесса и правил репозитория.

## Завершение и продолжение

Завершение или отмена одной Work не закрывает и не переоткрывает issue.
Промежуточные PR ссылаются на него без команды закрытия. Issue закрывается после
выполнения всех критериев и интеграции принятых изменений в `dev`, если его
постановка явно не требует приёмки релиза. `Closes #NUMBER` используется только
в завершающем PR. GitHub обрабатывает такие команды для ветки по умолчанию;
проверяйте действующую настройку, не предполагайте, что это всегда `dev`.
[Правила связывания GitHub](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue).

Другой контрибьютер или устройство читает issue, принятый код, общие решения и
проверки, затем создаёт собственную Work в локальном PF. Точное продолжение чужой
приватной Work требует явного переноса состояния и корректного continuation PF;
сводки issue для этого недостаточно. Чужие капсулы и пути устройства не должны
становиться зависимостями подготовки нового рабочего места.

Смена источника задач — зафиксированное решение сопровождающего: согласовать
открытые задачи и ссылки, определить область действия, затем применить правила
PF к затронутым активным контекстам. Завершённая история Work не переписывается.
Это соглашение не предполагает наличия автоматического двустороннего
синхронизатора.
