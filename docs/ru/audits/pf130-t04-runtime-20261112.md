## Публикация, читатели и существующая сериализация

`RuntimeServiceStateStore` создаёт staging рядом с назначением и атомарно заменяет
один из двух `service-details.{slot}.json`, затем последним публикует компактный
`service.json`. Предел control — 65 536 байт UTF-8; превышение отклоняется до
публикации. Details связаны slot, размером, хешем и instance. Отказ commit сохраняет
прежний принятый control и связанные details; неиспользуемый slot или staging
прерванного writer может остаться. Это не гарантия сохранности при потере питания.

Полный status восстанавливает подходящую диагностику с ограниченными повторами
при смене поколения того же владельца; испорченные/отсутствующие/чужие details дают
консервативный degraded результат. Живые starting/stopping/failed различаются.
Admission читает только ограниченный control и сохраняет fail-closed для malformed,
oversized и stopping/failed, без чтения diagnostic slots. Monitor имеет отдельный
ограниченный compatibility reader. Doctor получает protocol version из control.

Runtime save сохраняет operation lease и state serialization. Singleton и холодная
публикация токена используют существующие native guards и повторные проверки.
Маршрут проекта привязан к точным root/owner; скопированный освобождённый admission
context не заменяет живой native lease. Shutdown сохраняет deadline, guards
admission/singleton/project и текущие проверки owner/workers. Ошибочная авторизация
получает текущие полномочия записи до изменения диагностики. Единого универсального
fence нет: PID, terminal string, прежний preflight или возраст не дают права очистки.

## Completion, журналы и историческая очистка

Completion сохраняет run lock, immutable publication, identity intent/events и
dedupe/replay. Допуск complete только на финальной стадии повторно проверяется под
существующим lock. Terminal intent проверяет совместимость истории/предшественника
и точный набор ожидаемых событий. Тесты повреждений не доказывают поддержку
конкурентных cancellation writers или криптографическую аутентичность истории.
18 fault points включают retry до intent, replay intent и terminal cleanup;
это не восемнадцать повторов уже сохранённого intent.

Bootstrap журнала повторно читает оба заголовка под существующей сериализованной
транзакцией и отклоняет любой чужой объект основной схемы. Ошибка rollback сохраняет
первичную ошибку тела/COMMIT/отмены с best-effort заметкой о классе вторичной ошибки
и неизвестном исходе. Native close, другие Driver transactions и потеря питания
не входят в это ограниченное исправление.

Исторический capture проверяет все сохранённые output pins по объявлениям capsule,
без чтения текущих outputs. Некорректная история не подавляет настоящий semantic
recovery observation. Очистка принятого scratch отдельно проверяет строгую историю,
точные текущие task/attempt, native absence, SQL generation/revision/latest record
и resource authority. После внешней resource authorization проверки повторяются
под lifecycle lock, затем публикуется end-of-use. Физическое удаление остаётся вне
lifecycle/SQL locks. История сама по себе не разрешает удаление.

## Свидетельства и пределы

Поставленная Runtime recovery матрица выбирает 717 case IDs на настоящих Windows
и Ubuntu 22.04, Python 3.11/pytest 9.1.1. Cleanup выбирает полный набор исторической
collection/disposal/native lifecycle, включая 25 D2 случаев. Native Linux имеет
отдельный профиль. Результаты точной ревизии:

| Профиль | Windows PASS / SKIP | Linux PASS / SKIP |
|---|---:|---:|
| Runtime, 717 одинаковых case IDs | 708 / 9 | 707 / 10 |
| Cleanup, 342 случая | 341 / 1 | 328 / 14 |
| Native Linux, 643 случая | — | 605 / 38 |

Все 241 критический Runtime case, 35 Work-start и 25 новых historical-pin случаев
фактически прошли на обеих ОС. Оба Runtime jobs прошли все 18 completion fault
points, malformed-intent no-write и SQL recovery с шестью producers: 301 unique
concurrent events, 100303 history rows и indexed lookup.
Девять структурных Runtime skips: шесть writers без явного flush/fsync и три
worker-input-only capture проверки. Linux дополнительно пропускает Windows
native-handle случай, фактически прошедший на Windows. Cleanup пропускает один
Linux-native error case на Windows, private DACL/13 Windows-handle случаев на Linux.
Native Linux пропускает 29 Windows handle/Job случаев и девять структурных.
Пропуски не засчитаны как PASS.

[Repository checks](https://github.com/WebTolk/process-forge/actions/runs/43339744268)
и [native Linux](https://github.com/WebTolk/process-forge/actions/runs/43339744094)
дали все семь checks PASS. Logs и XML с уникальными case IDs проверены по точной
ревизии. Воспроизводимая выборка, окружение fixtures и команды приведены в
[закреплённом workflow](https://github.com/WebTolk/process-forge/blob/b159f68bb4e12829e55b7d56c0d88766763e8552/.github/workflows/repository-checks.yml).
Новые D2 + существующий verifier также дали по 104 PASS локально на каждой ОС,
без пропусков.

Профиль использует изолированные consumer fixtures с simple coordination и Core
Work-start port вместо stdio MCP. Запрет запуска охватывает наблюдаемые прямые
запуски services/models, а не произвольные действия потомков. Установленный Runtime,
подключённый host, MCP transport, model session и cross-boot recovery не приняты.
Настоящий child os._exit и управляемая fault injection имеют разные границы.

Сохранены исходная ошибка import path launcher, cold-journal race (PR32), настоящий
ограниченный отказ Windows sharing, шесть отказов Linux consumer onboarding на
mounted NTFS (private_acl_unavailable) и локальные concurrent-reader ENOENT без
установленной причины/чистой базовой проверки. Native CI квалифицирует выполненные
сценарии, но не отменяет локальные отказы и не принимает устройство целиком.
Блокировки и timeout ради PASS не обходились.

Исправления доставлялись отдельно в PR33–44 с целевыми проверками на реальных ОС
и семантическими ревью native PF shell Astra. Первоначальные REQUEST_CHANGES и
неуспешные прогоны сохранены рядом с исправленными. Итоговое ревью взаимодействия
Runtime/cleanup и CI точного docs-head должны быть отражены в delivery PR до merge.
Статический анализ ревьюера и выполненная автором проверка logs/XML различаются.
Общее исправление исторических contention_timeout/execution_activity_unknown,
универсальное восстановление remnants и stable-release GO не заявляются.
Дальнейшая release/installed-device квалификация относится к №22/25.
