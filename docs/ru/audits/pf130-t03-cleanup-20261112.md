## Поведение текущего caller

`verify_accepted_collection` в `prepared/input.py` проверяет ограниченные по
размеру immutable metadata точного исторического attempt: capsule, prepared
input, receipt, completion marker и сохранённые output pins. Приёмка не
пересоздаётся по текущей стадии; новый report не перечитывается.

CLI `_finalize_worker_scratch` отдельно выбирает точное SQL/native доказательство
завершения использования. Для принятого результата `release_accepted_scratch`
требует нынешние assignment/capsule/resource authorization и owned creation
metadata. SQL должен по-прежнему указывать на точный absent/collected attempt с
совпадающими generation, revision и latest record. Legacy-путь отдельно
доказывает отсутствие native tree своего attempt. Старый receipt не даёт
нынешних разрешений.

Caller повторно проверяет task, state, acceptance и identity ресурса вокруг
resource authorization. Под worker serialization публикуется только release.
Resource admission и физическое удаление выполняются вне lifecycle lock.
CLI вызывает cleanup до admission prepare/start и после выхода из
serialization collect. Failed и never-launched пути сохраняют отдельные
требования к evidence. Unknown activity, чужой owner, pending collection и
изменённое наблюдение запрещают cleanup с сохранением данных.

## Выполненный профиль

Чистый снимок исходников не содержал приватного состояния проекта. На обеих
платформах использованы реальные файлы и существующие тесты без изменения
исполняемого PF.

| Платформа | Python | Успешно | Платформенных пропусков | Результат |
| --- | --- | ---: | ---: | --- |
| Windows | 3.11.9 | 316 | 1 | PASS |
| Linux на смонтированном NTFS | 3.12.3 | 299 | 14 | FAIL: 4 отказа filesystem/privacy |

Таблица описывает локальные запуски и не объявляет Linux принятым. Итоговая
проверка Linux выполняется на Linux-файловой системе CI runner; JUnit и результат
точной ревизии фиксируются в PR поставки, связанном с задачей №15.

На Windows пропущен только Linux-specific signal-reopen failure. Все 13
Windows identity/handle cases успешно выполнены на Windows. Пропуски Linux
перечислены в сохранённом JUnit и не засчитываются как проверка другой ОС.
Обязательный native cleanup cycle прошёл на Windows и остаётся условием Linux
CI; локальный Linux native case остановился на инициализации.

Выборка содержит 79 verifier cases, 39 cleanup-caller cases, один native cycle,
150 disposal cases и 48 execution-lifecycle cases. Прежний результат в 449 cases
не прибавляется к этим новым проверкам.

Native cycle запускает зарегистрированный тестовый worker через настоящий
CLI/Work и SQL, собирает результат и удаляет его owned scratch, переводит
стадию штатным transition, затем готовит attempt 2. Прежние capsule/receipt/
completion/resource/release и новый report остаются побайтово неизменными.
Первый payload уже удалён при collect. Физическое удаление после перехода
стадии отдельно проверяет caller test с моделями state/resource ports;
verifier, contract, owned creation и удаление в нём настоящие. Чистые тесты
ветвей ОС не доказывают native-поведение ОС.

Матрица отказов охватывает отзыв текущих разрешений, изменение intent/capsule,
чужой attempt, drift SQL collection/revision/generation, cancellation/retry,
изменение completion/creation records и false/unknown legacy absence.
Disposal-тесты проверяют ownership/path redirection, retain policy, ошибки I/O,
replay receipt и cleanup после failed/unpublished preparation.

## Воспроизведение и прежние сбои

Подготовить изолированное окружение из
[`repository-checks.yml`](../../../.github/workflows/repository-checks.yml),
шаг “Qualify historical collection cleanup and native stage advance”, и выполнить:

```text
python -m pytest -q -ra --capture=sys -p no:cacheprovider --basetemp=<owned-scratch>/pytest --junitxml=cleanup-results.xml tests/prepared_collection_state tests/temporary_disposal tests/executions/test_lifecycle.py
```

`PYTHONPATH` включает `src`, `tools`, `tests` через `os.pathsep`. Workflow
создаёт отдельные owned roots всех fixture/temp variables, запускает одну
выборку на Windows и Linux, закрепляет pytest 9.1.1 и сохраняет JUnit каждой ОС.

Первый локальный Linux-запуск остановился до выполнения тестов: стандартный
захват pytest через файловый дескриптор не смог обрезать временный файл на
смонтированном диске. Ненулевой exit и traceback сохранены. Исправленный запуск
использует `--capture=sys` и выполнил всю выборку, но четыре случая завершились
ошибкой. Смонтированная файловая система сообщала mode `0777`: две проверки
owned creation не подтвердили права, private staging и инициализация native
cycle отказали с `private_acl_unavailable`. При раскрутке отказа инициализация
также показала ошибку присвоения traceback frozen exception; сбой сохранён,
реализация исключения в этой поставке не меняется. Это не PASS. Guards PF,
assertions и обязательные сценарии не ослаблялись. Linux CI должен выполнить
те же случаи на файловой системе с поддержкой POSIX privacy; remount и изменение
host configuration не входят в задачу. Прежняя Windows-приёмка также не закрывала
условие Linux.

Первый CI-запуск на `ubuntu-latest` прошёл filesystem privacy, но дал 282 PASS,
21 FAIL и 14 Windows-only skips. Native helpers вернули `Operation not permitted`:
необходимые условия запуска недоступны. Полный native suite уже использует
`ubuntu-22.04`. Теперь cleanup выполняется на том же Linux image отдельной
job вместе с Windows; общие public source checks сохраняют `ubuntu-latest`.
Host policy и guards PF не меняются. JUnit первого CI сохранён как failure,
а не как PASS.

Исполняемый Python не менялся, новая область lint/type diagnostics не появилась.
YAML workflow и встроенный Python разбираются, PyCharm не показывает ошибок
workflow. На чистой итоговой композиции должны пройти schema, inventory и
public-cleanliness validators. Профиль не является приёмкой полной установки
Runtime, обновления из архива, cross-boot recovery или stable-релиза 1.3.0;
задачи №16, №19, №20 и №22 сохраняют отдельные условия.
