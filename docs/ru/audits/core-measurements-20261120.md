# Замеры ProcessForge на двух Windows-устройствах и проверка документации

20 ноября 2026 года. На этом устройстве медиана запуска `hooks-dispatch --dry-run` составила **1,319 с** в обычном режиме. На устройстве из #110 та же команда заняла **4,424 с**. При чтении страницы из 100 событий результат обратный — **20,568 мс** у RC1 и **4,861 мс** у beta3. У RC1 чтение включало проверку привязки хранилища. В обеих установках два журнала SQLite использовали WAL и страницы по 4 096 байт. При замерах их WAL-файлы занимали 0 байт. Суммарный размер основных файлов двух журналов составил **79 765 504 Б** и **1 636 335 616 Б**. Прежний NDJSON может пересекаться с импортированной историей. Квитанции и исходные данные описывают разные стороны одного приёма, поэтому складывать их как события нельзя.

По первому и последнему номеру последовательности локальные события и квитанции охватывали 11–20 ноября. В #110 события охватывали 7 сентября – 20 ноября, квитанции — 20 августа – 20 ноября. При повторе локального подсчёта в 11:07:46 было 14 423 события, 4 695 квитанций и 801 исходная запись. В конце серии #110 — 245 906, 89 540 и 33 469. Действующая настройка определяет сохранение новых данных, поэтому число прежних исходных записей может оставаться ненулевым при выключенном `raw_hooks`.

**Хуки.** В проектной конфигурации Codex обоих устройств объявлено по восемь обработчиков PF для `SessionStart`, `SessionEnd`, `PostToolUse`, `UserPromptSubmit`, `PreCompact`, `PostCompact`, `Stop` и `SubagentStop`. Это число записей конфигурации. Для подтверждения каждой доставки нужны наблюдения клиента. В `.pf/hooks.yaml` здесь два маршрута, из них включён один, в #110 — три и один соответственно. Во всех сухих прогонах с `assignment.completed` выбран ровно один outbox.

### Как повторить серию

Запускайте установленный `tools/processforge.py` из нового процесса Python с `-B`. Для каждой пробы фиксируйте `perf_counter_ns()` от запуска до получения полного stdout/stderr, код выхода и выбранные маршруты. Используйте один начальный вызов в каждом режиме и семь пар, меняя порядок в соседних парах.

```text
python -B <Core>/tools/processforge.py --diagnostic-profile normal --diagnostic-threshold info hooks-dispatch --project-root <Project> --event-type assignment.completed --dry-run
python -B <Core>/tools/processforge.py --diagnostic-profile diagnostic --diagnostic-threshold debug hooks-dispatch --project-root <Project> --event-type assignment.completed --dry-run
python -B <Core>/tools/processforge.py project-context-check --project-root <Project> --json --check-update-candidates never
python -B <Core>/tools/processforge.py events-validate --project-root <Project>
```

В RC1 профиль задан для отдельного вызова, в #110 подробный профиль временно действовал на проект. Приёмник у обеих серий CLI — JSONL. Внутреннее время берётся из `hooks-dispatch.completed`. У всех семи подробных локальных проб есть запись `started` с тем же `request_id`, в том числе у пробы с 3,124 мс. На обычном уровне записано только завершение. Время внутри PF включает обработку `started` до вычисления `duration_ms`. Полное время также включает загрузку Python и Core и запись результата.

Для SQL загрузите модуль из `src` **установленного** Core. На RC1 создайте `ProcessEventJournal(storage_host=host)` с конфигурацией проекта и его workplace. Эту привязку использует и `ProcessEventRecorder().event_journal_for_project(project)`. В одном процессе измерьте `journal.page(path, after=0, limit=100)` один раз и ещё 20 раз. Сверяйте длину и порядок ID. На этом устройстве попытка дословно повторить конструктор beta3 без привязки дала `storage_host_required`. Проба с привязкой вернула одни и те же 100 событий во всех повторах. Для MCP измеряйте вызовы последовательно от обращения к подключённому инструменту до получения ответа, записывая режим, статус и решение политики. Здесь использованы часы клиента с разрешением 1 мс.

### Что объясняют измерения

- Медиана внешнего времени обычной команды в #110 в **3,35 раза** выше. На обоих устройствах общее время существенно превышает внутреннее. В отдельном прогоне cProfile RC1 для подробной команды из 1,564 с профиля суммарно 0,530 с занял захват публикации Core, среди крупных собственных затрат были `stat`, компиляция и открытие файлов. В #110 также выделялись компиляция и открытие файлов. Эти затраты не измеряют скорость маршрутизации события.
- Переключение на debug подняло медиану внутреннего времени с 1,481 до 95,942 мс здесь и с 4,962 до 531,764 мс в #110. Различия медиан полных запусков между профилями укладываются в наблюдавшийся разброс. Семь пар не дают надёжной оценки постоянной надбавки для всего процесса.
- Несмотря на примерно в 17 раз меньшую историю событий, локальная страница заняла в **4,23 раза** больше времени. В отдельном профиле 20 чтений RC1 на `adapter_identity_access` пришлось 1,266 с из 1,336 с. Профиль beta3 занял 0,115 с, среди основных затрат были декодирование JSON и запросы SQLite. Обе страницы ограничены 100 строками, но путь допуска различается.
- MCP на RC1 вернул свежий контекст за медианные **4,458 с**, на beta3 — устаревший за **47,863 с**. Здесь различаются результаты запросов, история, Python, SQLite и версия ядра. Эти две установки дают ориентир для конкретных операций. Чтобы приписать разницу версии PF, потребуется прогон на одном устройстве с одной историей, конфигурацией и одинаковым исходом.

## Аудит документации

Проверка исходного дерева `a4ecea35` охватила 404 Markdown-файла из README, QUICKSTART, CONTRIBUTING, `docs/` и `prompts/` на двух языках. 72 датированных аудита, релизных страницы и черновика учитывались как исторические материалы. На исходной ревизии все 945 проверенных относительных ссылок указывали на существующие пути. Парсер CLI принял 730 самостоятельных примеров из shell-блоков текущих документов. 15 динамических или справочных примеров исключены из разбора. Это проверка синтаксиса. Поведение сверялось отдельно по следующим механизмам.
