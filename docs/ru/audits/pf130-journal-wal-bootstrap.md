# Активация WAL при одновременном старте журналов

Исправление поддерживает работу над производительностью журналов к 1.3.0.
Несколько воркеров могут обратиться к новому журналу событий или raw hooks до
включения WAL. При смене режима SQLite может сразу вернуть SQLITE_BUSY даже с
настроенным ожиданием. Раньше адаптер сразу отказывал в операции.

Теперь повторяется только активация WAL до публикации. Курсор каждой попытки
закрывается перед ожиданием. Единый бюджет по монотонным часам берётся из
действующего busy_timeout; последующим native-попыткам передаётся остаток.
Исходный timeout восстанавливается до доменной записи или закрытия соединения.
Повторяется только первичный SQLITE_BUSY. Другие ошибки, исчерпание бюджета и
возврат режима, отличного от WAL, приводят к отказу.

Сохраняются быстрый путь уже включённого WAL, FULL, проверки заголовков,
миграционный барьер, допуск владельца и чтение без записи. Создание схемы, BEGIN,
доменные записи, dispatch и тело вызывающей операции не повторяются.

## Проверка

К существующему bootstrap-набору добавлены четыре регрессии. Все девять случаев
выполнены на настоящих Windows и Linux без пропусков:

- Отдельный процесс удерживает реальную reserved-блокировку корректного журнала
  в DELETE. Он коммитит после наблюдаемого SQLITE_BUSY у конкурента. Оба адаптера
  сохраняют исходную запись и данные владельца блокировки и добавляют одну запись.
- Реальная конкуренция при бюджетах 0 и 60 мс завершается отказом без публикации.
  Проверяются восстановление timeout и закрытие курсоров попыток.
- Инъекции nonbusy, отсутствующего кода и SQLITE_LOCKED проверяют классификацию.
  Отказ при фактическом режиме, отличном от WAL, проверяется на in-memory SQLite.
- Сохраняются проверки чередования инициализаторов, чужих и частичных заголовков,
  неизвестной схемы, чтения без записи и миграционного барьера.

Неизменённый smoke с шестью процессами проверяет 301 уникальную конкурентную
запись, дедупликацию, историю в 100000 записей, индексный поиск, rollback и
восстановление dispatch. Успешные результаты native Windows и Ubuntu CI на
итоговом коммите обязательны для доставки.

Локальные Linux failures сохранены рядом с успешными узкими тестами. Трасса
показала непрерывные успешные записи одного процесса, пока конкуренты исчерпывали
десятисекундное ожидание допуска при медленных FULL-коммитах. Исправление не
обещает справедливую очередь writer, не повторяет транзакции и не увеличивает
timeout ради прохождения нагрузки. Полный Linux-сценарий должен пройти CI до merge.

[Документация busy handler](https://sqlite.org/c3ref/busy_handler.html) описывает
возможность обхода обработчика при повышении блокировки.
[Контракт journal_mode](https://sqlite.org/pragma.html#pragma_journal_mode)
требует проверять фактически возвращённый режим. Изменение не вводит новую схему,
backend, глобальную блокировку или объединение баз.
