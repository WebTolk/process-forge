## Конечная таблица маршрутов

Владелец — явный project ID, workplace ID или accounting origin ID, выбранный
хостом, и конкретный store UUID после adoption. Имя каталога не создаёт эти
идентичности. SQL execution facts, YAML Work stages, неизменяемые ресурсы и
совместимая проекция сохраняют разных владельцев истины.

| Существующий маршрут / вход | Источник → цель; владелец | Запрет при active / unknown и восстановление |
| --- | --- | --- |
| Инспекция: `tools/migrate-storage.py --inspect` / `StorageMigrationService.inspect` | Выбранные существующие stores → ограниченная диагностика; точные корни владельца | Не создаются UUID, pin, DDL, history scan или proof миграции. Pending сообщается как блокировка. |
| Автоматическое обновление / первая безопасная запись: host `ensure_ready` | Непривязанный распознанный legacy → те же выбранные цели | До pending fence active/unknown откладывает переход, сохраняя распознанный legacy route. Флаг, PID и пустой registry не являются доказательством. Повтор после настоящего terminal collection или следующей mutation. |
| Adoption существующих events/raw/accounting/search: `_target` | Распознанная legacy domain schema → тот же файл плюс `store_identity@1`; явный domain owner | Доказанное поколение хоста перепроверяется под admission. Pending pin предшествует mutation БД; WAL-aware backup и parity предшествуют ready. Resume использует прежние план/UUID; foreign/unknown schema не перемаркируется. |
| Явная свежая инициализация | Отсутствующий store в действительно новом потоке → новая identity/envelope и выбранный namespace | Pending предшествует файлу/binding. Прерванная инициализация использует прежний UUID. Forced onboarding существующего состояния не делает его новым. |
| Импорт execution: `_execution` / `ExecutionMigrationService.apply` | Замороженные наблюдаемые legacy status snapshots и allocation floors → `execution@1` + `execution_migration@1`; точные project/store/profile/relative target | Freeze/resume/pre-cutover перепроверяют pins источника и safety generation. Binding закрывает route до schema/import mutation. Порция содержит не более 256 units; import и checkpoint коммитятся вместе. Только проверенный SQL CAS переводит generation 0/legacy/importing в 1/sql/ready. |
| Pending и committed recovery: `--resume` / точный service plan | Существующие selector, descriptor, source manifest, backup и checkpoint → та же цель | Нет выбора newest plan, второго UUID/backup и JSON fallback. Abort ограничен состоянием до mutation; после namespace/import commits восстановление идёт вперёд. Готовая цель сохраняется при отказе следующей. Исправление производного отчёта не отменяет SQL authority. |
| Чтение/attach привязанного SQL: `select_execution_storage` | Точные binding/profile/envelope → repository одной операции | UUID metadata сама не даёт доступа или cutover. Missing/corrupt/foreign/future store, другой owner, изменённые profile/path, неподдерживаемый checksum и непривязанный execution namespace отказываются. Старый status JSON не импортируется повторно. |
| Перенос всего проекта offline, затем новый selector | Закрытый fixture project → переименованный корень; прежние relative binding/target и явные IDs | Новый selector открывает перенесённый SQL store и сохраняет историю. Это не квалификация переноса live Work/Workplace ownership, native publications или произвольного retarget database profile. |
| Restore: `SQLiteBackupService.restore` | Проверенный bundle → отсутствующий новый файл в существующем безопасном каталоге | Существующая цель запрещена. Точные UUID/байты восстанавливаются без смены live binding и без нового pin; adapter access отказывает восстановленной envelope без совпадающего pin. |

Native cold-v1 attach/update остаётся отдельной границей. См.
[T04](pf130-t04-runtime-20261112.md) и задачи
[#13](https://github.com/WebTolk/process-forge/issues/13) /
[#16](https://github.com/WebTolk/process-forge/issues/16).
Synthetic cold reset, issuer и closure fixtures — компонентные доказательства;
они не означают настоящий reboot, Q0, deployment или разрешение для всего устройства.

## Неподдерживаемые сочетания и границы транзакций

Команда миграции предоставляет inspect/apply/resume; общего режима attach,
live relocation или reverse export у неё нет. `SchemaManager.apply` регистрирует
отсутствующие namespaces и запрещает менять версию/checksum существующего.
Restore или rename каталога не разрешает rollback на старый Core: SQL commits
требуют отдельно квалифицированного reverse export перед таким откатом.
Основание — фактические entry, schema manager и selector, а не неудачный
глобальный поиск текста. Универсальные backends, автоматическое присвоение
неизвестных remnants и объединение всех доменов в одну БД вне этой квалификации.

Backup, source scans, manifest reads и внешние операции находятся вне SQL
transactions. Сериализация цели и короткий admission защищают публикацию;
SQLite `data_version` и physical identity обнаруживают drift при отпущенном gate.
Spawn/signal/wait не добавляется как тест quiescence. Maintained suites проверяют
атомарность checkpoint, WAL-only writes, physical replacement, запрет pending
access, независимость целей и сохранение ready authority.

## Воспроизводимые доказательства

Новый `tests/execution_migration/test_storage_qualification.py` содержит **20
случаев**, все выполнены успешно на настоящих Windows и Linux:

- Физический offline rename, новый production selector, прежние явные IDs,
  binding/history и неизменные непрозрачные fixture resources, даже при повреждении
  бывшей JSON projection.
- Четырнадцать отказов bound route без relabel, пересоздания цели и JSON fallback.
- Настоящий hardlink и перенаправление owner/target-parent directory: Windows
  junction и Linux symlink, без подставных результатов файловой системы и skip.
- Конфликт identity gate с другим процессом, затем успешный доступ после освобождения.
- Restore в новую цель, запрет перезаписи, прежний UUID и отказ выдумать adapter binding.

Подготовка миграции в fixtures использует maintained deterministic host proof.
Она доказывает алгоритм; последующие selection, filesystem, restore и
межпроцессный gate используют настоящие production ports. Непрозрачные fixture
resources проверяют сохранность байтов, а не новый YAML Work/resource-admission
процесс. Успешная команда не превращает injected proof в OS ownership.

CI jobs **Storage (windows-latest / ubuntu-22.04)** выполняют целиком
`tests/execution_migration` и `tests/database` на точном head PR и публикуют
JUnit `storage-results-*`, включая ошибки и причины skip. Используются Python
3.11, runtime requirements и pinned pytest 9.1.1, изолированные consumer fixtures
без production services:

```text
python -B -m pytest -q -ra --capture=sys -p no:cacheprovider \
  --basetemp=<owned-scratch>/pytest --junitxml=storage-results.xml \
  tests/execution_migration tests/database
```

Workflow задаёт все maintained fixture roots внутри собственного scratch.
Skip или недоступный обязательный сценарий не является PASS. В частности,
зависящие от прав Windows leaf-symlink проверки, Windows-only ACL/handle/Job и
namespace сценарии сохраняют фактическую применимость; synthetic host/cold
positives остаются ограниченными. Native Linux CI проверяет свойства файловой
системы, которые нельзя установить на смонтированном Windows filesystem.
Существующие Linux native и Runtime checks также входят в приёмку; не заявляется,
что каждый platform-specific сценарий выполнен на обеих ОС.

Расширенный набор получает `W332_SOURCE` из того же checkout и Windows fixture
venv, созданный через `--without-pip`, для `NATIVE_FIXTURE_PYTHON`.
Отсутствующие Windows prerequisites остаются ошибками. Проверки Windows
boot/token/SDDL и material sharing имеют точные platform markers; потребители
Windows redirector/material-handle fixture явно ограничены Windows. Policy,
настоящие lock и hardlink проверки продолжают выполняться на Linux. Два cold-v1
adoption/resume случая проверяют успешные synthetic-provider потоки на Windows,
а на Linux — отказ до adoption journal/epoch; их Linux outcomes не доказывают
положительные adoption или resume. Существующие Windows Job тесты включают
эмуляцию POSIX snapshot selection на Windows, а не настоящую POSIX syscall
квалификацию. Отдельный Linux native job покрывает реальный native lifecycle.

Проверка импорта maintenance наблюдает возврат из настоящего native
`bootstrap_entry` в свежем subprocess. Она проверяет отсутствие обоих целевых
модулей, затем включает прежние запреты Path open/stat/mkdir и SQLite connect
до их первого импорта и создания команды. Нет подмены `sys.modules` или обхода
доверенного package entry. Существующий normal-route admission wrapper
передаёт production deadline keyword.

Штатные lint/format/typecheck и IDE inspections охватывают изменённые Python файлы;
public schema/checksum/cleanliness проверки — доставку. PR и локальные PF receipts
связывают фактические JUnit outcomes, review, окончательный head и принятый merge
tree. Независимое ревью выполняет PF shell worker с Astra. Акт передаётся в
[#20](https://github.com/WebTolk/process-forge/issues/20) и
[#22](https://github.com/WebTolk/process-forge/issues/22); готовность всего релиза
1.3.0 не объявляется.
