# Upgrading To ProcessForge 1.2.0

This procedure is for the operator maintaining an existing installation.
An ordinary project agent reports infrastructure blockers rather than updating
Core or restarting services. For a new installation, use the
[installation guide](../getting-started/installation.md).

## 1. Prepare And Review

Check [requirements](../requirements.md), download the intended release archive
and verify its SHA-256 against its published sidecar. Keep the exact version,
tagged commit and hash in private upgrade evidence. Back up project/workplace
state and review local changes to PF-owned files. Keep project scratch in
`.pf/tmp/`; do not put backups of private state in public release assets.

Use the currently installed CLI to inspect status and preview the manifest-based
update. Supply the existing workplace so any archive-declared compatible
workplace migration is included:

```bash
python <core-root>/bin/pf.py core-update status --core-root <core-root>
python <core-root>/bin/pf.py core-update plan --core-root <core-root> --archive <release-archive> --workplace-root <workplace-root>
```

Review additions, changes, removals, local-modification conflicts and backups.
The plan is read-only. Do not use `workplace-init` to upgrade an existing workplace.
See [Core update details](../concepts/core-update-manifest.md).

## 2. Apply Core In A Maintenance Window

If old journal writers are active, stop them through the existing operator
lifecycle procedure and keep them stopped through journal migration. Avoid
concurrent Core/workplace updates. After reviewing the plan, explicitly apply:

```bash
python <core-root>/bin/pf.py core-update apply --core-root <core-root> --archive <release-archive> --workplace-root <workplace-root> --confirm
python <core-root>/bin/pf.py core-update status --core-root <core-root>
python <core-root>/bin/pf.py version
python <core-root>/bin/pf.py doctor-workplace --root <workplace-root>
```

Local changes to PF-owned files block apply unless explicitly overridden.
Unknown files are preserved. If status reports `incomplete_update`, stop and
inspect `core-update repair --core-root <core-root>`; it classifies recovery
needs and does not promise automatic rollback.

## 3. Migrate Legacy Journals Where Needed

Core installation does not import old project event or raw-hook journals.
For each project with legacy journals, back up the frozen sources, then run
the migration utility from the updated distribution root:

```bash
python tools/migrate-hook-journals.py --project-root <project-root> --workplace <workplace-root>
python tools/migrate-hook-journals.py --project-root <project-root> --workplace <workplace-root> --apply
```

The first command previews without creating a project database. Review its
diagnostics before apply. Verify both journals are `ready` before resuming
writers with the new Core. An unfinished import blocks normal access; correct
the cause and rerun the same import to resume. Original files remain unchanged,
and later legacy appends are not mirrored automatically. Already migrated
projects need no repeat import merely to reconnect a host.

Store SQLite databases, WAL and shared-memory files privately on local storage.
Use SQLite's backup API for a live database backup. See the
[journal migration reference](../concepts/hook-journal-sqlite.md) for source
selection, validation and recovery.

## 4. Verify Entry And Continue Exact Work

Review inherited `logging.raw_hooks`, `logging.events` and
`runtime.garage_hooks` before changing collection policy. Garage hooks default
to disabled; optional history settings do not stop explicit Work or chat.

In each affected project, inspect the current root `AGENTS.md` contract and local
instructions. Existing START files are preserved; `agent-start-prompt` previews
without writing by default. Project entry migration is a separate reviewed
operation. Release, process, schema and startup-contract versions are independent.

```bash
python <core-root>/bin/pf.py doctor-project --project-root <project-root>
python <core-root>/bin/pf.py project-context-check --project-root <project-root> --json
```

If context is stale or broken, follow its required operator action before
dependent work. Core update does not rewrite approved capsules or process pins.
Use exact continuation selectors to resume existing Work, as shown in the
[agent runbook](../getting-started/agent-prompts.md#continue-work-without-mcp).
Scope changes require a governed handoff. Terminal Work cannot launch another
native worker attempt.

If Runtime or a connected MCP host is used, refresh it through the operator's
existing lifecycle procedure and verify the version actually loaded by that
host. A new Runtime process alone does not prove host reload. File-only mode
requires neither service. For collection recovery, inspect the current refusal
and inputs before explicit manual collection or a new attempt; an old successful
capture does not qualify changed source bytes.

Review the [release notes](1.2.0.md) and [known limitations](../known-limitations.md)
before returning the installation to ordinary use.
