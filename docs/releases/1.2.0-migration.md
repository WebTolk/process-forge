# Migrating to the 1.2.0 checkpoint

Use the existing [manifest-controlled Core update](../concepts/core-update-manifest.md)
planning and verification flow. Review local modifications and required preimages
before an explicit apply. Candidate, archive, installed Core, Runtime and the
actual connected host require their own evidence.

Existing Work retains its immutable context and process version. Continue with
exact run/assignment/context selectors. Scope changes use the existing governed
handoff/continuation path. Terminal Work cannot start a new native worker attempt.
Updating Core does not silently migrate old process definitions or capsules.

The release version becomes 1.2.0; schema and startup-contract versions retain
their independent compatibility contracts. Project entry migrations require
review of the current contract and local instructions. Existing START files are
preserved; the default start-prompt operation is a preview.

Stable automatic collect refusal is visible as recovery required. Inspect its
reason and current inputs before using explicit recovery/manual collection or
a new attempt. Historical successful capture remains an observation of that
attempt, rather than fresh acceptance of changed source. Transient I/O/locking
failures remain retryable.

Internal module ownership continues to change during refactoring. Existing
external CLI/MCP and storage contracts are qualified at the affected boundaries;
the presence of a new class alone does not establish completed migration.
Egress qualification remains implementation-bound and opt-in; use its existing
qualification flow when the implementation identity changes.

Review the [release notes and known qualification limits](1.2.0.md) before
choosing this intermediate checkpoint for an installation. No automatic service,
host-hook or connected-session restart follows from these notes.
