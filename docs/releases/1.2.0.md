# ProcessForge 1.2.0 — intermediate refactoring checkpoint

Candidate for review; public publication is pending qualification and explicit
maintainer approval.

This version fixes an intermediate point in the ongoing Core refactoring.
The complete migration of CLI, MCP and Daemon to independent Core services
continues after this version. A new Kernel, DI container or plugin engine is
not a prerequisite for this checkpoint.

Existing responsibilities now have concrete Core owners for Work/context and
material reads, process/catalog and snapshot reads, context/resource policies,
selection, evidence/completion rules and event journals. Command and parser
classes delegate selected use cases to these services. Default bootstrap and
some composition paths still depend on the legacy facade; the five OOP program
areas remain open.

The accepted set also includes performance and recovery changes: verified exact
Work selection avoids unrelated history scans; journal snapshots preserve
bounded reuse across project interleaving; supervisor observes an already
captured attempt as history; stable semantic collect refusals stop automatic
repetition with a visible recovery reason. First/manual collect and new attempts
retain full checks, and transient failures remain retryable. These behavior
decisions are distinct from structural code movement.

Project entry uses root `AGENTS.md` and current PF context. Onboarding/repair
preserve existing START files; `agent-start-prompt` defaults to a no-write
preview, with explicit compatibility placement still available.

Release, process, schema and startup-contract versions have separate meanings.
This checkpoint does not rewrite historical capsules, process pins or approved
inputs. See the [migration notes](1.2.0-migration.md).

CLI parser construction defers egress initialization until an egress command
executes. Unrelated commands avoid that startup work; egress implementation
identity, qualification and transport guards keep their existing semantics.
This change is platform neutral.

The diagnostics smoke now verifies complete append-or-refusal accounting under
the existing optional best-effort contract. It retains the 50 ms admission
budget, shared-budget/late-grant controls, exclusion, mixed writers and storage
checks. Uncontrolled filesystem stalls no longer imply a loss-free guarantee.
The diagnostics implementation is unchanged.

Large retained histories can still increase Runtime scheduler CPU and admission
cost. Earlier private-dev timings are workload observations, not a universal
performance promise. No experimental cross-request YAML payload cache was
accepted. Final source, archive, installed Core, Runtime and connected-host
qualification remain separate evidence layers.

Broad smoke-test audit/cleanup and device-wide launcher model policy are separate
follow-up work. Public tag, release assets and the stable update channel remain
unchanged until the release decision.
