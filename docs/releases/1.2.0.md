# ProcessForge 1.2.0

ProcessForge 1.2.0 improves responsiveness when selecting Work and reading
context, and makes worker recovery easier to understand. Start with the
[requirements](../requirements.md) and follow the
[upgrade and migration steps](1.2.0-migration.md) for an existing installation.
Download availability, the tagged source commit and archive SHA-256 belong to
the published release assets; these notes are not a publication receipt.

## What Changes For Users

- Selecting an exact Work avoids scanning unrelated history. Repeated context
  reads reuse unchanged parsed documents while still checking current files
  and permissions. Improvements depend on the size and shape of your workload;
  large retained histories can still cost CPU and memory.
- Project event and native hook journals use separate local SQLite databases.
  Indexed admission and replay reduce repeated history reads. Existing legacy
  journals require an explicit migration; installing Core does not import or
  delete them.
- A completed worker capture remains visible as history. A stable automatic
  collect refusal reports that recovery is required instead of repeating the
  same refusal indefinitely. Transient I/O and locking failures remain retryable.
  A worker result and Runtime operational health are reported separately.
- Work continuation keeps the selected Run, assignment, immutable context and
  pinned process. A session change does not authorize a different assignment
  or wider scope. See [continuation](../concepts/work-continuation.md).
- Project entry uses root `AGENTS.md` and current context. Existing START files
  are preserved, and `agent-start-prompt` previews guidance without writing by
  default. Prepared workers follow their supplied input without needing a PF
  MCP connection or creating another Work.
- Project scratch belongs in `.pf/tmp/`. The optional app-server can notify
  you about old files after a configurable number of hours; it never deletes
  them or guesses relevance from Work history. See [temporary files](../temporary-files.md).

## Optional Infrastructure And Privacy

File-only Garage work remains available without PF Runtime. Runtime, worker
orchestration and host telemetry are optional capabilities with their own setup.
Automatic Garage hooks are disabled by default and can be enabled through
inherited `runtime.garage_hooks`; Forge retains its required checks.

`logging.raw_hooks` and `logging.events` control optional history independently.
Disabling history preserves minimal admissions and pending processing; it does
not stop explicit Work or chat delivery and does not erase earlier data.
Keep SQLite databases and their WAL/shared-memory files private on local
storage. See [configuration](../authoring/workplace-configuration.md#project-history-and-raw-hooks).

Keep repository scratch under `.pf/tmp/`, with a separate directory per writer.
Preserve live or unrelated files when cleaning up.

## Before Upgrading

Back up local state, review the Core update plan and migrate legacy project
journals during a controlled maintenance window. Updating Core does not rewrite
existing capsules, process pins or approved inputs. Reloading a connected MCP
host is a separate operator action; it is not proven by a new Runtime process.

See [migration](1.2.0-migration.md) for commands and completion checks, and
[known limitations](../known-limitations.md) for supported boundaries. Validation
on one operating system does not establish acceptance on every other platform.

Implementation details and historical measurements belong to the developer
references: [document reads](../concepts/document-reads.md),
[journal storage](../concepts/hook-journal-sqlite.md) and
[Work selection audit](../audits/canonical-work-selection-20261016.md).
