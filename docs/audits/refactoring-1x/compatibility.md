# Контракты при рефакторинге ProcessForge 1.x

Для каждого среза фиксируются опубликованный договор 1.3.0 и точный актуальный `dev` с принятыми #119 и #120. Для выпуска проверяется поддерживаемый переход с последнего стабильного архива и существующими данными. Исправление документированного дефекта записывается как ожидаемое изменение в своём сценарии. ## Правила проверки

1. Сценарий и допускаемую разницу записать перед изменением. Использовать текущие `tests/mcp_bridge`, `smoke_workplace_search_index.py`, `smoke_work_transition_commit_service.py` и подходящие release consumer gates. Для регрессии добавить минимальный отсутствующий сценарий.
2. Сохранить проверки admission, auth, freshness и совместимых fallback в прежнем порядке. Вывод результатов, ошибок и сигнал завершения держать на границе транспорта. В Core передаются структурированные факты и причины с явными зависимостями.
3. Проверить правильность источника результата на каждой платформе. Записать точные revision, OS/kernel, Python/SQLite, вход, ожидаемый и фактический ответ, exit, состояние до и после. Source, archive, установленный Core, Runtime и реальный подключённый host — отдельные слои доказательства.
4. Сверить штатное чтение и запись ранее созданных данных, locks, retry/replay, восстановление из неполного состояния и гарантию предыдущего version pin. Учитывать реальные платформенные режимы. Fixture, skip и mock покрывают лишь указанное условие.

## Допустимое расширение

Совместимое расширение требует конкретного поддерживаемого сценария, который имеющимся контрактом выполнить нельзя. Сначала проверяется возможность решить его изменением внутреннего владельца. Для действительно нужного расширения записываются минимальная новая возможность, version/negotiation, прежние defaults, старые клиенты и неизменные данные, пример миграции и обратное чтение. В минорном плане сохраняют существующие команды, endpoints, aliases, payload и политики. Для отдельного расширения нужен собственный тест совместимости и публичная документация.
