# PF 1.3.0 T05 — supported storage routes

Date: 2026-11-13. Task: [#17](https://github.com/WebTolk/process-forge/issues/17);
release map: [#12](https://github.com/WebTolk/process-forge/issues/12).
Source baseline: `c4d5fabec80eb67d95186e61d5990f257f175103`.
This qualification adds tests and CI; it changes no product storage code.
The governing contract is [Execution storage and authority](../concepts/execution-storage.md).

## Finite route table

“Owner” below means explicit project ID, workplace ID or accounting origin ID
selected by the host, plus the concrete store UUID after adoption. A directory
name supplies none of these identities. SQL execution facts, YAML Work stages,
immutable resources and compatibility projections retain distinct authorities.

| Existing route / entry | Source → target; owner | Active / unknown boundary and recovery |
| --- | --- | --- |
| Inspection: `tools/migrate-storage.py --inspect` / `StorageMigrationService.inspect` | Selected existing stores → bounded diagnostic; exact owner roots | No UUID, pin, DDL, history scan or migration proof is created. Pending is reported blocked. |
| Automatic update / first safe write: host `ensure_ready` | Unbound recognized legacy stores → the same selected targets | Before a pending fence, active/unknown defers with the recognized legacy route retained. A flag, PID or empty registry is no proof. Retry after genuine terminal collection or on the next mutation. |
| Existing events/raw/accounting/search adoption: `_target` | Recognized legacy domain schema → same file plus `store_identity@1`; explicit domain owner | A proven host generation is rechecked under admission. Pending pin precedes database mutation; WAL-aware backup and parity precede ready publication. Exact plan/UUID resumes; foreign/unknown schema is not relabelled. |
| Explicit fresh initialization | Absent store in a genuinely new flow → new identity/envelope and selected namespace | Pending precedes file/binding creation. Interrupted initialization reuses the same UUID. Forced onboarding of existing state is not a fresh-start exemption. |
| Execution import: `_execution` / `ExecutionMigrationService.apply` | Frozen observable legacy status snapshots and allocation floors → `execution@1` + `execution_migration@1`; exact project/store/profile/relative target | Freeze/resume/pre-cutover revalidate source pins and safety generation. Binding fences the route before schema/import mutation. Batches have at most 256 units; import and checkpoint commit together. Only the verified SQL CAS changes generation 0/legacy/importing to 1/sql/ready. |
| Pending and committed recovery: `--resume` / exact service plan | Existing selector, descriptor, source manifest, backup and checkpoint → same target | No newest-plan selection, second UUID/backup or JSON fallback. Abort is restricted to pre-mutation state; after namespace/import commits recovery rolls forward. One ready target is retained if a later target fails. Derived report repair does not reverse SQL authority. |
| Bound SQL attach/read: `select_execution_storage` | Exact binding/profile/envelope → operation-local repository | UUID metadata alone grants neither access nor cutover. Missing/corrupt/foreign/future store, owner mismatch, changed profile/path, unsupported checksum and an unbound execution namespace refuse. Old status JSON is not reimported. |
| Offline whole-project move, then a fresh selector | Closed fixture project → renamed root; unchanged relative binding/target and explicit IDs | The new selector opens the moved SQL store and retains history. This does not qualify moving live Work/Workplace ownership, native publications or arbitrary database-profile retargeting. |
| Restore: `SQLiteBackupService.restore` | Verified bundle → absent new file in an existing safe directory | Existing output is refused. Exact UUID/bytes are restored without changing a live binding or minting a new pin; a restored envelope with no matching pin is refused by adapter access. |

The native cold-v1 attach/update boundary remains separate from these SQL
routes. See [T04](pf130-t04-runtime-20261112.md) and issues
[#13](https://github.com/WebTolk/process-forge/issues/13) /
[#16](https://github.com/WebTolk/process-forge/issues/16).
Synthetic cold reset, issuer and closure fixtures are component evidence,
not a real reboot, Q0, deployment or device-wide approval.

## Unsupported combinations and transaction limits

The migration command exposes inspect/apply/resume; it supplies no generic
attach, live relocation or reverse-export operation. `SchemaManager.apply`
registers absent namespaces and refuses changing an existing namespace version
or checksum. A restore or directory rename is not a qualified old-Core rollback:
SQL commits require a separately qualified reverse export before such a rollback.
These limits follow the actual entry, schema manager and selector, not a failed
global text search. Universal backends, automatic adoption of unknown remnants
and merging all domains into one database are outside this qualification.

Backup, source scans, manifest reads and external operations occur outside SQL
transactions. Target serialization and short admission protect publication;
SQLite `data_version` and physical file identity detect released-gate drift.
No spawn/signal/wait is introduced as a quiescence test. The maintained suites
check checkpoint atomicity, WAL-only writes, physical replacement, pending
access refusal, independent target progress and retained ready authority.

## Reproducible evidence

The new `tests/execution_migration/test_storage_qualification.py` has **20
cases**, all executed successfully on real Windows and Linux. It checks:

- A physical offline rename, a fresh production selector, unchanged explicit
  IDs/binding/history and opaque immutable fixture bytes, even with a damaged
  former JSON projection.
- Fourteen bound-route faults, with no relabel, target rebuild or JSON fallback.
- A real hardlink and owner/target-parent directory redirection: Windows junctions
  and Linux symlinks, with no fabricated filesystem results or skip.
- Actual identity-gate contention from a separate process, followed by successful
  access after release.
- Restore into a new target, refusal to overwrite it, preserved UUID and refusal
  to invent an adapter binding.

Migration setup in these fixtures uses the maintained deterministic host proof.
That setup is algorithm evidence; the subsequent selection, filesystem,
restore and interprocess gate use actual production ports. Opaque fixture
resources test byte preservation, not a new YAML Work or resource-admission
workflow. A passing command never turns injected proof into OS ownership.

The **Storage (windows-latest / ubuntu-22.04)** CI jobs run the complete
`tests/execution_migration` and `tests/database` trees on the pull request's
exact head and publish `storage-results-*` JUnit artifacts, including failures
and explicit skip reasons. Commands use Python 3.11, runtime requirements and
pinned pytest 9.1.1, isolated consumer fixtures and no production services:

```text
python -B -m pytest -q -ra --capture=sys -p no:cacheprovider \
  --basetemp=<owned-scratch>/pytest --junitxml=storage-results.xml \
  tests/execution_migration tests/database
```

The workflow sets all maintained fixture roots inside owned scratch. A skipped
or unavailable required scenario is not a pass. In particular, account-dependent
Windows leaf-symlink checks and Windows-only ACL/handle/Job or namespace
scenarios retain their actual applicability; synthetic host/cold positives
remain explicitly limited. Native Linux CI qualifies filesystem cases that a
mounted Windows filesystem cannot establish. Existing Linux native and Runtime
checks remain part of acceptance, without claiming that every platform-specific
scenario ran on both operating systems.

Scoped shipped lint/format/typecheck and IDE inspections cover the new Python
file; public schema/checksum/cleanliness checks cover the delivery. The PR and
local PF receipts bind actual JUnit outcomes, review, final head and accepted
merge tree. Independent review uses a PF shell worker with Astra. This act is
input to [#20](https://github.com/WebTolk/process-forge/issues/20) and
[#22](https://github.com/WebTolk/process-forge/issues/22); it does not declare the
entire 1.3.0 release ready.
