## Publication, readers and existing serialization

`RuntimeServiceStateStore` stages beside the destination and atomically replaces
one of two `service-details.{slot}.json` files, then commits compact `service.json`
last. The control limit is 65,536 UTF-8 bytes; oversized projections fail before
publication. Details bind slot, length, digest and instance. A failed commit
preserves the previous committed control and its referenced details; an unused
slot or interrupted writer staging may remain. This is not power-loss durability.

Full status reconstructs matching diagnostics with bounded same-owner generation
retries; corrupt/missing/mismatched details degrade conservatively. Live starting,
stopping and failed lifecycle states remain distinguishable. Admission reads only
bounded control, fails closed on malformed/oversized/stopping/failed state and
does not load diagnostic slots. Monitor retains its separate bounded compatibility
reader. Protocol version is published in compact control for doctor inspection.

Runtime save retains operation leases/state serialization. Singleton acquisition
and cold token publication use existing native guards and rechecks. Project routes
retain exact root/owner binding; copied released admission contexts cannot stand
in for a live native lease. Shutdown retains deadline, admission/singleton/project
guards and current owner/worker checks. Rejected authorization must acquire current
write authority before diagnostics mutate. These mechanisms are not one universal
fence; a PID, terminal string, old preflight or elapsed age is not cleanup authority.

## Completion, journals and historical cleanup

Completion retains its run lock, immutable publication, intent/event identity and
dedupe/replay. Final-stage complete admission is rechecked under the existing lock.
Terminal intent validation checks saved history/predecessor compatibility and the
exact expected event set. Corruption tests are not proof of supported concurrent
cancellation writers or cryptographic history authenticity. The 18 fault points
span pre-intent retry, intent replay and terminal cleanup; they are not eighteen
durable-intent replays.

Journal bootstrap rechecks both headers under its existing serialized transaction
and refuses any foreign main-schema object. Rollback failure preserves the primary
body/COMMIT/cancellation exception with best-effort class-only unknown-outcome notes.
Native close failure, other Driver transaction implementations and power loss remain
outside that bounded correction.

Historical capture rejects ambiguous JSON and checks exact references, receipt
shape, immutable capsule bindings and saved output pins, without current body reads.
Duplicate fields, invalid receipt/marker shape or mismatched saved pins are history
misses; valid prepared metadata still permits a genuine semantic refusal observation.
Invalid prepared identity stays unknown and cannot authorize an invented observation;
malformed existing observations are retained without overwriting. Accepted scratch
cleanup separately verifies strict history, exact task/attempt, native absence,
SQL generation/revision/latest
record and resource authority. It checks again under the lifecycle lock after
external resource authorization, then publishes end-of-use. Physical disposal stays
outside lifecycle/SQL locks. History alone never permits deletion.

## Evidence and limits

The shipped `Runtime recovery` matrix selects 717 case IDs on real Windows and
Ubuntu 22.04 with Python 3.11/pytest 9.1.1. Cleanup selects the complete historical
collection/disposal/native lifecycle suites, including 41 capture-reader cases. Native Linux
has its separate execution profile. Exact-revision results:

| Profile | Windows PASS / SKIP | Linux PASS / SKIP |
|---|---:|---:|
| Runtime, 717 identical case IDs | 708 / 9 | 707 / 10 |
| Cleanup, 358 cases | 357 / 1 | 344 / 14 |
| Native Linux, 643 cases | — | 605 / 38 |

All 241 critical Runtime cases, 35 Work-start cases and 41 historical-pin
cases actually passed on both OS. Both Runtime jobs passed all 18 completion
fault points, malformed-intent no-write checks and six-producer SQL recovery:
301 concurrent unique events, 100303 history rows and indexed lookup.
Runtime's nine structural skips are six writers without explicit flush/fsync and
three worker-input-only capture checks; Linux also skips the Windows native-handle
case, which passed on Windows. Cleanup skips one Linux-native error case on
Windows, and private DACL/13 Windows-handle cases on Linux. Native Linux skips
29 Windows handle/Job cases plus those nine structural cases. Skips are not PASS.

[Repository checks](https://github.com/WebTolk/process-forge/actions/runs/43345453390)
and [native Linux](https://github.com/WebTolk/process-forge/actions/runs/43345453348)
passed all seven checks. Logs and unique-case XML were verified against the exact
revision. The reproducible selection, fixture environment and commands are in the
[pinned workflow](https://github.com/WebTolk/process-forge/blob/5589d6e9f59ef526b18bceab20dc18fb5bf6023b/.github/workflows/repository-checks.yml).
The 41 reader plus 79 verifier cases also passed locally: 120 on each OS, no skips.

New historical-metadata fixtures use actual producer/verifier with bounded
preparation/configuration ports, not a native worker launch. Output reads are guarded
dynamically; absence of required-source body reads also relies on static path review
because these fixtures declare none.

The profile uses isolated simple-coordination consumer fixtures and the Core
Work-start port instead of stdio MCP. Launch guards cover observed direct forbidden
service/model launches, not every possible descendant action. This does not accept
an installed Runtime, connected host, MCP transport, model session or cross-boot
recovery. Real child `os._exit` and controlled fault injection have distinct limits.

Retained failures include the original import-path launcher error, cold journal
bootstrap race (PR32), actual bounded Windows sharing refusal, six Linux consumer
onboarding refusals on mounted NTFS (`private_acl_unavailable`), and local concurrent
reader ENOENT failures without an established cause/pristine baseline. Native CI
qualifies its executed scenarios; it does not erase those local failures or qualify
the entire device. No locks or timeouts were bypassed to obtain acceptance.
