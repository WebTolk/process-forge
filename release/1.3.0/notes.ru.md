# ProcessForge 1.3.0

Если вы ведёте проект в обычной папке, теперь туда можно отправить штатного исполнителя Codex. Создавать репозиторий Git только ради запуска больше не требуется. Мы проверили весь путь на Windows и Linux — от выдачи задания до получения результата.

## Что изменилось в работе

- **Проще продолжить прерванную задачу.** На Windows и Linux ProcessForge проверяет, какие процессы принадлежат исполнителю. Если результат уже принят, повторный сбор возвращает его. В новых проектах PF ведёт отдельный список текущих исполнений, поэтому для их поиска не приходится перебирать все завершённые попытки.
- **После перезапуска Forge агент может вернуться к своей работе.** Подключение MCP восстанавливается после перезапуска службы или совместимого обновления ядра. Если служба остановлена, команда сообщает об этом. В Garage с задачами по-прежнему можно работать локально.
- **Прерванное обновление можно продолжить.** Обновляющая программа проверяет файлы и сохраняет исходные копии. Для перехода со стабильной 1.2.0 мы проверили обновление и семь сценариев восстановления на каждой из двух систем. [Проверка перехода с 1.2.0](https://github.com/WebTolk/process-forge/issues/19)

## Было — стало

На одном компьютере с Windows мы дали обеим версиям одинаковые 258 записей о запусках. Обе нашли те же 15 активных запусков в том же порядке.

| Поиск активных запусков | Было в 1.2.0 | Стало в 1.3.0 |
| --- | ---: | ---: |
| Первый поиск в новом процессе | 987 мс | 959 мс |
| Повторный поиск | 55 мс | 53 мс |

Это медианы семи первых и четырнадцати повторных поисков для каждой версии. На этом проекте разница при повторном поиске невелика.

Заметнее результат, когда несколько агентов подключаются одновременно. В отдельном тесте на Windows шесть клиентов регистрировали 12 сессий в двух проектах. Самая долгая регистрация до исправления в серии 1.3.0 заняла **2,95 с**. После исправления — **1,47 с и 1,72 с** в двух прогонах. Все 12 сессий попали в нужные проекты. [Замер регистрации](https://github.com/WebTolk/process-forge/pull/87)

В октябре мы измеряли похожую задачу на 570 записях. После прогрева поиск тех же 49 активных запусков занимал **3,44–4,55 с процессорного времени до исправления — 0,141 с после**. Это ускорение уже получили пользователи 1.2.0. [Октябрьское исправление](https://github.com/WebTolk/process-forge/commit/8f00ca1711f1d7ad276da61a9fcbec907da0cd36)

## Если у вас установлена 1.2.0

Сохраните резервные копии проекта и рабочего места. Дождитесь завершения исполнителей и остановите остальные процессы, которые пишут в проект. Запускайте проверенную программу обновления из каталога вне установленного ядра. В Forge параметр `--manage-runtime` позволяет ей самой остановить и снова запустить службу. Установка требует вашего подтверждения. [Обновление и восстановление](../../docs/ru/concepts/update-lifecycle.md)

Новые проекты сразу получают хранилища SQLite. Если существующий проект при записи сообщает `storage_migration_required`, остановите службу и выполните перенос по инструкции. При прерывании его можно продолжить с сохранённой контрольной точки. Если PF не может определить состояние старого исполнителя, понадобится проверка оператором. [Перенос истории и исполнений](../../docs/ru/concepts/sqlite-journal-maintenance.md)

Для нативного запуска исполнителей на Linux системе нужны разрешённые пространства имён пользователей и процессов, доступный `/proc` и Python 3.11+ с поддержкой pidfd. Это важно проверить, в частности, если PF работает в контейнере. [Требования Linux](../../docs/ru/concepts/linux-owned-execution.md)
