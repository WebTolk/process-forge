# ProcessForge 1.3.0-beta3 — сборка для разработки

Восстановлено обновление существующей файловой установки, у которой нет native-
регистрации. Проверенный архив распаковывается в отдельный каталог. Команды
`bin/pf.py core-update plan|apply` запускаются из него с явными путями установленного
Core, ZIP и, при необходимости, рабочего места. Для `apply` требуется `--confirm`.
Установщик должен находиться вне заменяемого Core; самостоятельная замена файлов
исполняемой установки без managed-регистрации не допускается.

Этот путь фиксирует и проверяет содержимое архива, последовательно выполняет
согласованные файловые обновления, сохраняет фактические исходные файлы и журнал
восстановления. Заменяются только файлы манифеста. После проверки содержимого
последним публикуется новый манифест. Приватные данные и процессы user/custom
сохраняются. Известный App Server рабочего места перед заменой должен быть
остановлен. Миграции рабочего места требуют своего штатного maintenance-пути.

Полная и незавершённая native-регистрация продолжают требовать строгого native-
обновления. Файловый путь не создаёт control, epoch, adoption или полномочия
миграции. Его блокировка не доказывает завершение всех сторонних интерпретаторов.

Если известный Windows App Server отклоняет аутентифицированную остановку,
внешний установщик поддерживает явную команду `server stop --force`. Перед
завершением проверяются текущий владелец и удерживаемый дескриптор процесса:
интерпретатор, командная строка и идентичность создания. Завершается только этот
процесс. Неоднозначный владелец, managed-установка, ошибка аутентификации или
недоступные сведения ОС по-прежнему приводят к отказу. Обычная остановка сохраняет
прежнее поведение. После обновления Core подключённые MCP-хосты переподключаются
отдельно.

Это обособленное исправление для dev-сборки. Общая приёмка Core, POSIX, RC и
стабильного релиза остаётся отдельной работой. Расширяемые maintenance-пакеты,
общие для Runtime и MCP, зафиксированы как дальнейшее архитектурное направление.
