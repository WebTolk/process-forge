# Участие в разработке ProcessForge

Для подготовки нового устройства используйте [инструкцию для агента](docs/ru/contributors/agent-setup.md):
общие пакеты знаний из отдельных репозиториев, проверка хешей и регистрация,
Python QA, инструменты, подключение MCP и подтверждение готовности.

[English version](CONTRIBUTING.md)

Правила относятся к людям и агентам, которые разрабатывают сам ProcessForge.
GitHub — площадка для принятых исходников, PR и ревью. Источник задач задаёт
[режим совместной работы](docs/ru/contributors/task-collaboration.md): для 1.3.0
по умолчанию первичен локальный PF, а GitHub отражает крупные задачи и результаты;
при явном выборе `github` issue создаётся до связанной Work. GitVerse зеркалирует
принятые исходники. Автоматический синхронизатор задач не предполагается.

## Начало работы в свежем клоне

До начала задачи прочитайте корневой `AGENTS.md` и это руководство. Предыдущая
переписка, чужая история `.pf` и запущенные службы PF для чтения и подготовки
клона не требуются. До содержательной разработки создайте свой локальный PF. Проверьте
текущую ветку, рабочее дерево и `git remote -v`, затем подготовьте рабочую ветку
от актуального `origin/dev` по правилам ниже, даже если clone открыл `main`.

Основные remote проекта:

| Remote | Репозиторий |
| --- | --- |
| `origin` | `https://github.com/WebTolk/process-forge.git` |
| `gitverse` | `https://gitverse.ru/webtolk/process-forge.git` |

В свежем клоне с GitHub уже есть `origin`. Если `gitverse` отсутствует, добавьте его:

```sh
git remote add gitverse https://gitverse.ru/webtolk/process-forge.git
```

Если репозиторий клонирован с GitVerse и единственный remote называется `origin`,
переименуйте его в `gitverse`, затем добавьте GitHub как `origin`. Сначала проверьте
существующую конфигурацию; не заменяйте другую настройку вслепую. Используйте
доступные учётные данные GitHub и авторизацию GitVerse через токен. Токены нельзя
помещать в URL remote, аргументы команд, журналы и файлы. Отсутствие учётных данных
блокирует удалённую доставку, но не локальный анализ; назовите недостающий доступ.

## Ветки и доставка изменений

`dev` — интеграционная ветка, `main` — релизная. Обычные изменения направляются
в `dev` через PR. Не коммитьте и не отправляйте изменения задач прямо в эти ветки.
Рабочую ветку выбирайте по характеру работы:

| Ветка | Когда подходит |
| --- | --- |
| `fix/<тема>`, `docs/<тема>`, `chore/<тема>` | Отдельная задача или исправление. |
| `feat/<тема>` | Функция, которая поставляется одним или несколькими связными PR. |
| `work/<разработчик-или-агент>` | Постоянная рабочая ветка с регулярной синхронизацией с `dev`. |

Названия — соглашение, а не обязательные идентификаторы. Номер существующего Issue
можно добавить в имя. В режиме `local_pf` основанием Work может быть локальная
задача или принятое поручение без issue. В режиме `github` до Work нужно прочитать
или создать issue и привязать его URL. Один issue может включать несколько Work,
итераций и PR. Ссылки хранятся в дополнительных полях проекта/Work по инструкции
совместной работы.

Обязательный маршрут: **рабочая ветка -> проверки -> коммит -> push -> PR в `dev`
-> ревью и CI -> merge**. Поручение реализовать задачу включает этот маршрут,
если пользователь явно не ограничил результат планом, локальной правкой или другой
границей. Агент не должен требовать повторения правил проекта для каждой задачи.

1. Прочитайте задачу и применимую документацию. Проверьте Git и удалённые ветки,
   определите границы результата, сохраните чужие локальные изменения.
2. Создайте ветку от актуальной `origin/dev` или синхронизируйте существующую:

   ```sh
   git fetch origin
   git switch -c fix/example origin/dev
   ```

   В долгоживущей ветке `git merge origin/dev` переносит принятые изменения без
   переписывания общей истории. Согласуйте владение, если веткой пользуются другие
   исполнители. После разрешения конфликтов повторите затронутые проверки.
3. Реализуйте задачу и обновите документацию поведения. Не включайте несвязанные
   исправления. Выполните применимые проверки, добавьте явные пути в индекс,
   проверьте `git diff --cached`, сделайте содержательный коммит: например,
   `fix: ...` или `docs: ...`. Несколько поясняющих коммитов допустимы.
4. Отправьте рабочую ветку на GitHub и создайте PR с **целевой веткой `dev`**.
   Укажите существующий Issue. Ветка разработчика может использоваться для нескольких
   последовательных PR. Независимые изменения разделяйте, если общий diff мешает ревью.
5. Разберите замечания и дождитесь применимых проверок. Выполните merge через PR
   при наличии полномочий и выполненных требований ревью. Не обходите провалы
   и не объявляйте отсутствующие платформенные результаты успешными. Если доставка
   упирается в права или обязательное ревью, оставьте готовый к проверке PR и назовите
   точное ограничение.
6. Получите итоговый `dev`, отправьте тот же коммит в GitVerse и прочитайте обе
   удалённые ветки для проверки полного SHA. Не создавайте отдельный коммит зеркала
   и не применяйте force push к общим веткам. Сохраняйте ветки для продолжения работы.

Продвижение продукта в `main`, теги и артефакты выполняются по отдельной
[процедуре релиза](docs/maintainers/release-publishing.md). Явно порученный перенос
инструкций для контрибьютеров выполняется отдельным проверенным PR в `main`;
он не должен переносить незавершённые изменения продукта или менять теги и каналы
релизов. После слияния также зеркалируйте и проверьте полученный `main`.

## Окружение и проверки

Используйте Python 3.11+ и изолированное окружение с `requirements.txt`. Инструменты
разработки устанавливаются в отдельное QA-окружение либо используются из существующей
зарегистрированной цепочки инструментов; это не зависимости Runtime. Настройка и
команды lint, format, typecheck и test описаны в [Python QA](tools/python-qa/README.md).
Конфигурация Ruff и mypy в репозитории имеет приоритет перед общими настройками.

Публичные проверки исходников работают в чистом clone без проектного `.pf`:

```sh
python tools/validate-process-forge-schemas.py
python tools/validate-process-forge-checksums.py
python tools/validate-public-cleanliness.py
```

После изменения поставляемых файлов выполните
`python tools/validate-process-forge-checksums.py --write`, проверьте diff inventory
и повторите проверку. Запускайте существующие тесты и smoke-проверки затронутого
поведения. Для Python обязательны применимые Ruff lint/format и mypy; отличайте
прежние диагностики от новых ошибок. Массовое форматирование и устранение всего
техдолга не должны незаметно становиться частью небольшой задачи.

Изменения исполняемого кода требуют применимой проверки на настоящих Windows и
Linux, включая затронутые файловые, SQL и процессные сценарии. Подходят нативные
окружения и CI-раннеры. Подмена платформы, отсутствующий backend и `skip`/`xfail`
не заменяют обязательный сценарий. Для изменений только документации обосновывайте
неприменимость исполняемых тестов. Сохраняйте полезные неудачные результаты вместе
с исправленными прогонами и указывайте фактически проверенную ревизию.

## Pull request и ревью

Начинайте описание с проблемы и полученного поведения. Укажите состав изменений,
команды и результаты проверки, совместимость и оставшиеся ограничения. Ссылайтесь
на задачи, решения и сохраняемые доказательства; не публикуйте частные диалоги.
Ревью относится к итоговым изменениям. После новых правок повторяйте затронутые
проверки. Успешный запуск автоматизации сам по себе не является вердиктом.

Для изменений с участием ИИ действуют те же требования качества. Автор отвечает
за понимание кода, проверку результата и устранение подтверждённых замечаний.
Независимый ревьювер не должен выдавать собственную реализацию за независимо проверенную.

## Состав репозитория и параллельная работа

Корневой `.pf/` — локальное состояние окружения. Его задачи, историю, контексты,
журналы, секреты, кэш и временные файлы нельзя отслеживать или включать в поставку.
Существующий локальный каталог сохраняется; чужое частное состояние не должно
требоваться для сборки, тестирования или понимания исходников.

Перед первым обновлением старого checkout, где `.pf/` ещё отслеживается, сохраните
весь каталог в частной резервной копии вне этого checkout. При применении коммита
удаления Git может удалить неизменённые отслеживаемые файлы; `.gitignore` этому
не препятствует. После обновления восстановите нужное локальное состояние и
оставьте его игнорируемым. В свежем клоне `.pf/` отсутствует; прежняя история Git
этим изменением не переписывается.

Шаблоны продукта размещаются в `templates/`, публичные примеры — в `examples/`,
тестовые данные — рядом с тестами, постоянные пояснения — в `docs/`. Использование
`.pf` продуктом и пользовательскими fixtures сохраняется; оно не означает включение
корневого проектного `.pf` в репозиторий.

Независимым исполнителям выделяйте отдельные рабочие каталоги и понятные области
изменений. Код согласуется через ветки и PR, общие решения по задачам — в GitHub.
Перед уборкой сохраняйте нужную историю и доказательства. Рабочие базы и сведения
о процессах нельзя сливать как общую очередь задач. Не коммитьте машинные пути,
токены, файлы окружения и частные журналы. Удаляйте собственные одноразовые данные
после сохранения материалов для ревью или продолжения.

Агенты также соблюдают [AGENTS.md](AGENTS.md) и применимые вложенные инструкции.
После первичной подготовки содержательная разработка ведётся через локальные
контекст и Work PF. Runtime, MCP, Agent Ledger и hooks включаются по требованиям
выбранного процесса; штатный CLI остаётся допустимым входом. Общие инструкции
и первоначальная настройка доступны до создания Work.
